> [!NOTE] 이 글은 후속편입니다
> [IP는 등록했는데 포트 연결이 안 되는 이유](/posts/ip-allowed-but-port-blocked)에서 be와 ai를 GPU 서버로 옮겼습니다. 그러면 이번엔 반대 문제가 생깁니다. **GCP에 남은 fe가 사설망에 있는 be를 어떻게 부르는가.** 답은 SSH 리버스 터널이었고, 그 터널이 조용히 죽으면서 데모가 502를 뱉었습니다.

> [!WARNING] 숫자와 이름은 실제 값이 아닙니다
> 호스트 이름(`gpu-server`), 포트(`51234`, `8800`, `3100`, `45002`), 공인 IP(`203.0.113.10`, `198.51.100.7`), 도메인(`demo.example.com`)은 전부 임의로 잡은 값입니다. 공인 IP는 문서용으로 예약된 대역(RFC 5737)을 썼습니다. 구조와 인과 관계만 실제 그대로입니다.

## 1. 왜 서버가 2대인가

번역기는 fe → be → ai 3-tier인데, 배포는 2대로 쪼개져 있습니다. 이유는 하나입니다. **LLM이 GPU에 묶여 있기 때문입니다.**

|         | 사내 `gpu-server`                 | GCP `gcp-vm`              |
| ------- | --------------------------------- | ------------------------- |
| 있는 것 | be + ai + GPU/vLLM(`51234`)       | nginx(TLS) + web 컨테이너 |
| 없는 것 | 공인 도메인·인증서·안정적 공인 IP | GPU                       |
| 주소    | 사설 `192.168.0.71`               | 공인 `203.0.113.10`       |

GPU는 사무실 랙에 있는 물리 장비라 클라우드로 못 옮깁니다. 반대로 `demo.example.com`은 외부 사용자가 접속해야 하니 공인 IP와 TLS가 필요해서 GCP에 둡니다. 그래서 둘을 이어야 하고, 여기서 모든 문제가 시작됩니다.

## 2. GCP가 사내 서버를 직접 못 부르는 이유

`192.168.0.71`은 사설 IP입니다. RFC1918이 예약해둔 대역이 셋 있습니다.

```text
10.0.0.0/8        (10.x.x.x)          ← GCP 내부망이 이걸 씀
172.16.0.0/12     (172.16~31.x.x)     ← Docker 브리지가 이걸 씀
192.168.0.0/16    (192.168.x.x)       ← 사무실 랜이 이걸 씀
```

이 주소들은 인터넷에 라우팅되지 않습니다. 전 세계 수많은 사무실이 똑같이 `192.168.0.71`을 쓰고 있어서, GCP가 "192.168.0.71로 보내줘"라고 해봐야 어디로 보낼지 알 수가 없습니다. 라우터는 그냥 버립니다.

사무실은 NAT(Network Address Translation)로 인터넷에 나갑니다. 사내 장비들이 공유기의 공인 IP 하나를 나눠 쓰는 구조입니다.

```text
192.168.0.71  ─┐
192.168.0.31  ─┼─→ [공유기 NAT] ─→ 198.51.100.7 ─→ 인터넷
192.168.0.105 ─┘
```

여기서 **비대칭성**이 핵심입니다.

- **나가는 건 쉽다** — 사내 → 인터넷. NAT가 누가 요청했는지 기억했다가 응답을 되돌려줍니다.
- **들어오는 건 어렵다** — 인터넷 → 사내. 공유기에 `198.51.100.7:45002`로 뭐가 오면 사내 어느 장비로 보낼지 규칙(포트포워딩)을 미리 박아둬야 합니다. 공유기 관리 권한이 필요하고, 방화벽·보안 이슈도 따라옵니다.

처음엔 "공유기가 45002를 포워딩하는 구조인가?" 하고 의심했습니다. 아니었습니다. 실제로는 이 비대칭성을 역이용하고 있었습니다.

## 3. ssh -R — 나가는 연결로 들어오는 길을 만든다

들어오는 게 어렵고 나가는 게 쉽다면, 안쪽에서 밖으로 걸어 나가서 그 통로를 거꾸로 쓰면 됩니다. SSH가 이걸 지원합니다.

### 3-1. -L과 -R은 방향이 정반대다

`ssh -L`의 동작은 [앞 글](/posts/ip-allowed-but-port-blocked)에서 정리했습니다. 요약하면 이렇습니다.

```bash
# -L : 로컬 포워딩 — 내 쪽에 포트를 연다
ssh -L 51234:localhost:51234 gpu-server
```

내 PC의 `51234`에 연결하면 `gpu-server`의 `51234`로 갑니다. 저쪽 것을 끌어다 쓰는 것입니다.

```bash
# -R : 리버스(원격) 포워딩 — 저쪽에 포트를 연다
ssh -R 45002:localhost:3100 user@203.0.113.10
```

GCP의 `45002`에 연결하면, **명령을 실행한 이 박스**의 `3100`으로 갑니다. 내 것을 저쪽에 내어주는 것입니다.

기억법은 단순합니다. `-L`은 **L**ocal에 리스너가 생기고, `-R`은 **R**emote에 리스너가 생깁니다.

우리가 쓰는 건 `-R`입니다. 사내 서버가 GCP로 걸어 나가서, GCP에 `45002` 구멍을 뚫고, 그 구멍을 자기 `3100`으로 연결합니다. NAT를 정면 돌파하지 않고 우회합니다.

### 3-2. localhost의 기준점 — 가장 위험한 함정

```bash
ssh -R 45002:localhost:3100 user@203.0.113.10
                 ↑
        이 localhost는 누구인가?
```

**명령을 실행한 박스**입니다. GCP가 아닙니다. 그래서 이 한 줄은 **어느 박스에서 치느냐에 따라 뜻이 완전히 달라집니다.**

| 실행한 곳                   | 데모가 물게 되는 be              |
| --------------------------- | -------------------------------- |
| `gpu-server` (192.168.0.71) | 사내 서버의 be — 정답            |
| 내 노트북                   | 노트북에서 dev로 돌던 be         |
| GCP 자신                    | GCP의 3100 (아무것도 없음) → 502 |

잘못된 박스에서 띄우면 `/health`는 200이 뜨는데 로그인이 안 되는 상태가 됩니다. 겉으론 고쳐진 것처럼 보여서 원인 찾기가 훨씬 어려워집니다. 뒤에 나오는 볼륨 이야기(6-2)와 합쳐지면 특히 그렇습니다.

### 3-3. 왜 nginx가 127.0.0.1:45002를 보나

`-R`은 기본적으로 **원격 쪽 루프백에만 바인딩**합니다.

```text
LISTEN  127.0.0.1:45002     ← 0.0.0.0이 아님
LISTEN  [::1]:45002
```

즉 GCP 바깥에서는 `45002`에 직접 접근할 수 없습니다. GCP 안에서만 보입니다. 버그가 아니라 보안 기본값입니다. 안 그러면 인터넷 아무나 `45002`로 사내 be를 때릴 수 있게 됩니다. `GatewayPorts yes`로 풀 수 있지만 풀면 안 됩니다.

그래서 구조가 이렇게 됩니다.

```text
브라우저 ─TLS→ nginx(443) ─평문→ 127.0.0.1:45002 ─터널(암호화)→ 사내 be:3100
                   ↑                    ↑
            공개된 유일한 문      루프백이라 외부 차단
```

nginx가 유일한 공개 창구이고 TLS를 담당합니다.

### 3-4. 플래그

```bash
ssh -fN -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
    -R 45002:localhost:3100 user@203.0.113.10
```

| 플래그                     | 뜻                     | 왜 필요한가                         |
| -------------------------- | ---------------------- | ----------------------------------- |
| `-f`                       | 백그라운드로 감        | 터미널 닫아도 유지                  |
| `-N`                       | 명령 실행 안 함        | 셸이 필요 없고 터널만 원함          |
| `ExitOnForwardFailure=yes` | 포워딩 실패하면 죽어라 | 없으면 터널만 실패한 채 멀쩡한 척함 |
| `ServerAliveInterval=30`   | 30초마다 생존 확인     | NAT는 유휴 연결을 조용히 끊음       |
| `ServerAliveCountMax=3`    | 3번 실패하면 포기      | 90초 내에 죽은 걸 인지              |

`ExitOnForwardFailure`가 중요한 이유가 있습니다. 이게 없으면 `45002`가 이미 점유 중일 때 SSH는 포워딩 실패 경고만 찍고 연결은 유지합니다. 프로세스는 살아있으니 `ps`로 보면 정상 같은데 실제 터널은 없습니다. 최악의 실패 모드입니다. 죽으려면 시끄럽게 죽어야 합니다.

### 3-5. 왜 자꾸 끊기나

`-f`로 띄운 터널은 아무도 안 지켜줍니다. 죽는 경우는 많습니다.

- 사무실 인터넷 순간 끊김
- NAT 세션 타임아웃 (유휴 연결을 공유기가 조용히 정리)
- GCP sshd 재시작 / 서버 재부팅
- 노트북 절전

죽으면 아무도 안 살립니다. 그래서 autossh와 systemd가 필요합니다.

- **autossh** — 터널 상태를 감시하다 끊기면 재연결
- **systemd** — `Restart=always`로 autossh 자체가 죽어도 재시작, `enable`로 부팅 시 자동 시작

이 조합이 있어야 설정하고 잊어버릴 수 있습니다. 수동으로 띄운 터널은 언젠가 반드시 끊깁니다.

## 4. nginx 리버스 프록시 — proxy_pass 끝의 /

GCP nginx 설정입니다.

```nginx
server_name demo.example.com;
location /     { proxy_pass http://127.0.0.1:3000;   }   # web 컨테이너
location /api/ { proxy_pass http://127.0.0.1:45002/; }   # ← 터널 종단
```

끝에 `/`가 있으면 **location 접두사를 떼고** 넘깁니다.

```text
브라우저: /api/auth/login  →  be가 받는 것: /auth/login   ← /api 제거됨
```

`/`가 없으면 `/api/auth/login`이 그대로 갑니다. be는 라우트가 `/auth/login`(전역 prefix 없음)이라 `/api`가 붙으면 404가 납니다. 로컬에서 확인하면 이렇습니다.

```text
localhost:3100/auth/login      → 401  ← 정상
localhost:3100/api/auth/login  → 404  ← /api 붙이면 없는 라우트
```

이게 "fe는 `/api/*`로 부르는데 be는 루트로 서빙한다"는 구조가 성립하는 이유입니다. dev 환경에선 vite가 같은 rewrite를 해줍니다.

## 5. 502와 503은 다른 곳에서 나온다

이번 장애에서 502와 503을 둘 다 봤는데, **원인이 완전히 다른 문제**였습니다. 구분법이 응답 자체에 있습니다.

먼저 코드의 의미부터 정리합니다.

| 코드 | 이름                | nginx 기준 의미              |
| ---- | ------------------- | ---------------------------- |
| 502  | Bad Gateway         | 업스트림에 연결 자체가 안 됨 |
| 503  | Service Unavailable | 서비스 이용 불가             |
| 504  | Gateway Timeout     | 연결은 됐는데 응답이 안 옴   |

여기서 중요한 건 **502/503/504는 nginx만 내는 게 아니라는 점**입니다. 백엔드 앱도 냅니다. 이게 결정적이었습니다.

### 502 — nginx가 만든 것

```html
<html>
  <head>
    <title>502 Bad Gateway</title>
  </head>
  <center><h1>502 Bad Gateway</h1></center>
  <hr />
  <center>nginx/1.24.0 (Ubuntu)</center>
</html>
```

HTML이고 하단에 nginx 서명이 있습니다. nginx가 만든 응답입니다. be에 도달조차 못 했다는 뜻이고, 곧 **터널이 죽었다**는 뜻입니다.

### 503 — be가 만든 것

```text
content-type: application/json; charset=utf-8
x-powered-by: Express          ← ★
etag: W/"ad-HjIijnY5y8JtEIAAxryh8U0ZKF4"

{"code":"AI_UNAVAILABLE", ...}
```

JSON이고 `x-powered-by: Express`가 붙었습니다. Express는 NestJS가 내부적으로 쓰는 HTTP 프레임워크입니다. **nginx는 이 헤더를 만들 줄 모릅니다.**

즉 be가 직접 응답한 것이고, 따라서 터널은 살아 있었고, be가 ai에 못 붙은 것입니다. 헤더 한 줄이 문제의 절반을 잘라냅니다.

### 코드로 확증

be 전체에서 503을 내는 곳을 찾으니 한 군데였습니다.

```ts
// translation.service.ts
if (code === "ECONNREFUSED" || code === "ENOTFOUND" || code === "EAI_AGAIN") {
  return this.build(HttpStatus.SERVICE_UNAVAILABLE, "AI_UNAVAILABLE", ...);
}
```

이 `toHttpException`은 네트워크 에러 코드를 HTTP 상태로 번역합니다.

| Node 에러                    | 뜻                             | → HTTP |
| ---------------------------- | ------------------------------ | ------ |
| `ECONNREFUSED`               | 포트에 아무도 없음 (즉시 거부) | 503    |
| `ENOTFOUND` / `EAI_AGAIN`    | DNS 실패 — 이름을 못 찾음      | 503    |
| `ECONNABORTED` / `ETIMEDOUT` | 응답 없음                      | 504    |
| `ECONNRESET` / `EPIPE`       | 연결이 끊김                    | 502    |

503이 나왔다는 건 이 중 하나이고, ai 컨테이너가 죽었거나 DNS로 못 찾았다는 뜻입니다. 범위가 확 좁혀집니다.

> [!TIP] 상태 코드만 보지 말고 응답 본문과 헤더를 봐야 합니다
> 같은 503이라도 nginx가 낸 것과 앱이 낸 것은 원인이 정반대입니다. `curl -i`로 헤더까지 보면 어느 계층까지 도달했는지가 그대로 드러납니다.

## 6. Docker에서 걸리는 것들

### 6-1. 내부 DNS — ai가 죽으면 DNS부터 실패한다

```yaml
be:
  environment:
    AI_API_URL: "http://ai:8800" # ← 'ai'가 호스트명?
ai:
  # 포트를 밖으로 안 염
```

`ai`는 공인 DNS에 없는 이름인데 왜 될까요. Docker Compose가 **서비스 이름으로 내부 DNS를 만들어주기 때문**입니다. 같은 compose 네트워크(여기선 `172.24.0.0/16`) 안에서 `ai` → `172.24.0.2`로 해석됩니다.

그래서 두 가지가 따라옵니다.

- `ai`는 포트를 밖에 안 열어도 됩니다. be만 내부 네트워크로 부르면 됩니다. 보안상 좋습니다. ai는 인증이 없어서 외부에 노출되면 안 됩니다.
- 대신 ai 컨테이너가 죽으면 **DNS 해석 자체가 실패**해서 `EAI_AGAIN`/`ENOTFOUND`가 납니다. 위 표대로 503입니다.

ai 검증은 호스트에서 컨테이너 IP를 직접 찔러서 했습니다.

```text
172.24.0.2:8800/docs → 200      ← ai 살아있음
```

### 6-2. 볼륨 — DB가 여기 있습니다

```yaml
volumes:
  - be-db:/data
```

`DATABASE_URL: "file:/data/prod.db"` — SQLite 파일 하나가 볼륨에 있습니다. 컨테이너를 지우고 다시 만들어도 볼륨은 남습니다. `--build`를 아무리 해도 회원 정보가 안 날아가는 이유입니다.

단 `docker compose down -v`를 하면 볼륨까지 지웁니다. 회원·용어집·설비 파일이 전부 사라집니다. `-v`를 조심해야 합니다.

그리고 이게 **3-2의 "엉뚱한 박스에서 터널 띄우면 안 되는" 이유**이기도 합니다. 박스마다 볼륨이 다르니 DB가 다릅니다. be는 멀쩡히 200을 주는데 계정이 없어서 로그인이 안 되는 상황이 됩니다.

> [!CAUTION] compose 프로젝트 이름은 디렉터리 이름입니다
> `/home/user/demo`에서 실행하면 네트워크는 `demo_default`, 볼륨은 `demo_be-db`가 됩니다. 클론 위치를 옮기면 다른 프로젝트가 되어 볼륨도 새로 생깁니다. DB가 사라진 것처럼 보이는 함정이 여기 있습니다.

### 6-3. 권한이 없어도 ps로 읽을 수 있다

`docker` 소켓도 sudo도 없는 상태였는데, 포트를 퍼블리싱하면 `docker-proxy` 프로세스가 뜹니다.

```text
04:08  docker-proxy -host-port 3100 -container-ip 172.24.0.3    ← 재빌드 시각
Apr29  docker-proxy -host-port 28008 -container-ip 172.22.0.2   ← 다른 프로젝트
```

`ps`만으로 언제 재빌드했는지, 컨테이너 IP가 뭔지를 읽어냈습니다. 컨테이너 안의 프로세스는 호스트 `ps`에 전부 보입니다. PID 네임스페이스는 컨테이너 안쪽만 격리하고, 호스트에선 다 보입니다. ai의 uvicorn도 이렇게 찾았습니다.

```text
root  918466  python3.12 /usr/local/bin/uvicorn app.api:app --host 0.0.0.0 --port 8800
```

## 7. git — 이름이 같은데 다른 브랜치

원격의 `perf/optimization`을 받으려고 했는데, 정작 로컬 브랜치엔 그 코드가 없었습니다.

```bash
git checkout -b perf/optimization     # 실제로 친 것
```

`-b`는 **현재 HEAD(=main)에서 새 브랜치를 만듭니다.** 원격은 쳐다도 안 봅니다. 그래서 이름만 `perf/optimization`인 main의 복사본이 생겼습니다.

```bash
git checkout perf/optimization        # 의도했던 것
```

로컬에 그 이름이 없으면 git이 DWIM(Do What I Mean)으로 `origin/perf/optimization`을 찾아 추적 브랜치로 만들어줍니다.

함정은 여기입니다. **일단 `-b`로 껍데기를 만들고 나면, 그 다음부터 `git checkout perf/optimization`은 DWIM을 안 합니다.** 로컬에 이미 있으니 그걸 씁니다. 계속 껍데기에 갇힙니다.

`git branch -vv`로 알 수 있었습니다.

```text
  main              2c460d1 [origin/main] fix: yaml 수정
* perf/optimization 2c460d1 fix: yaml 수정      ← [origin/...] 없음 = 추적 안 함
```

그리고 더 근본적인 사실이 있습니다. **커밋은 가져와야 존재합니다.** `ed71144` 커밋이 로컬 저장소에 아예 없었습니다. 브랜치를 어디로 옮기든 없는 커밋은 나타나지 않습니다. git은 분산 VCS라 `origin/perf/optimization`은 "마지막으로 fetch했을 때 원격이 이랬다"는 로컬 스냅샷일 뿐입니다. fetch 안 하면 영원히 모릅니다.

fetch하고 나니 `ed71144`의 부모가 `2c460d1`, 즉 로컬이 서 있던 자리였습니다. 갈라진 게 없으니 합칠 것도 없고 포인터만 밀면 됩니다. fast-forward입니다.

> [!NOTE] fast-forward와 divergent
> 어떤 상황에서 fast-forward가 되고 안 되는지는 [git fetch, pull, 그리고 fast-forward가 안 될 때](/posts/git-fetch-pull-and-divergent-branches)에 정리해뒀습니다. `git merge-base --is-ancestor A B`가 이걸 판정해줍니다.

`reset --hard`도 짚어둘 만합니다. reset은 "되돌리기"가 아니라 **"현재 브랜치를 지정한 커밋으로 옮겨라"**입니다. 방향은 목적지가 어디냐에 달렸습니다. `reset --hard origin/perf/optimization`은 `ed71144`로 **앞으로** 갑니다. 이름이 reset이라 되돌리기처럼 들리는 게 함정입니다. 위험한 건 딱 하나 — 커밋 안 한 변경을 말없이 날립니다. 그래서 실행 전에 `git status --porcelain`으로 깨끗한지 먼저 확인했습니다. `--ff-only`가 심리적으로 안전한 이유도 같습니다. 뒤로 가는 게 구조적으로 불가능하고, 애매하면 에러 내고 멈춥니다.

## 8. 실제 타임라인

```text
04:07  git checkout -b perf/optimization   ← main 껍데기 생성 (perf 코드 없음)
04:08  docker compose up --build -d        ← main 코드로 be+ai 재빌드
       ↓
       이 시점 사내 be = main 코드 (/health 없음)
       데모 be = ??? (perf 코드, /health 있음)  ← 서로 다름

04:14  데모 502   ← 터널 죽음
04:17  데모 503   ← 터널 살아있음 + ai 죽음 (x-powered-by: Express가 증거)
04:19  데모 401   ← 정상 (터널·ai 모두 복구)
04:25  데모 /api/health 200  ┐
       사내 /health 404      ┘ ← 두 be가 다르다는 결정적 증거
04:36  main pull + 재빌드     ← 이제 사내 be에도 perf 코드 들어감
04:40  데모 502 (20/20)      ← 터널 완전히 죽음
05:0x  터널 재생성           ← 복구
```

`docker compose up --build -d`는 원인이 아니었습니다. 재배포할 때마다 로그인해 봤기 때문에, **이미 죽어 있던 터널을 그때 발견한 것뿐**입니다. 인과가 반대였습니다.

전형적인 상관관계와 인과관계의 혼동입니다. "재배포하면 502가 뜬다"는 관찰은 사실이었지만, 재배포가 502를 만든 게 아니라 재배포가 502를 확인하는 계기였습니다.

## 9. 어떻게 좁혔나

### 9-1. 경계마다 찔러서 구간을 자른다

경로가 길면 양 끝이 아니라 중간을 찌릅니다.

```text
브라우저 → nginx → 터널 → be → ai → LLM
            ①      ②     ③    ④    ⑤
```

| 검사                           | 결과     | 잘라낸 것       |
| ------------------------------ | -------- | --------------- |
| `localhost:3100/health`        | 200      | be 정상         |
| `172.24.0.2:8800/docs`         | 200      | ai 정상         |
| `192.168.0.71:51234/v1/models` | 200      | LLM 정상        |
| GCP `ss \| grep 45002`         | 비어있음 | ← 여기가 끊겼다 |

각 검사가 경로의 절반씩 날립니다. 처음부터 로그를 뒤지는 것보다 훨씬 빠릅니다.

### 9-2. 지문 — 두 개가 같은 놈인지 판별

가장 결정적이었던 기법입니다. "데모의 be와 이 박스의 be가 같은가"를 알아야 했는데, **한쪽에만 있는 특징**을 찾으면 됩니다.

`ed71144`가 `health.controller.ts`를 새로 추가한다는 걸 알아냈으니 이렇게 됩니다.

```text
데모  /api/health  → {"status":"ok"} 200   ← health 있음
로컬  :3100/health → 404                    ← health 없음
```

같은 be라면 불가능한 조합입니다. 이걸로 "데모 be는 여기가 아니다"를 확정했습니다.

### 9-3. 능동 프로브 — 안 되면 만들어서 확인

`/api`가 `45002`를 쓴다는 걸 알았는데 이 박스엔 `45002`가 없었습니다. 그래서 직접 `45002`를 열고 데모를 때려봤습니다.

```text
45002 바인딩 → 데모에 6번 요청 → 인바운드 0건
```

0건이라는 게 "데모 트래픽은 이 박스의 45002로 오지 않는다"를 증명했습니다. 터널이 GCP 루프백에 뜬다는 걸 몰랐을 때, 이 실험이 잘못된 가설을 잘라냈습니다.

### 9-4. 권한이 없어도 읽을 수 있는 것들

| 소스                | 알아낸 것                         |
| ------------------- | --------------------------------- |
| `ps aux`            | 컨테이너 안 프로세스, 재시작 시각 |
| `docker-proxy` 인자 | 포트 매핑, 컨테이너 IP            |
| `ss -tlnp`          | 리스닝 포트                       |
| `ip route`          | Docker 브리지 서브넷              |
| `git reflog`        | `-b`로 브랜치 만든 시각           |
| `/var/log/auth.log` | SSH 접속 이력 (adm 그룹)          |

`git reflog`가 특히 결정적이었습니다. `branch: Created from HEAD` 한 줄이 `checkout -b`를 썼다는 증거였습니다.

### 9-5. 틀렸던 것들

| 오판                          | 왜                                                            |
| ----------------------------- | ------------------------------------------------------------- |
| "45002 포트포워딩 구조일 것"  | 리버스 터널이라는 선택지를 몰랐음. 배포 문서에 한 줄도 없었음 |
| "메모리 상한 4g가 원인"       | 최근 변경 = 원인 편향. 로그도 못 본 채 가설을 밀었음          |
| "VPN 출구 IP가 사내 서버"     | IP만 보고 서버라 단정. VPN 출구일 가능성을 못 떠올림          |
| "호스트명이 다르니 다른 장비" | hostname과 ssh config 별칭이 다를 수 있다는 걸 놓침           |

메모리 상한 건은 헛다리의 대표 사례입니다. compose에 이런 게 있었습니다.

```yaml
deploy:
  resources:
    limits:
      memory: 4g
```

`deploy`는 원래 Docker Swarm 전용 필드였고 옛날 `docker compose up`은 무시했는데, compose v2부터는 적용합니다. 이건 runaway 백스톱입니다. 메모리 누수가 터졌을 때 호스트 전체를 죽이지 말고 컨테이너만 OOM kill 되게 하는 안전장치라 나쁜 게 아닙니다. 다만 이 박스 RAM이 약 500GB라 4g는 1%도 안 됩니다. 주석에 "호스트 RAM의 50~70%로 튜닝"이라고 명시적으로 경고돼 있는데 아무도 안 고친 상태였습니다.

그래도 이번 문제와는 무관했습니다. be는 4g를 건드리지도 않았습니다. "perf 브랜치가 뭘 바꿨지?" → "메모리 상한 추가!" → "이거다!"로 갔는데, 증거(로그)를 못 본 상태에서 가설을 너무 밀었습니다.

## 10. 정리

1. **NAT는 비대칭이다.** 나가는 건 쉽고 들어오는 건 어렵습니다. `ssh -R`은 이 비대칭을 역이용해서 안쪽에서 밖으로 나간 연결을 거꾸로 씁니다.
2. **`-R`의 `localhost`는 명령을 실행한 박스 기준이다.** 어느 박스에서 치느냐로 데모가 물 be가 결정됩니다. 박스마다 Docker 볼륨이 달라서 DB도 다릅니다.
3. **502/503/504는 nginx만 내는 게 아니다.** `x-powered-by: Express` 한 줄이 "터널은 살아있었다"를 증명합니다. 상태 코드가 아니라 응답을 만든 주체를 봐야 합니다.
4. **수동으로 띄운 터널은 반드시 끊긴다.** autossh + systemd가 없으면 같은 일이 반복됩니다.
5. **상관관계를 인과관계로 읽지 말 것.** 재배포는 502를 만든 게 아니라 502를 발견하게 한 계기였습니다.

경로가 긴 시스템에서는 어느 구간이 끊겼는지부터 자르는 게 로그를 뒤지는 것보다 빠릅니다. 그리고 그 구간을 자르는 정보는 응답 본문과 헤더에 이미 들어있는 경우가 많습니다.
