회사에서 AI가 만든 보고서 docx를 브라우저에 띄워야 합니다. docx-preview로 띄우면 워드와 다르게 나옵니다. 표 옆 좁은 틈에 제목이 한 글자씩 세로로 서고, 번호가 전부 `0-1`로 나오고, 99페이지 문서가 아주 긴 페이지 하나로 나옵니다.

두 달 동안 하나씩 고쳤지만 아직 워드와 같지 않습니다. 지금은 다른 렌더링 엔진으로 바꿔서 테스트하고 있습니다. ~~엔진을 바꾸면 두 달 동안 고친 코드는 대부분 지웁니다.~~

왜 이렇게 어려운지, 그럼 어떻게 렌더링해야 하는지 정리했습니다.

> [!NOTE] 이 글의 요점
> docx에는 줄바꿈 위치와 페이지 정보가 없습니다. 파일을 여는 프로그램이 폰트로 글자 폭을 재서 그때 계산합니다. docx-preview는 docx를 HTML/CSS로 바꿀 뿐 이 계산을 하지 않아서, 직접 고친 부분만 워드와 맞습니다. 워드 PDF를 기준으로 비교하면 10페이지짜리 섹션에서 첫 줄이 워드와 같은 페이지가 docx-preview는 1개, docx-editor는 8개였습니다.

## 왜 어려울까

### 1. docx에는 줄과 페이지 정보가 없다

docx 압축을 풀면 문단, 텍스트 조각(run), 스타일, 번호 정의, 구역 설정이 XML로 들어 있습니다. 어느 줄이 어디서 끊기는지, 그 줄이 몇 페이지에 있는지는 없습니다. PDF에는 글자마다 좌표가 있지만 docx에는 없습니다.

```xml
<!-- 문단 하나. 폰트·크기·간격은 있지만 줄바꿈 위치와 페이지는 없다 -->
<w:p>
  <w:pPr><w:spacing w:after="120" w:line="360" w:lineRule="auto"/><w:keepNext/></w:pPr>
  <w:r><w:rPr><w:rFonts w:eastAsiaTheme="minorEastAsia"/><w:sz w:val="22"/></w:rPr>
    <w:t>본 시험에 참여한 20명 모두 시험을 완료하였다.</w:t></w:r>
</w:p>
```

줄과 페이지는 파일을 여는 프로그램이 계산합니다. 워드는 폰트 파일로 글자 폭을 재고, 자기 규칙으로 줄을 나누고, 줄을 페이지에 채우고, 페이지가 정해진 다음 페이지 번호 같은 필드를 채웁니다. 워드로 저장한 파일에는 마지막으로 페이지가 나뉜 위치(`w:lastRenderedPageBreak`)가 남지만 참고용입니다. 워드로 한 번도 저장하지 않은 AI 출력에는 이것도 없습니다.

### 2. 워드의 레이아웃 규칙은 공개되지 않았다

docx 형식은 ECMA-376이라는 공개 표준입니다. 표준은 각 요소가 무슨 뜻인지만 정하고, 줄과 페이지에 어떻게 배치하는지는 정하지 않습니다. 실제 기준은 워드가 렌더링한 결과인데, 워드의 레이아웃 규칙은 공개되지 않았습니다. 같은 파일도 호환 설정(`w:compat`)에 따라 워드가 다르게 배치합니다.

그래서 워드가 아닌 렌더러는 전부 워드 결과를 보고 규칙을 맞춰 만듭니다. 렌더러마다 결과가 조금씩 다른 이유입니다.

### 3. 브라우저는 CSS 규칙으로 렌더링한다

docx를 HTML/CSS로 바꾸면 줄바꿈과 높이는 브라우저가 CSS 규칙으로 정합니다. 워드와 규칙이 다른 곳이 많습니다.

| 워드                                                              | 브라우저(HTML/CSS)                                                                          |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 내용을 A4 페이지에 채우고, 넘치면 다음 페이지로 보냄              | 화면에는 페이지가 없다. 세로로 계속 이어진다. CSS 페이지 나누기 속성은 인쇄할 때만 적용된다 |
| 줄 간격 1.5줄은 폰트 파일에 정의된 한 줄 높이의 1.5배             | `line-height: 1.5`는 폰트와 상관없이 글자 크기의 1.5배                                      |
| 한글과 숫자 사이를 조금 띄움(`w:autoSpaceDN`)                     | 붙여서 렌더링한다. "20명"에서 워드는 20과 명 사이가 벌어지고 브라우저는 붙는다              |
| 다음 단락과 함께(`keepNext`), 외톨이 줄 제어(`widowControl`)      | CSS에도 `break-after: avoid`, `widows`가 있지만 페이지를 나눌 때만 적용된다                 |
| 페이지를 넘는 표는 행 단위로 자르고 머리글 행(`tblHeader`)을 반복 | 표를 페이지 단위로 자르지 않는다                                                            |
| 위치를 지정한 표(`tblpPr`) 둘레로 텍스트를 배치                   | `float`로 비슷하게 만든다                                                                   |
| 구역마다 다른 머리글·바닥글, 페이지 번호·목차 필드                | 페이지가 없으니 페이지 번호를 계산할 수 없다                                                |
| 페이지 테두리(`pgBorders`)                                        | 페이지가 없으니 페이지 테두리도 없다                                                        |

docx-preview 코드를 보면 줄 간격을 이렇게 바꿉니다.

```js
// docx-preview 0.4.0 · parseSpacing. w:line은 auto일 때 1/240줄, 그 밖에는 1/20pt 단위
switch (lineRule) {
  case "auto":
    // 360 → 1.50. 글자 크기의 1.5배
    style["line-height"] = `${(line / 240).toFixed(2)}`;
    break;
  case "atLeast":
    // "최소 18pt"가 "글자 크기 + 18pt"가 된다
    style["line-height"] = `calc(100% + ${line / 20}pt)`;
    break;
  default:
    style["line-height"] = style["min-height"] = `${line / 20}pt`;
    break;
}
```

워드의 한 줄 높이는 폰트 파일에 적힌 위아래 높이로 정해서 폰트마다 다릅니다. CSS로 바꾸면 글자 크기 기준이 됩니다. `atLeast`(최소 높이)는 글자 크기에 지정값을 더한 높이가 돼서 워드보다 줄 간격이 넓어집니다. 문단 속성 중 `keepNext`, `keepLines`, `widowControl`은 읽기만 하고 CSS로 바꾸지 않습니다.

### 4. 폰트가 다르면 줄바꿈이 달라진다

글자 폭은 폰트마다 다릅니다. 한 줄에서 한 글자만 넘쳐도 줄이 하나 늘고, 줄이 하나 늘면 뒤 페이지가 전부 밀립니다. 2페이지에서 한 줄이 넘치면 3페이지 첫 줄이 바뀌고, 그 뒤 페이지도 전부 바뀝니다. 페이지 수가 같아도 페이지마다 시작하는 내용은 다를 수 있습니다.

문서에 폰트가 임베드되어 있지 않으면 보는 PC에 설치된 폰트로 대체합니다. 워드도 마찬가지입니다. HY신명조가 없는 맥 워드는 HY신명조 부분을 바탕체로 렌더링했습니다. 같은 워드라도 PC의 폰트와 OS가 다르면 결과가 다를 수 있습니다.

브라우저에서 워드와 같게 띄우려면 폰트로 글자를 재고, 워드 규칙으로 줄을 나누고, 페이지를 나누고, 필드를 채우는 일을 브라우저에서 다시 해야 합니다. 워드프로세서의 레이아웃 엔진을 하나 만드는 일입니다.

## docx-preview로 띄웠을 때 나온 문제

docx-preview는 서버 없이 브라우저에서 docx를 렌더링하는 Apache-2.0 라이브러리입니다. docx를 HTML/CSS로 바꾸고, 줄바꿈과 크기는 브라우저에 맡깁니다. 실제 보고서를 넣으면 에러는 없는데 결과가 워드와 달랐습니다. 원인을 라이브러리 코드까지 확인하고, 렌더링된 DOM을 후처리해서 하나씩 고쳤습니다.

| 증상                                         | 원인                                                                                               | 고친 방법                                    |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 고정 폭 표의 칸 폭이 글자 길이에 따라 바뀐다 | `tblLayout`을 `table-layout: fixed`로 바꾸지만, 표 너비가 `auto`면 브라우저가 자동 폭으로 배치한다 | colgroup의 열 너비로 고정 폭을 다시 적용     |
| 99페이지 문서가 긴 페이지 하나로 나온다      | 페이지를 계산하지 않는다. 문서에 적힌 페이지 나누기에서만 나눈다                                   | 렌더링 후 A4 높이로 재서 나누는 `paginate`   |
| 여러 페이지에 걸친 표에 머리글 행이 없다     | `tblHeader`를 읽지만 렌더링에 쓰지 않는다                                                          | XML에서 머리글 행 수를 세서 페이지마다 붙임  |
| 워드가 남긴 위치로 나누면 페이지 아래가 빈다 | `lastRenderedPageBreak`에서 나눈다. 워드가 워드 폰트로 계산한 위치다                               | 무시함(빈 공간 실측 547px)                   |
| 한글이 앱 기본 폰트로 나온다                 | 테마 한글 폰트(`eastAsiaTheme`)를 무시한다                                                         | styles.xml → theme1.xml을 따라가 폰트를 적용 |
| 용지 크기가 없는 문서가 한 페이지로 나온다   | 용지 높이를 모르면 나눌 기준이 없다(실측 2555px)                                                   | A4로 간주하고 화면에 알림                    |
| 번호가 0-1, 0-1, 0-1                         | 번호를 CSS 카운터로 센다                                                                           | numbering.xml을 읽어 번호를 직접 계산        |
| 섹션 끝에 빈 페이지가 하나 더 나온다         | 섹션 끝의 페이지 나누기에서 새 페이지를 만든다                                                     | 마지막 빈 페이지를 제거                      |

고친 방법은 전부 같습니다. docx-preview가 렌더링을 끝낸 DOM을 받아서 직접 수정합니다. 가장 큰 작업은 페이지 나누기입니다. 브라우저가 배치한 요소마다 아래쪽 좌표를 재서, A4 한 페이지의 아래 여백을 넘는 요소부터 새 페이지로 옮깁니다.

```js
// paginate: 렌더링이 끝난 뒤 좌표를 재서 나눈다
for (const page of pages) {
  // 페이지 위쪽 + A4 높이 − 아래 여백 − 바닥글이 여백을 넘친 높이
  const edge = page.top + A4_HEIGHT - page.paddingBottom - footerOverflow(page);
  for (const node of page.flow.children) {
    if (node.bottom + node.marginBottom <= edge) continue;
    // 표는 행 단위로 자르고 머리글 행을 다시 붙인다. 나머지는 그 요소부터 새 페이지로 옮긴다
    if (isTable(node)) moveRowsBelow(node, edge, { repeatHeaderRows });
    else moveFrom(node, addPageAfter(page));
    break;
  }
}
```

번호는 원인이 다섯 개였습니다. docx-preview는 번호를 CSS 카운터로 셉니다. 한 페이지에 문서 두 개를 렌더링하면 카운터 초기화 규칙이 같은 선택자(`:root`)에 두 번 들어가서, 나중에 렌더링한 문서의 규칙만 남습니다.

```css
/* 문서마다 docx-preview가 만드는 초기화 규칙. 선택자가 같아서 뒤의 것만 적용된다 */
:root {
  counter-reset: docx-1-num-44-0 0;
}
:root {
  counter-reset: docx-2-num-44-0 0;
}
```

초기화가 없는 문서는 문단마다 카운터가 새로 생겨서 매번 1이 됩니다. 상위 번호가 없으면 `%1-%2` 형식에 0이 들어가고, 같은 목록 정의를 쓰는 번호를 따로 세고, ①②③을 1·2·3으로 렌더링하는 문제도 있었습니다. 그래서 번호 계산은 numbering.xml을 읽어 직접 하고, 1·가·① 같은 숫자 모양만 docx-preview CSS에 맡겼습니다. 24개 섹션의 번호 문단 282개가 LibreOffice 결과와 같아졌습니다.

### float 표 옆으로 제목이 들어간다

표 옆에 제목이 세로로 서는 문제는 위치를 지정한 표(`w:tblpPr`) 때문이었습니다. docx-preview는 이런 표를 무조건 `float: left`로 렌더링합니다.

```js
// docx-preview 0.4.0 · parseTablePosition
table.cssStyle["float"] = "left";
table.cssStyle["margin-bottom"] = values.addSize(table.cssStyle["margin-bottom"], bottomFromText);
table.cssStyle["margin-left"] = values.addSize(table.cssStyle["margin-left"], leftFromText);
table.cssStyle["margin-right"] = values.addSize(table.cssStyle["margin-right"], rightFromText);
table.cssStyle["margin-top"] = values.addSize(table.cssStyle["margin-top"], topFromText);
// 텍스트와의 간격(*FromText)만 읽는다. tblpX · tblpY · tblpXSpec(가운데 정렬)는 읽지 않는다
```

문제가 된 섹션은 본문 폭이 9026twip, 표 폭이 8500twip이고, 표 좌우로 텍스트와 142twip씩 간격을 둡니다. 남는 틈은 9026 − 8500 − 284 = 242twip, 약 16px입니다. 다음 제목이 이 틈으로 들어가서 한 글자씩 줄바꿈됩니다. 워드는 같은 문서에서 제목을 표 아래에 둡니다.

회사 문서는 올릴 수 없어서, 같은 구조의 표를 다른 내용으로 만들어 같은 버전(0.4.0)과 같은 옵션으로 렌더링했습니다.

![docx-preview로 렌더링한 재현 문서. "1-1. 참여자 정보" 아래 4행 2열 표가 있고, 표 오른쪽 좁은 틈에 "1-"와 "2."가 두 줄로 세로로 서 있다. 그 아래 "중도 탈락자"만 표 밑에 따로 놓이고 본문이 이어진다.](/posts/why-docx-breaks-in-the-browser/float-docx-preview.png)

틈은 15px, 제목 문단 높이는 89px이었습니다. 표의 float만 풀면 20px, 한 줄이 됩니다.

![같은 문서에서 표의 float만 푼 모습. "1-2. 중도 탈락자"가 표 아래에 한 줄로 놓이고, "참여한 20명 모두 시험을 끝냈다." 문장과 "1-3. 측정 결과"가 이어진다.](/posts/why-docx-breaks-in-the-browser/float-unfloated.png)

### 후처리로는 못 고치는 것

float를 푸는 건 한 줄이면 됩니다. 그런데 워드 PDF와 비교해 보니 이런 식으로는 못 고치는 문제가 두 개 더 있었습니다.

- 표 행을 페이지 사이에서 나누지 못합니다. 행 하나가 한 페이지보다 길면 `paginate`는 그 행을 통째로 다음 페이지로 넘기고, 그 페이지가 A4보다 길어집니다. 요약 보고서 섹션은 워드 8페이지가 3페이지로 나왔습니다.
- 바닥글 페이지 번호가 전부 같습니다. 페이지를 나눌 때 첫 페이지 바닥글을 그대로 복사해서 10페이지 내내 같은 번호가 나옵니다.

행 안의 줄을 페이지 사이에서 나누려면 그 행 안 텍스트의 줄 위치를 알아야 하고, 페이지 번호를 채우려면 페이지가 먼저 정해져야 합니다. `paginate`는 브라우저가 이미 배치한 요소를 옮기기만 하니 둘 다 못 합니다. 최신 버전 0.4.1도 `parseTablePosition` 코드가 같습니다. 고치면 고친 부분만 맞고, 다른 문서를 넣으면 고칠 곳이 또 나옵니다.

## 그럼 어떻게 렌더링해야 할까

### 변환형과 레이아웃 엔진형

브라우저용 docx 라이브러리는 두 종류입니다.

```yaml
변환형: docx를 HTML/CSS로 바꾼다. 줄바꿈은 브라우저 CSS가 하고 페이지는 없다. docx-preview, mammoth
레이아웃 엔진형: 폰트 파일로 글자 폭을 재서 줄을 나누고, 페이지를 나누고, 페이지 번호를 채운다. docx-editor, SuperDoc, ONLYOFFICE, LibreOffice
```

변환형은 앞에서 본 대로 워드와 같아질 수 없습니다. 레이아웃 엔진형은 워드와 같은 계산을 하지만 결과는 똑같지 않습니다. 2번에서 쓴 대로 엔진마다 워드 결과를 보고 규칙을 따로 만들었기 때문입니다. 줄 높이 계산, 한글을 어절 단위로 끊을지 글자 단위로 끊을지, 표 안의 표를 페이지 사이에서 나누는지, float 표를 어디에 두는지가 엔진마다 다릅니다.

측정해 보니 ONLYOFFICE는 줄 간격이 워드보다 5~7% 컸고, SuperDoc은 한글을 단어 중간에서 끊었고, docx-editor는 표 안의 표를 나누지 않았습니다. 폰트도 같아야 합니다. ONLYOFFICE는 문서에 임베드된 폰트를 쓰지 않았습니다.

### 워드로 렌더링하는 방법은 쓸 수 없다

완전히 같아야 하면 워드로 렌더링하는 방법밖에 없습니다. MS의 온라인 뷰어는 파일이 공개 URL로 열려야 하고, 편집기를 다른 서비스에 넣으려면 MS 파트너 프로그램에 가입해야 합니다. 사내 보고서는 외부에 올릴 수 없습니다. 서버에서 워드로 PDF를 만드는 방법은 MS가 서버 자동화를 지원하지 않고, 그렇게 만든 PDF는 수정할 수 없습니다.

그래서 목표를 "워드와 똑같이"에서 "같은 폰트로 렌더링했을 때 워드와 가장 많이 같은 엔진"으로 바꿨습니다.

### 기준은 워드 PDF

지금까지는 LibreOffice 결과를 기준으로 썼습니다. 서버가 내보내는 PDF를 LibreOffice가 만들기 때문입니다. 그런데 이건 "서버 PDF와 같은가"의 기준이지 "워드와 같은가"의 기준이 아닙니다. 서버에는 워드가 없어서 맥 워드에서 PDF로 저장해 받았습니다.

첫 PDF는 기준으로 쓸 수 없었습니다. 문서 본문 대부분이 HY신명조인데, PDF에 들어 있는 폰트에는 HY신명조가 없었습니다.

```yaml
문서에 지정된 폰트: HY신명조(5622곳), Times New Roman, 맑은 고딕
워드 PDF에 들어 있는 폰트: Batang, TimesNewRomanPSMT, MalgunGothic, ArialMT, GulimChe
측정 서버의 폰트: HY신명조 있음, 바탕·맑은 고딕 없음
```

그 맥에 HY신명조가 없어서 워드가 바탕체로 대체한 것입니다. 측정 서버는 반대로 HY신명조만 있습니다. 이 PDF로 비교하면 엔진 차이와 폰트 차이가 섞입니다.

다른 종류의 섹션 docx에는 폰트가 임베드되어 있었습니다(`w:embedTrueTypeFonts`, Times New Roman 4종, HY신명조 3종 등 11개). 이 섹션 두 개를 다시 워드 PDF로 받으니 PDF 폰트가 `H2mjsM`, 문서에 임베드된 HY신명조였습니다. 워드와 엔진이 같은 폰트 파일로 렌더링하는 조건이 됩니다.

비교는 페이지마다 첫 줄로 했습니다. 처음 만든 규칙은 너무 느슨했습니다. PDF는 텍스트를 화면 위치 순서로 읽고 DOM은 문서 순서로 읽어서 표의 칸 이름 순서가 바뀝니다. 이걸 허용하려고 "한쪽 첫 6글자가 다른 쪽 앞 30글자 안에 있으면 같은 페이지"로 했더니, "3) 주름깊이(눈밑)"로 시작하는 워드 6페이지와 "3-2) 주름깊이측정(팔자)"로 시작하는 페이지가 같다고 나왔습니다. 페이지가 하나씩 밀려 있었는데 점수는 올라갔습니다. 그래서 규칙을 좁혔습니다.

```python
# 페이지마다 첫 줄 비교. 한글·영문만 남긴다.
# 한쪽 첫 6글자가 다른 쪽 맨 앞에서 시작하면 같은 페이지로 본다.
# 앞에 표 칸 이름(4글자까지)이 붙는 것만 허용한다.
def same_start(a, b):
    a, b = letters(a), letters(b)
    return 0 <= b.find(a[:6]) <= 4 or 0 <= a.find(b[:6]) <= 4
```

> [!NOTE] 측정 환경
> 기준은 맥 워드(macOS 26.6.2)가 저장한 PDF입니다. 엔진은 docx-preview 0.4.0(직접 고친 코드 포함), docx-editor 2.34.0, SuperDoc 2.29.0, ONLYOFFICE Docs 9.4.0 Community Edition, LibreOffice 24.2입니다. 브라우저 엔진은 헤드리스 Chromium에서 렌더링했고, PDF를 내보내는 엔진은 PDF에서 텍스트를 뽑았습니다. 페이지마다 첫 줄만 비교했으므로 모든 줄이 같다는 뜻은 아닙니다. 윈도우 워드는 결과가 다를 수 있습니다.

### 엔진 넷 비교 결과

| 엔진                       | 섹션 A (워드 10페이지) | 섹션 B (워드 8페이지) | 섹션 A 바닥글 페이지 번호 | 임베드 폰트      |
| -------------------------- | ---------------------- | --------------------- | ------------------------- | ---------------- |
| docx-preview (지금 화면)   | 10페이지, 첫 줄 1/10   | 3페이지               | 1/10                      | 직접 고쳐서 사용 |
| LibreOffice (서버 PDF)     | 10페이지, 6/10         | 8페이지, 3/8          | 10/10                     | 사용             |
| ONLYOFFICE + HY신명조 설치 | 13페이지, 3/10         | 9페이지, 3/8          | 10/10                     | 사용 안 함       |
| SuperDoc                   | 10페이지, 8/10         | 8페이지, 3/8          | 10/10                     | 사용             |
| **docx-editor**            | **10페이지, 8/10**     | 10페이지, **5/8**     | 10/10                     | 사용             |

폰트가 임베드되지 않은 60페이지 완성본(워드가 바탕체로 대체한 것)으로도 비교했습니다. 폰트가 섞여 있어서 참고값입니다. docx-editor에 HY신명조와 Times New Roman을 넣으면 60페이지 중 43페이지의 첫 줄이 워드와 같았고, 안 넣으면 58페이지가 나왔습니다. 나머지 엔진은 54~62페이지로 페이지 수부터 달랐습니다.

ONLYOFFICE가 가장 많이 밀렸습니다. 워드와 가장 비슷하게 렌더링한다고 알려져 있어서 기대했던 엔진입니다. 같은 HY신명조를 서버에 설치해도 줄 간격이 워드보다 5~7% 컸습니다(표 행 30.7pt, 워드는 28.8pt). 표마다 뒤에 오는 그림이 다음 페이지로 밀려서 10페이지가 13페이지가 됐습니다.

서버 PDF도 워드와 절반만 같았습니다. 기준으로 쓰던 LibreOffice가 10페이지 중 6페이지만 워드와 같은 위치에서 나뉘었습니다. LibreOffice PDF는 텍스트를 뽑을 때 몇 글자가 깨져서, 실제로는 한두 페이지 더 맞을 수 있습니다.

SuperDoc은 섹션 A가 docx-editor와 같았지만 섹션 B가 3/8이었고, 편집 영역 경계에서 입력한 글자가 저장할 때 빠지는 문제가 있어서 뺐습니다.

## 지금 상태

docx-editor로 테스트 페이지를 만들어 확인하고 있습니다. 같은 폰트에서 워드와 같은 페이지가 가장 많았고, 서버 없이 브라우저에서 돌고, Apache-2.0입니다. docx-editor는 임베드된 폰트 파일을 불러와 HarfBuzz로 글자 폭을 재고, 페이지와 머리글·바닥글을 직접 배치합니다.

아직 교체하지 않았습니다. 워드와 다른 곳이 다섯 개 남아 있습니다.

1. 섹션 A의 두 번째 float 표를 다음 페이지로 밀어낸다. 2·3페이지가 어긋나고 4페이지에서 다시 맞는다.
2. 표 안의 표를 페이지 사이에서 나누지 않는다. 섹션 B가 10페이지가 된다.
3. 한글 굵게가 안 나온다. 문서에 임베드된 HY신명조 Bold 파일이 실제로는 weight 400이라 엔진이 굵게 렌더링하지 않는다.
4. 페이지 테두리를 렌더링하지 않는다.
5. 머리글 워터마크 그림 두 장이 어긋나서 겹친다.

이 다섯 개는 우리 코드에서 고치지 않고 docx-editor 저장소에 이슈와 PR로 올리기로 했습니다. 우리 쪽에서 후처리를 시작하면 docx-preview 때와 똑같아집니다. docx-editor는 7월에 처음 나와 11월에 2.34 버전일 만큼 빨리 바뀌어서, 버전을 고정하고 올릴 때마다 워드 PDF 비교를 다시 돌립니다.

폰트는 엔진과 별개로 해결해야 합니다. 폰트가 임베드되지 않은 서식은 서버에서 폰트를 넣어 달라고 요청했습니다. HY신명조, 맑은 고딕 같은 상용 폰트를 웹폰트로 내려보내려면 라이선스를 먼저 확인해야 합니다.

## 정리

- docx에는 줄과 페이지 정보가 없다. 파일을 여는 프로그램이 폰트로 계산한다. 워드와 같은 페이지가 필요하면 이 계산을 하는 레이아웃 엔진을 쓴다.
- docx를 HTML/CSS로 바꾸면 줄 간격, 페이지 나누기, 다음 단락과 함께 같은 워드 규칙이 CSS 규칙으로 바뀐다. 직접 고치면 고친 부분만 맞고, 페이지 번호와 표 행 나누기처럼 페이지가 먼저 정해져야 하는 건 후처리로 못 고친다.
- 레이아웃 엔진도 워드 규칙을 따로 만든 것이라 워드와 똑같지 않다. 같은 폰트에서 몇 페이지가 같은지 측정해서 고른다.
- 비교 기준은 워드 PDF로 정한다. LibreOffice 결과는 서버 PDF의 기준이지 워드의 기준이 아니다.
- 기준 PDF는 폰트부터 확인한다. PDF에 들어 있는 폰트가 문서에 지정된 폰트와 다르면 그 PDF로는 엔진을 비교할 수 없다.
- 비교 규칙은 틀린 경우로도 시험한다. 느슨한 규칙은 밀린 페이지를 같은 페이지로 셌다.
