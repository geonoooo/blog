회사에서 AI가 만든 보고서 docx를 화면에 띄우는 일을 맡았습니다. 서버에 워드가 없으니 브라우저에서 직접 그리는 수밖에 없었습니다.

처음엔 docx-preview를 썼는데 워드와 다르게 나오는 곳이 많았습니다. 표 옆 좁은 틈에 제목이 한 글자씩 세로로 서고, 번호는 전부 `0-1`이고, 99페이지짜리 문서는 아주 긴 한 페이지로 나왔습니다. 두 달 동안 하나씩 고쳤는데도 워드와 같아지지 않아서 결국 docx-editor로 바꿨습니다. ~~두 달 동안 고친 코드는 대부분 지웠습니다.~~

docx-editor에도 워드와 다른 곳은 남아 있었습니다. 이번에는 회사 앱에서 고치지 않고 docx-editor 저장소에 PR을 올렸습니다. 15개가 merge되면서 Contributors 목록에 이름이 올라갔습니다. 오픈소스 컨트리뷰터는 코딩을 아주 잘하는 사람들이나 하는 줄 알았는데, 저는 회사 문서가 깨져서 고쳤을 뿐입니다.

docx가 브라우저에서 왜 이렇게 어려운지, 엔진은 어떻게 골랐는지, PR은 어떤 순서로 올렸는지 정리했습니다.

> [!NOTE] 이 글의 요점
> docx에는 줄바꿈 위치와 페이지 정보가 없습니다. 파일을 여는 프로그램이 폰트로 글자 폭을 재서 그때그때 계산합니다. docx-preview는 HTML/CSS로 바꾸기만 하고 이 계산은 하지 않아서, 직접 고친 부분만 워드와 맞습니다. 워드 PDF와 페이지별 첫 줄을 맞춰 보면, 10페이지짜리 섹션에서 docx-preview는 1페이지, docx-editor는 8페이지가 워드와 같았습니다. docx-editor에 남은 문제는 원본 저장소에 PR로 올렸습니다. PR 하나에 버그 하나만 담고, 고치기 전 코드에서 실패하는 테스트를 같이 넣었습니다.

## 왜 어려울까

### 1. docx에는 줄과 페이지 정보가 없다

docx 압축을 풀면 문단, 텍스트 조각(run), 스타일, 번호 정의, 구역 설정이 XML로 들어 있습니다. 줄이 어디서 끊기는지, 그 줄이 몇 페이지에 있는지는 어디에도 없습니다. PDF는 글자마다 좌표가 정해져 있지만 docx는 그렇지 않습니다.

```xml
<!-- 문단 하나. 폰트·크기·간격은 있지만 줄바꿈 위치와 페이지는 없다 -->
<w:p>
  <w:pPr><w:spacing w:after="120" w:line="360" w:lineRule="auto"/><w:keepNext/></w:pPr>
  <w:r><w:rPr><w:rFonts w:eastAsiaTheme="minorEastAsia"/><w:sz w:val="22"/></w:rPr>
    <w:t>본 시험에 참여한 20명 모두 시험을 완료하였다.</w:t></w:r>
</w:p>
```

줄과 페이지는 파일을 여는 프로그램이 계산합니다. 워드는 폰트 파일로 글자 폭을 재고, 자기 규칙대로 줄을 나눠 페이지에 채운 다음, 페이지가 정해지면 페이지 번호 같은 필드를 채웁니다. 워드로 저장한 파일에는 마지막으로 페이지가 나뉜 위치(`w:lastRenderedPageBreak`)가 남긴 하지만 참고용입니다. 워드로 한 번도 저장한 적 없는 AI 출력에는 이것조차 없습니다.

### 2. 워드의 레이아웃 규칙은 공개되지 않았다

docx 형식 자체는 ECMA-376이라는 공개 표준입니다. 다만 표준은 요소마다 뜻만 정하고, 그걸 줄과 페이지에 어떻게 배치할지는 정하지 않습니다. 결국 기준은 워드가 그린 결과인데, 워드의 레이아웃 규칙은 공개되어 있지 않습니다. 같은 파일이라도 호환 설정(`w:compat`)에 따라 워드가 다르게 배치하기도 합니다.

그래서 워드가 아닌 렌더러는 전부 워드 결과를 보면서 규칙을 맞춰 갑니다. 렌더러마다 결과가 조금씩 다른 것도 이 때문입니다.

### 3. 브라우저는 CSS 규칙으로 렌더링한다

docx를 HTML/CSS로 바꾸면 줄바꿈과 높이는 브라우저가 CSS 규칙대로 정합니다. 그런데 이 규칙이 워드와 다른 곳이 많습니다.

| 워드                                                              | 브라우저(HTML/CSS)                                                                          |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 내용을 A4 페이지에 채우고, 넘치면 다음 페이지로 보냄              | 화면에는 페이지가 없다. 세로로 계속 이어진다. CSS 페이지 나누기 속성은 인쇄할 때만 적용된다 |
| 줄 간격 1.5줄은 폰트 파일에 정의된 한 줄 높이의 1.5배             | `line-height: 1.5`는 폰트와 상관없이 글자 크기의 1.5배                                      |
| 한글과 숫자 사이를 조금 띄움(`w:autoSpaceDN`)                     | 붙여서 렌더링한다. "20명"에서 워드는 20과 명 사이가 벌어지고 브라우저는 붙는다              |
| 다음 단락과 함께(`keepNext`), 외톨이 줄 제어(`widowControl`)      | CSS에도 `break-after: avoid`, `widows`가 있지만 페이지를 나눌 때만 적용된다                 |
| 페이지를 넘는 표는 행 단위로 자르고 머리글 행(`tblHeader`)을 반복 | 표를 페이지 단위로 자르지 않는다                                                            |
| 위치를 지정한 표(`tblpPr`) 둘레로 텍스트를 배치                   | `float`로 비슷하게 만든다                                                                   |
| 구역마다 다른 머리글·바닥글, 페이지 번호·목차 필드                | 페이지가 없으니 페이지 번호를 계산할 수 없다                                                |
| 페이지 테두리(`pgBorders`)                                        | 페이지가 없으니 페이지 테두리도 없다                                                        |

docx-preview는 줄 간격을 이렇게 CSS로 옮깁니다.

```js
// docx-preview 0.4.0 · parseSpacing. w:line은 auto일 때 1/240줄, 그 밖에는 1/20pt 단위
switch (lineRule) {
  case "auto":
    // 360 → 1.50. 글자 크기의 1.5배
    style["line-height"] = `${(line / 240).toFixed(2)}`;
    break;
  case "atLeast":
    // "최소 18pt"가 "글자 크기 + 18pt"가 된다
    style["line-height"] = `calc(100% + ${line / 20}pt)`;
    break;
  default:
    style["line-height"] = style["min-height"] = `${line / 20}pt`;
    break;
}
```

워드는 한 줄 높이를 폰트 파일에 적힌 위아래 높이로 정하기 때문에 폰트마다 다릅니다. CSS로 옮기면 기준이 글자 크기로 바뀝니다. `atLeast`(최소 높이)는 글자 크기에 지정값을 더한 높이가 되니 워드보다 줄 간격이 넓어집니다. 문단 속성 중 `keepNext`, `keepLines`, `widowControl`은 읽기만 하고 CSS로는 옮기지 않습니다.

### 4. 폰트가 다르면 줄바꿈이 달라진다

글자 폭은 폰트마다 다릅니다. 한 글자만 넘쳐도 줄이 하나 늘고, 줄이 하나 늘면 뒤 페이지가 줄줄이 밀립니다. 2페이지에서 한 줄이 넘치면 3페이지 첫 줄이 바뀌고, 그 뒤도 다 바뀝니다. 그래서 페이지 수가 같아도 페이지마다 시작하는 내용은 다를 수 있습니다.

문서에 폰트가 임베드되어 있지 않으면 보는 PC에 깔린 폰트로 대체합니다. 워드도 예외가 아닙니다. HY신명조가 없는 맥 워드는 그 부분을 바탕체로 그렸습니다. 같은 워드라도 PC에 깔린 폰트와 OS가 다르면 결과가 달라질 수 있습니다.

결국 브라우저에서 워드처럼 보이게 하려면 폰트로 글자를 재고, 워드 규칙으로 줄과 페이지를 나누고, 필드를 채우는 일을 브라우저에서 전부 다시 해야 합니다. 워드프로세서 레이아웃 엔진을 하나 새로 만드는 일입니다.

## docx-preview로 띄웠을 때 나온 문제

docx-preview는 서버 없이 브라우저에서 docx를 그려 주는 Apache-2.0 라이브러리입니다. docx를 HTML/CSS로 바꾸고, 줄바꿈과 크기는 브라우저에 맡깁니다. 실제 보고서를 넣어 보니 에러는 안 나는데 결과가 워드와 달랐습니다. 라이브러리 코드까지 열어 원인을 찾고, 렌더링된 DOM을 후처리하는 식으로 하나씩 고쳤습니다.

| 증상                                         | 원인                                                                                               | 고친 방법                                    |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 고정 폭 표의 칸 폭이 글자 길이에 따라 바뀐다 | `tblLayout`을 `table-layout: fixed`로 바꾸지만, 표 너비가 `auto`면 브라우저가 자동 폭으로 배치한다 | colgroup의 열 너비로 고정 폭을 다시 적용     |
| 99페이지 문서가 긴 페이지 하나로 나온다      | 페이지를 계산하지 않는다. 문서에 적힌 페이지 나누기에서만 나눈다                                   | 렌더링 후 A4 높이로 재서 나누는 `paginate`   |
| 여러 페이지에 걸친 표에 머리글 행이 없다     | `tblHeader`를 읽지만 렌더링에 쓰지 않는다                                                          | XML에서 머리글 행 수를 세서 페이지마다 붙임  |
| 워드가 남긴 위치로 나누면 페이지 아래가 빈다 | `lastRenderedPageBreak`에서 나눈다. 워드가 워드 폰트로 계산한 위치다                               | 무시함(빈 공간 실측 547px)                   |
| 한글이 앱 기본 폰트로 나온다                 | 테마 한글 폰트(`eastAsiaTheme`)를 무시한다                                                         | styles.xml → theme1.xml을 따라가 폰트를 적용 |
| 용지 크기가 없는 문서가 한 페이지로 나온다   | 용지 높이를 모르면 나눌 기준이 없다(실측 2555px)                                                   | A4로 간주하고 화면에 알림                    |
| 번호가 0-1, 0-1, 0-1                         | 번호를 CSS 카운터로 센다                                                                           | numbering.xml을 읽어 번호를 직접 계산        |
| 섹션 끝에 빈 페이지가 하나 더 나온다         | 섹션 끝의 페이지 나누기에서 새 페이지를 만든다                                                     | 마지막 빈 페이지를 제거                      |

고친 방식은 다 같습니다. docx-preview가 렌더링을 끝낸 DOM을 받아서 직접 손봅니다. 가장 큰 작업은 페이지 나누기였습니다. 브라우저가 배치한 요소마다 아래쪽 좌표를 재고, A4 한 페이지의 아래 여백을 넘는 요소부터 새 페이지로 옮깁니다.

```js
// paginate: 렌더링이 끝난 뒤 좌표를 재서 나눈다
for (const page of pages) {
  // 페이지 위쪽 + A4 높이 − 아래 여백 − 바닥글이 여백을 넘친 높이
  const edge = page.top + A4_HEIGHT - page.paddingBottom - footerOverflow(page);
  for (const node of page.flow.children) {
    if (node.bottom + node.marginBottom <= edge) continue;
    // 표는 행 단위로 자르고 머리글 행을 다시 붙인다. 나머지는 그 요소부터 새 페이지로 옮긴다
    if (isTable(node)) moveRowsBelow(node, edge, { repeatHeaderRows });
    else moveFrom(node, addPageAfter(page));
    break;
  }
}
```

번호 문제는 원인이 다섯 개나 됐습니다. docx-preview는 번호를 CSS 카운터로 셉니다. 그런데 한 페이지에 문서 두 개를 렌더링하면 카운터 초기화 규칙이 같은 선택자(`:root`)에 두 번 들어가고, 나중에 렌더링한 문서의 규칙만 남습니다.

```css
/* 문서마다 docx-preview가 만드는 초기화 규칙. 선택자가 같아서 뒤의 것만 적용된다 */
:root {
  counter-reset: docx-1-num-44-0 0;
}
:root {
  counter-reset: docx-2-num-44-0 0;
}
```

초기화 규칙이 빠진 문서는 문단마다 카운터가 새로 생겨서 번호가 매번 1입니다. 이 밖에도 상위 번호가 없으면 `%1-%2` 형식에 0이 들어가고, 같은 목록 정의를 쓰는 번호를 따로따로 세고, ①②③을 1·2·3으로 그리는 문제가 있었습니다. 그래서 번호 계산은 numbering.xml을 읽어 직접 하고, 1·가·① 같은 숫자 모양만 docx-preview CSS에 맡겼습니다. 그 결과 24개 섹션의 번호 문단 282개가 LibreOffice 결과와 같아졌습니다.

### float 표 옆으로 제목이 들어간다

표 옆에 제목이 세로로 서는 문제는 위치를 지정한 표(`w:tblpPr`) 때문이었습니다. docx-preview는 이런 표를 무조건 `float: left`로 렌더링합니다.

```js
// docx-preview 0.4.0 · parseTablePosition
table.cssStyle["float"] = "left";
table.cssStyle["margin-bottom"] = values.addSize(table.cssStyle["margin-bottom"], bottomFromText);
table.cssStyle["margin-left"] = values.addSize(table.cssStyle["margin-left"], leftFromText);
table.cssStyle["margin-right"] = values.addSize(table.cssStyle["margin-right"], rightFromText);
table.cssStyle["margin-top"] = values.addSize(table.cssStyle["margin-top"], topFromText);
// 텍스트와의 간격(*FromText)만 읽는다. tblpX · tblpY · tblpXSpec(가운데 정렬)는 읽지 않는다
```

문제가 된 섹션은 본문 폭 9026twip에 표 폭 8500twip이고, 표 좌우로 텍스트와 142twip씩 간격을 둡니다. 남는 틈은 9026 − 8500 − 284 = 242twip, 약 16px입니다. 다음 제목이 이 틈에 들어가면서 한 글자마다 줄이 바뀝니다. 같은 문서를 워드로 열면 제목은 표 아래에 있습니다.

회사 문서는 올릴 수 없어서 본문 폭·표 폭·텍스트와의 간격만 같게 맞춘 문서를 따로 만들고, docx-preview 0.4.0 기본 옵션으로 렌더링했습니다. 맑은 고딕이 없는 맥의 Chromium이라 한글은 대체 폰트로 나왔습니다.

틈은 16px, 제목 문단은 일곱 줄에 121px이었습니다. 표의 float만 풀면 17px 한 줄로 돌아옵니다.

### 후처리로는 못 고치는 것

float를 푸는 건 코드 한 줄이면 됩니다. 그런데 워드 PDF와 비교해 보니 이런 식으로는 못 고치는 문제가 두 개 더 나왔습니다.

- 표 행 하나를 두 페이지에 나눠 담지 못합니다. 행 하나가 한 페이지보다 길면 `paginate`는 그 행을 통째로 다음 페이지로 넘기고, 그 페이지는 A4보다 길어집니다. 요약 보고서 섹션은 워드에서 8페이지인데 3페이지로 나왔습니다.
- 바닥글 페이지 번호가 전부 같습니다. 페이지를 나눌 때 첫 페이지 바닥글을 그대로 복사하니 10페이지 내내 같은 번호가 찍힙니다.

행을 페이지 사이에서 나누려면 행 안 텍스트가 몇째 줄에서 끊기는지 알아야 하고, 페이지 번호를 채우려면 페이지가 먼저 정해져야 합니다. `paginate`는 브라우저가 이미 배치한 요소를 옮기기만 하니 둘 다 할 수 없습니다. 최신 버전 0.4.1도 `parseTablePosition` 코드는 그대로입니다. 고치면 고친 곳만 맞고, 다른 문서를 넣으면 고칠 곳이 또 나옵니다.

## 그럼 어떻게 렌더링해야 할까

### 변환형과 레이아웃 엔진형

브라우저용 docx 라이브러리는 크게 두 종류로 나뉩니다.

```yaml
변환형: docx를 HTML/CSS로 바꾼다. 줄바꿈은 브라우저 CSS가 하고 페이지는 없다. docx-preview, mammoth
레이아웃 엔진형: 폰트 파일로 글자 폭을 재서 줄을 나누고, 페이지를 나누고, 페이지 번호를 채운다. docx-editor, SuperDoc, ONLYOFFICE, LibreOffice
```

변환형은 앞에서 본 대로 워드와 같아질 수 없습니다. 레이아웃 엔진형은 워드와 같은 종류의 계산을 하지만 결과까지 똑같지는 않습니다. 2번에서 쓴 것처럼 엔진마다 워드 결과를 보고 규칙을 따로 만들었기 때문입니다. 줄 높이를 어떻게 계산하는지, 한글을 어절 단위로 끊는지 글자 단위로 끊는지, 표 안의 표를 페이지 사이에서 나누는지, float 표를 어디에 두는지가 엔진마다 다릅니다.

실제로 재 보니 ONLYOFFICE는 줄 간격이 워드보다 5~7% 컸고, SuperDoc은 한글을 단어 중간에서 끊었고, docx-editor는 표 안의 표를 나누지 않았습니다. 폰트도 같아야 하는데, ONLYOFFICE는 문서에 임베드된 폰트를 쓰지 않았습니다.

### 워드로 렌더링하는 방법은 쓸 수 없다

완전히 똑같아야 한다면 워드로 렌더링하는 수밖에 없습니다. 그런데 MS 온라인 뷰어는 파일을 공개 URL로 열 수 있어야 하고, 편집기를 다른 서비스에 넣으려면 MS 파트너 프로그램에 가입해야 합니다. 사내 보고서는 외부에 올릴 수 없으니 둘 다 안 됩니다. 서버에서 워드로 PDF를 만드는 방법은 MS가 서버 자동화를 지원하지 않고, 만들어도 PDF라 수정할 수 없습니다.

그래서 목표를 "워드와 똑같이"에서 "같은 폰트로 렌더링했을 때 워드와 가장 많이 같은 엔진 고르기"로 바꿨습니다.

### 기준은 워드 PDF

그때까지는 LibreOffice 결과를 기준으로 삼았습니다. 서버가 내보내는 PDF를 LibreOffice가 만들기 때문입니다. 그런데 이건 "서버 PDF와 같은가"를 보는 기준이지 "워드와 같은가"를 보는 기준이 아닙니다. 서버에는 워드가 없으니 맥 워드에서 PDF로 저장한 파일을 받아 기준으로 썼습니다.

그런데 처음 받은 PDF는 기준으로 쓸 수가 없었습니다. 본문 대부분이 HY신명조인데 PDF에 들어 있는 폰트 목록에 HY신명조가 없었습니다.

```yaml
문서에 지정된 폰트: HY신명조(5622곳), Times New Roman, 맑은 고딕
워드 PDF에 들어 있는 폰트: Batang, TimesNewRomanPSMT, MalgunGothic, ArialMT, GulimChe
측정 서버의 폰트: HY신명조 있음, 바탕·맑은 고딕 없음
```

그 맥에 HY신명조가 없어서 워드가 바탕체로 바꿔 그린 것입니다. 측정 서버는 반대로 HY신명조만 있습니다. 이 PDF로 비교하면 엔진 차이와 폰트 차이가 뒤섞입니다.

다행히 다른 종류의 섹션 docx에는 폰트가 임베드되어 있었습니다(`w:embedTrueTypeFonts`, Times New Roman 4종, HY신명조 3종 등 11개). 이 섹션 두 개를 워드 PDF로 다시 받으니 PDF 폰트가 문서에 임베드된 HY신명조(`H2mjsM`)였습니다. 이러면 워드와 엔진이 같은 폰트 파일로 그리게 됩니다.

비교는 페이지마다 첫 줄로 했습니다. 처음 만든 비교 규칙은 너무 느슨했습니다. PDF는 텍스트를 화면 위치 순서로 읽고 DOM은 문서 순서로 읽기 때문에, 표의 칸 이름이 앞뒤로 바뀌어 나옵니다. 이 차이를 봐주려고 "한쪽 첫 6글자가 다른 쪽 앞 30글자 안에 있으면 같은 페이지"로 정했더니, "3) 주름깊이(눈밑)"로 시작하는 워드 6페이지와 "3-2) 주름깊이측정(팔자)"로 시작하는 페이지를 같다고 판정했습니다. 페이지가 하나씩 밀려 있었는데 점수는 오히려 올라간 것입니다. 그래서 규칙을 좁혔습니다.

```python
# 페이지마다 첫 줄 비교. 한글·영문만 남긴다.
# 한쪽 첫 6글자가 다른 쪽 맨 앞에서 시작하면 같은 페이지로 본다.
# 앞에 표 칸 이름(4글자까지)이 붙는 것만 허용한다.
def same_start(a, b):
    a, b = letters(a), letters(b)
    return 0 <= b.find(a[:6]) <= 4 or 0 <= a.find(b[:6]) <= 4
```

> [!NOTE] 측정 환경
> 기준은 맥 워드(macOS 26.6.2)가 저장한 PDF입니다. 엔진은 docx-preview 0.4.0(직접 고친 코드 포함), docx-editor 2.34.0, SuperDoc 2.29.0, ONLYOFFICE Docs 9.4.0 Community Edition, LibreOffice 24.2입니다. 브라우저 엔진은 헤드리스 Chromium에서 렌더링했고, PDF를 내보내는 엔진은 PDF에서 텍스트를 뽑았습니다. 페이지마다 첫 줄만 비교했으니 모든 줄이 같다는 뜻은 아닙니다. 윈도우 워드에서는 결과가 다를 수 있습니다.

## docx-editor로 바꾸고 남은 문제

결국 docx-editor로 정했습니다. 같은 폰트에서 워드와 같은 페이지가 가장 많았고, 서버 없이 브라우저에서 돌아가고, 라이선스도 Apache-2.0입니다. docx-editor는 임베드된 폰트 파일을 불러와 HarfBuzz로 글자 폭을 재고, 페이지와 머리글·바닥글을 직접 배치합니다. 검토 화면에서는 값이 들어갈 자리를 콘텐츠 컨트롤(`w:sdt`)로 감싸 두고 그 자리만 편집할 수 있게 했습니다.

테스트 페이지를 만들어 확인해 보니 워드와 다른 곳이 아직 다섯 군데 있었습니다.

1. 섹션 A의 두 번째 float 표를 다음 페이지로 밀어낸다. 2·3페이지가 어긋나고 4페이지에서 다시 맞는다.
2. 표 안의 표를 페이지 사이에서 나누지 않는다. 섹션 B가 10페이지가 된다.
3. 한글 굵게가 안 나온다. 문서에 임베드된 HY신명조 Bold 파일이 실제로는 weight 400이라 엔진이 굵게 렌더링하지 않는다.
4. 페이지 테두리를 렌더링하지 않는다.
5. 머리글 워터마크 그림 두 장이 어긋나서 겹친다.

콘텐츠 컨트롤을 편집하다가 생기는 문제도 몇 개 나왔습니다.

폰트는 엔진과 따로 풀어야 하는 문제입니다. 폰트가 임베드되지 않은 서식은 서버 쪽에 폰트를 넣어 달라고 요청했습니다. HY신명조, 맑은 고딕 같은 상용 폰트를 웹폰트로 내려보내려면 라이선스부터 확인해야 합니다.

## PR별로 고친 것

아래 내용은 PR 본문과 코드 변경을 보고 정리했습니다. PR마다 고치기 전 `main`에서 실패하는 테스트를 같이 넣었습니다.

### #1810 float 표가 앵커 문단을 따라 다음 페이지로 넘어간다

텍스트 기준으로 위치를 잡은 float 표(`w:tblpPr`에 `w:vertAnchor="text"`)는 엔진이 다음 문단(앵커)이 나올 때까지 보류해 두었다가 그 문단이 시작하는 위치에 놓습니다. 그런데 앵커 문단에 `w:pageBreakBefore`가 있으면 표까지 앵커를 따라 다음 페이지로 넘어갔고, 앞 페이지는 일찍 끝났습니다. 워드는 표를 지금 본문이 있는 페이지에 그대로 두고, 앵커 문단만 다음 페이지로 넘깁니다. 엔진도 여러 페이지에 걸치는 float 표는 이미 이렇게 처리하고 있었습니다.

그래서 남은 공간에 표가 들어가면 그 페이지에 두도록 바꿨습니다. 들어가는지 여부는 앵커가 그 페이지에서 차지하는 공간 계산(`requiredAnchorBand`)으로 봅니다. 공간이 모자란 표나 페이지·여백 기준으로 위치를 잡은 표는 전처럼 앵커를 따라갑니다.

```ts
// packages/core/src/layout/table-float-exclusion.ts (타입 생략)
export function staysBeforeAnchorBreak(anchors, pending, paragraphId, fits) {
  const waiting = (positionedTablesByAnchor(anchors).get(paragraphId) ?? []).filter((anchor) =>
    pending.has(anchor.table.id),
  );
  return (
    waiting.length > 0 && waiting.every((anchor) => anchor.float.vertAnchor === "text") && fits()
  );
}
```

### #1811 세로 병합이 있는 중첩 표가 통째로 넘어간다

셀 안에 든 표(중첩 표)도 행 사이에서 페이지가 나뉘어야 합니다. 세로 병합 셀이 있어도 마찬가지고, 병합의 첫 행과 그다음 행 사이에서 나뉠 수도 있습니다. 그런데 엔진은 세로 병합이 있는 중첩 표를 한 덩어리로 묶어 두고, 표나 바깥 행의 나머지를 통째로 다음 페이지로 넘겼습니다. 그래서 그 뒤 페이지가 전부 엉뚱한 위치에서 시작했습니다.

```diff
- const keepsWhole =
-   !continuation &&
-   structure.rows.some((row) => row.isHeader || row.cells.some((cell) => cell.vMergeContinue));
+ const keepsWhole = !continuation && structure.rows.some((row) => row.isHeader);
```

세로 병합이 있는 중첩 표도 최상위 표처럼 행 단위로 나누도록 바꿨습니다. 병합된 행이 첫 행부터 전부 그 페이지에 들어가면 한 셀로 둡니다. 다 안 들어가면 병합의 첫 행에 병합된 텍스트를 담고, 다음 행 앞에서 페이지를 나눕니다. 다음 페이지에서는 병합 셀이 병합 셀의 테두리를 그대로 가진 빈 셀로 이어집니다. 문서를 연 뒤에 편집해도 처음 열었을 때와 같은 페이지가 나옵니다. 머리글 행이 반복되는 중첩 표는 전처럼 한 페이지에 들어가면 통째로 넘깁니다.

### #1813 한글 굵게가 보통 굵기로 나온다

docx는 굵은 글자용 폰트를 그 폰트의 Bold 자리에 임베드합니다. Bold가 없는 폰트라면 이 자리에 Regular 사본이 들어가고, 워드는 이 사본으로 굵게를 합성해서 그립니다. 엔진은 이 사본을 weight 700으로 등록했고, 그 때문에 두 군데가 틀어졌습니다.

- 화면: 브라우저는 굵은 글자에 weight 700 폰트를 골랐는데, 그 폰트가 실제로는 Regular라 보통 굵기로 그렸습니다. 굵은 한글 제목이 본문처럼 보이고 옆의 라틴 숫자만 굵게 나왔습니다.
- 레이아웃: `isSyntheticBold`가 폰트 파일이 아니라 등록된 자리의 weight를 보는 바람에, 합성 굵게에 붙는 추가 폭(`SYNTHETIC_BOLD_ADVANCE_EM`, 글자마다 1/50em)이 빠졌습니다. 그래서 줄이 늦게 바뀌었습니다.

Bold인지는 폰트 파일을 직접 읽어서 판단하도록 바꿨습니다. `OS/2.usWeightClass`가 600 이상이거나 `OS/2.fsSelection`·`head.macStyle`의 bold 비트가 켜져 있으면 Bold로 봅니다. PDF 내보내기 쪽은 이미 이 규칙을 쓰고 있었습니다.

```ts
// packages/core/src/layout/synthetic-bold.ts
export function sfntFaceIsBold(bytes: Uint8Array, faceIndex: number): boolean {
  const view = new DataView(bytes.buffer, bytes.byteOffset, bytes.byteLength);
  const base = tableDirectoryBase(view, bytes.byteLength, faceIndex);
  if (base === null) return false;
  // `usWeightClass` is at 4 and `fsSelection` at 62 in every OS/2 version; bit 5 is BOLD.
  const os2 = tableOffset(view, bytes.byteLength, base, OS2_TAG, 64);
  if (os2 !== null && (view.getUint16(os2 + 4) >= 600 || (view.getUint16(os2 + 62) & 0x20) !== 0))
    return true;
  // `macStyle` is at 44; bit 0 is bold.
  const head = tableOffset(view, bytes.byteLength, base, HEAD_TAG, 54);
  return head !== null && (view.getUint16(head + 44) & 0x01) !== 0;
}
```

Bold 자리에 Regular가 들어 있으면 weight를 599로 등록합니다. CSS에서 bold로 매칭되는 기준이 600이라, 굵은 글자에는 여전히 Regular보다 이 폰트가 먼저 골라지고 굵게는 브라우저가 합성합니다.

```ts
// packages/core/src/editor/embedded-font-faces.ts
function weightDescriptor(weight: number, bytes: Uint8Array): string {
  return weight >= 600 && !sfntFaceIsBold(bytes, 0) ? "599" : String(weight);
}
```

화면 위치도 맞췄습니다. 브라우저는 합성 굵게를 폰트의 원래 폭으로 그리는데 레이아웃은 글자마다 1/50em씩 넓게 잡으니, 그대로 두면 둘이 어긋납니다. 그래서 이런 span에 표시를 해 두고(`StyleSpanRecord.syntheticBold`), 그릴 때 추가 폭을 `letter-spacing`으로 더하고 공백에서는 `word-spacing`으로 뺍니다. 오른쪽에서 왼쪽으로 쓰는 문자처럼 shaping한 span은 `letter-spacing`을 주면 이어져야 할 글자가 떨어지기 때문에 박스 위치만 맞춥니다.

테스트는 세 개를 넣었습니다. `synthetic-bold.test.ts`는 추가 폭과 span 표시를, `embedded-font-faces.test.ts`는 599 등록을, `synthetic-bold-paint.test.ts`는 왼쪽·양쪽·가운데·배분 정렬 문단에서 그린 run이 레이아웃 x 위치에서 시작하는지를 봅니다. 셋 다 `main`에서는 실패합니다. 실제 문서에서도 굵은 한글 제목과 표 머리글이 굵게 나왔고, 그린 위치가 레이아웃 박스와 0.04pt 안에서 맞았습니다. `… 수 /`와 `%`로 나뉘던 굵은 표 머리글은 `… 수`와 `/ %`로 바뀌었고, 페이지 시작 위치는 그대로였습니다.

부작용도 PR 본문에 적었습니다. Bold가 아닌 폰트의 굵은 글자는 이제 글자마다 1/50em씩 넓게 재기 때문에 줄이 더 일찍 바뀌고, 그만큼 페이지가 밀릴 수 있습니다.

### #1812 머리글 워터마크와 그림이 같이 보인다

머리글·바닥글의 앵커 그림도 본문처럼 `relativeHeight` 순서로 쌓여야 하는데, 엔진은 문서에 나온 순서대로 그렸습니다. 그래서 그림 워터마크(음수 `z-index`인 VML `v:shape`)와 그보다 순위가 낮은 텍스트 뒤 그림이 겹치는 머리글에서 두 그림이 다 보였습니다. 워드에서는 워터마크가 그림 위에 그려져서 아래 그림이 가려집니다.

머리글·바닥글도 텍스트 뒤 레이어를 먼저 두고, 그 안에서 `relativeHeight` 순서로 그림을 정렬하도록 바꿨습니다. 순위가 같으면 문서 순서를 지킵니다. PDF 내보내기는 원래 `relativeHeight`로 정렬하고 있었으니, 이제 화면과 PDF가 같게 나옵니다.

```ts
// packages/core/src/layout/drawing-exclusion.ts (타입 생략)
/** Word's stacking: the behind-text layer first, then `relativeHeight`. 0 keeps document order. */
export function compareDrawingStackOrder(left, right): number {
  const leftLayer = paintLayerOf(left);
  const rightLayer = paintLayerOf(right);
  if (leftLayer !== rightLayer) return leftLayer === "behind" ? -1 : 1;
  return left.relativeHeight - right.relativeHeight;
}
```

### #1814 명조 사이에 고딕 글자가 섞인다

serif 한국어 폰트에 없는 글자는 같은 serif인 바탕으로 그려야 합니다. 그런데 엔진은 이런 run의 `font-family` 뒤쪽 대체 목록을 `Calibri, Carlito, Helvetica, Arial, sans-serif`로 채웠습니다. 그러니 브라우저는 없는 글자를 sans-serif 한글 폰트(맑은 고딕, Apple SD Gothic Neo)로 채웠고, 명조 사이에 고딕 글자가 섞였습니다.

폰트 테이블에서 `w:family`가 `roman`이고 `w:charset`이 한국어(`81`, `82`)인 폰트는 대체 폰트를 바탕 계열로 두도록 바꿨습니다. 화면에 그릴 때와 canvas로 잴 때 같은 조회 결과를 씁니다. HarfBuzz는 글자가 없는 run을 canvas 측정으로 넘기기 때문에, 이렇게 하면 없는 글자도 실제로 그려지는 폰트로 재게 됩니다.

```diff
 font-family: "<embedded alias>", "<serif Korean font>",
-  Calibri, Carlito, Helvetica, Arial, sans-serif
+  Batang, AppleMyungjo, "Noto Serif CJK KR", serif
```

근거는 ECMA-376 Part 1 §17.8.2입니다. 이 절은 대체 폰트를 고를 때 볼 정보로 `w:charset`, `w:panose1`, `w:pitch`, `w:family`를 드는데, 바탕은 해당 폰트 항목의 네 값과 모두 맞습니다. 한계도 PR에 적었습니다. 바뀌는 건 한국어 serif 폰트뿐이고, 일본어·중국어 serif 폰트와 한국어 sans-serif 폰트는 그대로입니다. 줄 높이는 여전히 원래 폰트 기준이고, canvas가 없는 환경(서버 레이아웃)에서는 고정 측정기로 잽니다.

### #1815 Linux Chromium에서 하이라이트가 글자와 어긋난다

하이라이트, 선택 영역, 커서는 레이아웃이 잰 위치에 그립니다. 레이아웃은 HarfBuzz로 hinting 없는 글자 폭을 재는데, Linux Chromium은 웹폰트(임베드된 문서 폰트 포함)를 hinting된 폭으로, 그것도 픽셀 단위로 반올림해서 그립니다. 그래서 줄 끝으로 갈수록 글자가 레이아웃 위치에서 밀렸고, 짧은 run 끝에서도 몇 픽셀씩 차이가 났습니다.

페이지마다 `text-rendering: geometricPrecision`을 주고, canvas 측정기도 이 속성을 지원하면 같은 값을 쓰도록 바꿨습니다. 이러면 Chromium이 그릴 때도 잴 때도 hinting 없는 폭을 씁니다.

```ts
// packages/core/src/output/page-host-isolation.ts
element.style.textRendering = "geometricPrecision";

// packages/core/src/layout/canvas-measurer.ts
if ("textRendering" in ctx) ctx.textRendering = "geometricPrecision";
```

| 범위 (Chromium 151, Linux, Roboto 임베드) | 고치기 전: 하이라이트 끝 − 글자 끝 | 고친 뒤 |
| ----------------------------------------- | ---------------------------------- | ------- |
| `lazy dog.` 왼쪽 끝                       | 0.58px                             | 0px     |
| `lazy dog.` 오른쪽 끝                     | 3.84px                             | 0px     |

HarfBuzz로 shaping하는 run은 원래 폭을 그대로 쓰니 줄바꿈이 바뀌지 않습니다. canvas로 재는 run(문서에 임베드되지 않은 폰트 등)은 폭이 바뀔 수 있고, 실제로 임베드하지 않은 폰트를 쓴 문서 두 개에서 페이지 시작이 달라졌습니다. Linux Chromium에서만 확인했고 다른 브라우저와 OS는 확인하지 않았다는 점도 PR 본문에 적었습니다.

### #1807 컨트롤 끝에서 입력하면 보호된 문서라고 거절한다

양식 보호(`w:documentProtection w:edit="forms"`)를 건 문서에서는 inline 텍스트 콘텐츠 컨트롤 바로 뒤에 한글이 오면 컨트롤 끝에 글자를 덧붙일 수 없었습니다. `번호 [26202]의 값`(대괄호 부분이 컨트롤)에서 마지막 숫자 뒤를 클릭하고 입력하면 "보호된 문서라 양식 필드만 채울 수 있다"며 막혔습니다. 값 전체를 선택해서 덮어쓰면 첫 글자만 들어갔습니다.

원인은 앞에서 본 한글과 영문·숫자 사이 자동 간격(`w:autoSpaceDE`, `w:autoSpaceDN`)이었습니다. 이 간격 때문에 커서가 간격 뒤쪽에 놓입니다. 컨트롤 끝을 찾는 `contentControlAtSelection`은 커서에서 1/4pt 왼쪽을 확인하는데, 그 자리가 간격 안이라 컨트롤 밖으로 판정했습니다.

비어 있지 않은 inline 컨트롤은 화면 좌표 대신 모델상의 범위로 끝을 찾도록 바꿨습니다.

```ts
// packages/core/src/editor/content-control-at-selection.ts (타입 생략)
if (collapsed) return endingAt(layout, selection.head) ?? probe(selection.head, -INSIDE);

/** The innermost non-empty inline control whose content ends at `position`. */
function endingAt(layout, position) {
  let best = null;
  for (const control of layout.contentControls ?? []) {
    const range = control.range;
    if (!range || range.paragraphId !== position.paragraphId) continue;
    if (range.end !== position.offset || range.start === range.end) continue;
    if (!best || control.nestingDepth > best.nestingDepth) best = control;
  }
  return best;
}
```

간격이 없어도 막히는 경로가 하나 더 있었습니다. `insertText`와 `pasteWithoutFormatting`의 `can`·`exec`가 컨트롤 끝 입력을 거절했습니다. 입력 허용 판단과 서식 없이 붙여넣기 쪽에서 커서가 속한 컨트롤을 지정하지 않았기 때문입니다. 지금은 타이핑할 때와 같은 컨트롤을 기존 `insertText`의 `inside` 필드로 넘깁니다.

### #1808 값을 지우면 문서에 정의된 안내 문구 대신 기본 문구가 나온다

텍스트 컨트롤의 값을 다 지우면 엔진이 "Click here to enter text."를 넣었습니다. 컨트롤의 `w:placeholder/w:docPart`가 자기 안내 문구를 가진 glossary 블록을 가리키고 있어도 그랬습니다. 워드는 이때 그 블록의 문구를 보여 줍니다. 엔진도 처음부터 비어 있는 컨트롤을 열 때는 그 문구를 제대로 보여 주고 있었습니다.

새로 추가한 `EditOptions.placeholderText` 조회로 store가 glossary를 안내 문구 복원 코드에 넘기도록 바꿨습니다. 안내 문구를 되살릴 때는 지정된 블록의 첫 문단 텍스트를 쓰고, 그런 블록이 없으면 전처럼 기본 문구를 씁니다. 머리글·바닥글·각주 part에서 만든 store는 `TreeDocumentStoreOptions.placeholderText`로 패키지의 glossary를 읽습니다. 되살린 문구에는 지우기 전 run의 서식이 그대로 남습니다. `setContentControlValue`에 빈 문자열을 넘기면 전처럼 안내 문구 없이 비웁니다.

### #1809 안내 문구가 한 글자씩 지워진다

안내 문구가 보이는 컨트롤 안에서 Delete나 Backspace를 누르면 문구가 한 글자씩 지워졌습니다. 컨트롤은 `w:showingPlcHdr`를 그대로 달고 있어서 "ck here to enter text." 같은 잘린 문구가 보이는데도 빈 컨트롤로 취급됐습니다. 워드는 안내 문구를 한 덩어리로 다룹니다. 엔진도 첫 글자를 입력할 때는 문구를 통째로 바꾸고 있었습니다.

안내 문구의 일부만 지우는 `deleteText`는 아무것도 바꾸지 않도록 했습니다(`promptKeptByDeletion`). 전체 선택 후 Delete처럼 문구를 통째로 지우는 경우와 컨트롤 밖 편집은 전과 같습니다.

- `CLA.md`: 기여자 라이선스 동의서

세 문서가 요구하는 걸 추리면 다음과 같습니다.

- 고친 것마다 테스트를 같이 넣는다.
- 코드를 바꾸면 changeset(`.changeset/*.md`)에 바뀐 점을 한두 문장으로 쓴다. 이 문장이 CHANGELOG에 그대로 들어간다.
- 편집 동작을 바꾸면 동시 편집에 영향이 있는지 `bun run collaboration:change`로 판단을 남긴다(`.collaboration/changes/*.json`).
- 커밋 전 검사를 통과한다. 타입 검사, 린트, 포맷, 파일 줄 수 상한, 공개 API 스냅샷(`bun run api:check`).
- 커밋 제목은 `fix(core): ...` 형식으로 쓴다.
- PR 본문은 영어로 짧게 쓴다. 파일 목록, 이모지, 도구 서명 줄은 넣지 않는다. 이슈를 해결하면 본문 끝에 `Fixes #번호`를 붙인다. 문체는 Google 개발자 문서 스타일 가이드를 따른다.
- 이슈에는 타입(Bug/Feature/Task) 하나, `area:*` 라벨 하나, `priority:*` 라벨 하나를 붙인다.

### 2. PR로 낼까, 이슈로 낼까

9개는 바로 PR로 냈습니다. 원인이 분명하고, 워드로 기대 결과를 확인할 수 있는 버그였기 때문입니다. 이런 건 고친 코드와 테스트를 같이 보내야 관리자가 판단하기 편합니다.

아트 페이지 테두리만 이슈([#1806](https://github.com/eigenpal/docx-editor/issues/1806))로 냈습니다. 고치기 전에 관리자가 먼저 정해야 할 게 있었습니다.

- 이 라이브러리는 페이지 테두리를 추가한 [#839](https://github.com/eigenpal/docx-editor/pull/839)에서 선 테두리만 그리고 아트 테두리는 빼 두었습니다.
- 워드의 아트 테두리 무늬는 ECMA-376 Part 1 부록 F에 이미지로 들어 있습니다. 이 이미지에는 Ecma 저작권이 있고, Apache-2.0 패키지에 넣어도 되는지는 관리자만 정할 수 있습니다.

그래서 이슈에 재현 문서, 워드가 그리는 위치와 크기(pt 단위), 선택지 네 개를 적어 "어떻게 할까요"를 물었습니다. 선택지는 이미지를 별도 패키지로 싣기, 이미지를 라이브러리 사용자가 넘겨주게 하기, 일부 무늬를 벡터로 그리기, 지금처럼 빼고 경고만 띄우기입니다.

### 3. 고칠 코드를 준비한다

원본 저장소를 clone하고, 고칠 것마다 브랜치와 작업 디렉터리를 따로 만들었습니다. PR 하나에 버그 하나만 담아야 관리자가 하나씩 보고 골라서 받을 수 있습니다.

테스트는 코드를 고치기 전에 먼저 썼습니다. 고치기 전에는 실패하고 고친 뒤에는 통과해야 그 테스트가 정말 이 버그를 잡는다고 말할 수 있습니다.

테스트 문서는 직접 만든 작은 docx만 썼습니다. 실물 보고서는 고객 자료라 공개 저장소에 절대 들어가면 안 됩니다. 실물 파일은 `.git/info/exclude`에 등록해 실수로 커밋되지 않게 막고, 워드와 비교할 때만 로컬에서 열었습니다. `.git/info/exclude`는 `.gitignore`와 달리 커밋되지 않아서 원본 저장소에 흔적도 남지 않습니다.

커밋 전 검사(pre-commit hook)는 작업 서버에 없는 `npx`를 호출해서 아예 돌지 않았습니다. 그래서 같은 검사를 직접 돌려 통과시킨 뒤 `--no-verify`로 커밋했습니다. 이 저장소의 `AGENTS.md`도 이 방식을 허용합니다.

```md
`git commit --no-verify` is fine locally, but `bun run format` and `bun run lint` are not optional
```

### 4. 최신 main 위로 rebase한다

작업하는 사이에 원본 main에 새 커밋이 쌓였습니다. 오래된 main에서 만든 PR은 충돌이 나거나 관리자가 rebase를 다시 요청하게 됩니다. 그래서 올리기 전에 브랜치 9개를 전부 최신 main 위로 rebase하고, 바뀐 부분의 테스트를 다시 돌렸습니다.

```bash
git fetch origin
git rebase origin/main   # 브랜치마다 반복
```

### 5. fork, push, PR

```bash
gh repo fork eigenpal/docx-editor --clone=false   # 내 계정에 사본: geonoooo/docx-editor
git push <fork 주소> fix/control-trailing-edge-autospace
gh pr create --repo eigenpal/docx-editor \
  --head geonoooo:fix/control-trailing-edge-autospace --base main \
  --title "fix(core): ..." --body-file <PR 본문 파일>
```

fork는 `gh`에 로그인한 계정 아래에 생깁니다. `--head`에 `계정:브랜치`를 적어야 원본 저장소가 fork의 브랜치를 찾을 수 있습니다. 이렇게 올린 게 PR #1807~#1815 9개와 이슈 #1806입니다.

### 6. 봇 검사 세 가지

PR을 올리자마자 봇이 검사를 시작합니다.

#### CLA (기여자 라이선스 동의)

이 저장소는 기여한 코드를 저장소 쪽에서 쓰고, 고치고, 다시 배포해도 된다는 동의를 받은 뒤에야 PR을 받습니다. `CLA.md`에서 동의하는 내용은 크게 두 가지입니다.

- 기여한 코드에 대해 영구적이고 취소할 수 없는 무료 저작권 라이선스와 특허 라이선스를 준다.
- 내가 이 라이선스를 줄 권리가 있다고 보증한다. 회사가 권리를 가진 코드라면 회사가 허락했다는 뜻이 된다.

서명은 PR에 정해진 문장을 코멘트로 달면 끝납니다.

```md
I have read the CLA Document and I hereby sign the CLA
```

서명은 PR 단위가 아니라 GitHub 계정 단위로 저장돼서, 한 번 서명하면 그 계정의 PR 전부에 적용됩니다. 이미 실패로 찍힌 PR은 `!cla-check` 코멘트를 달면 다시 검사합니다. 이건 서명이 아니라 재검사 요청입니다.

#1815에 서명 문장을 달고 나머지 8개에는 `!cla-check`를 달아서 9개 모두 CLA 검사를 통과했습니다.

#### Vercel (미리보기 배포)

PR마다 데모 사이트를 미리 배포해 보는 검사입니다. 처음 기여하는 외부인의 PR은 저장소 팀원이 배포를 승인해야 돌아갑니다. 그래서 올린 직후에는 `Authorization required to deploy`로 실패 상태였고, 기여자 쪽에서 할 수 있는 건 없습니다.

#### 테스트 (CI)

원본 저장소의 자동 테스트입니다. 처음 기여하는 사람의 PR은 관리자가 승인해야 CI가 도는 경우가 많은데, 이 PR들도 올린 직후에는 CI가 돌지 않았습니다. 그래서 로컬에서 전체 테스트를 돌려 통과했다는 걸 PR 본문에 적었습니다. 작업 서버에 npm이 없어서 돌리지 못한 검사(배포된 버전과의 동시 편집 호환 검사)가 있다는 것도 같이 적었습니다.

### 7. 리뷰, merge, 릴리스

- 리뷰: 관리자가 코멘트로 수정을 요청할 수 있습니다. 같은 브랜치에 커밋을 더 push하면 PR이 알아서 갱신되니 PR을 새로 열 필요는 없습니다.
- merge: 관리자가 main에 합칩니다. 이 저장소는 외부 PR을 squash merge하고, 합친 커밋의 작성자는 PR 작성자로 남깁니다. merge되면 저장소 Contributors 목록에 이름이 올라갑니다. GitHub는 커밋에 적힌 이메일로 작성자를 찾으니, 그 이메일이 GitHub 계정에 등록되어 있어야 합니다.
- 릴리스: 쌓인 changeset으로 버전이 올라가고 npm에 새 버전이 배포됩니다.

PR 9개는 11월 4일에 6개, 11월 9일에 3개가 merge됐습니다. 아트 페이지 테두리 이슈 #1806은 아직 열려 있습니다. 그 뒤로 올린 PR 6개까지 merge되어 지금까지 [15개](https://github.com/eigenpal/docx-editor/pulls?q=is%3Apr+author%3Ageonoooo+is%3Amerged)가 들어갔습니다.

## 조심한 것

- 고객 자료: 테스트, PR 본문, 스크린샷 어디에도 실물 보고서를 넣지 않았습니다. 예시 문장에 들어 있던 실제 시험번호 형식도 지웠습니다.
- CLA는 법적 동의입니다. 회사가 권리를 가진 코드라면 회사가 허락했다는 보증까지 들어갑니다. 회사 업무로 만든 코드이니 서명 전에 이 조항부터 확인해야 합니다.

## 정리

- docx에는 줄과 페이지 정보가 없다. 파일을 여는 프로그램이 폰트로 계산한다. 워드와 같은 페이지가 필요하면 이 계산을 하는 레이아웃 엔진을 쓴다.
- docx를 HTML/CSS로 바꾸면 줄 간격, 페이지 나누기, 다음 단락과 함께 같은 워드 규칙이 CSS 규칙으로 바뀐다. 직접 고치면 고친 부분만 맞고, 페이지 번호와 표 행 나누기처럼 페이지가 먼저 정해져야 하는 건 후처리로 못 고친다.
- 레이아웃 엔진도 워드 규칙을 따로 만든 것이라 워드와 똑같지 않다. 같은 폰트에서 몇 페이지가 같은지 측정해서 고른다.
- 비교 기준은 워드 PDF로 정한다. LibreOffice 결과는 서버 PDF의 기준이지 워드의 기준이 아니다.
- 기준 PDF는 폰트부터 확인한다. PDF에 들어 있는 폰트가 문서에 지정된 폰트와 다르면 그 PDF로는 엔진을 비교할 수 없다.
- 비교 규칙은 틀린 경우로도 시험한다. 느슨한 규칙은 밀린 페이지를 같은 페이지로 셌다.
- 라이브러리 버그를 앱에서 고치면 라이브러리 버전을 올릴 때마다 다시 확인해야 하고, 라이브러리를 바꾸면 버린다. 라이브러리에서 고치면 앱에 남는 코드가 없다. 대신 리뷰와 릴리스를 기다린다.
- 기여하기 전에 `CONTRIBUTING.md`, `AGENTS.md`, `CLA.md`를 읽는다. changeset, 커밋 제목, PR 본문 형식까지 정해져 있다.
- PR 하나에 버그 하나만 담고, 고치기 전 코드에서 실패하는 테스트를 같이 넣는다.
- 관리자가 먼저 정해야 하는 문제는 PR 대신 이슈로 재현 방법과 선택지를 적어 묻는다.
- 공개 저장소에는 직접 만든 테스트 문서만 넣는다. 실물 파일은 `.git/info/exclude`로 막는다.
- CLA 서명은 계정 단위로 저장된다. 다른 PR은 `!cla-check`로 다시 검사한다.
