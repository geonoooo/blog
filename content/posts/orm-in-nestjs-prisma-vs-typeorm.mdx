> [!NOTE] [1부 — DB 종류와 선택 기준](/posts/sql-vs-nosql-how-to-choose)에서 PostgreSQL을 디폴트로 골랐습니다.
> 이번 글은 그 DB를 코드에서 어떻게 다루는지입니다. ORM이 정확히 무엇이고, 무엇을 해결하고 무엇을 대가로 치르는지, 그리고 NestJS에서는 무엇을 고르는지를 정리합니다.

DB를 정했으면 다음 질문은 "그래서 코드에서 어떻게 쿼리하느냐"입니다. 선택지는 세 단계로 펼쳐집니다.

## 1. 스펙트럼 — 생 SQL부터 ORM까지

```
생 SQL  ←─────  쿼리 빌더  ─────→  ORM
(완전 수동)      (Kysely)         (Prisma, TypeORM)
저수준 · 고제어                  고수준 · 고생산성
```

같은 조회를 세 방식으로 적으면 차이가 보입니다.

```ts
// 1) 생 SQL — 문자열로 직접
const { rows } = await pool.query("SELECT * FROM users WHERE id = $1", [id]);
// 결과 타입은 any. 오타가 나도 런타임에야 터진다.

// 2) 쿼리 빌더 (Kysely) — SQL 구조 그대로, 타입은 붙음
const user = await db.selectFrom("users").selectAll().where("id", "=", id).executeTakeFirst();

// 3) ORM (Prisma) — 테이블을 객체처럼
const user = await prisma.user.findUnique({ where: { id } });
```

아래로 갈수록 코드가 짧고 안전해지지만, 실제로 어떤 SQL이 나가는지는 가려집니다. 이 트레이드오프가 ORM 논쟁의 전부라고 봐도 됩니다.

## 2. ORM이 정확히 무엇인가

ORM(Object-Relational Mapping)은 이름 그대로 **객체(Object)와 관계형 테이블(Relational)을 매핑(Mapping)** 하는 도구입니다. DB의 테이블을 코드의 클래스/모델로, 행(row)을 객체 하나로 대응시킵니다.

```ts
// 테이블 users 의 한 행  ≈  타입이 잡힌 객체 하나
const user = await prisma.user.findUnique({ where: { id: 1 } });
//    ^? { id: number; email: string } — 자동완성과 타입체크가 붙는다
```

프론트엔드에서 API 응답에 타입을 붙여 다루던 감각과 거의 같습니다. 차이는 그 타입이 **DB 스키마에서 자동으로 파생된다**는 점입니다.

## 3. ORM이 해결하는 문제

**타입 안정성.** 쿼리 결과가 `any`가 아니라 스키마에서 파생된 타입으로 잡힙니다. 컬럼명을 오타 내면 빌드 단계에서 잡힙니다. TypeScript를 쓰는 프로젝트에서 이 가치가 가장 큽니다.

**마이그레이션 관리.** 스키마 변경 이력을 코드로 추적하고, 팀원·배포 환경에 동일하게 적용합니다. "이 컬럼 누가 언제 추가했지"를 git처럼 따라갈 수 있습니다.

**반복 CRUD 제거.** 흔한 생성·조회·수정·삭제 SQL을 매번 손으로 쓰지 않아도 됩니다.

**DB 이식성.** PostgreSQL에서 MySQL로 옮길 때 코드 변경이 줄어듭니다. 다만 이건 과대평가된 장점입니다. 실무에서 메인 DB를 바꾸는 일은 드뭅니다.

## 4. ORM의 비용 — 가장 중요한 부분

ORM을 "SQL 안 써도 되는 편한 도구"로만 알면 반드시 사고가 납니다. 대가가 분명합니다.

### 4-1. N+1 쿼리 문제

ORM에서 가장 흔하고 가장 비싼 함정입니다. 글 목록과 각 글의 작성자를 가져온다고 합시다.

```ts
const posts = await postRepo.find(); // 쿼리 1번: 글 10개

for (const post of posts) {
  // 루프마다 작성자를 조회 → 쿼리 10번
  console.log(post.author.name);
}
```

글 10개를 가져오는 데 쿼리가 **1 + 10 = 11번** 나갑니다. 글이 100개면 101번입니다. SQL을 직접 썼다면 JOIN 한 번이면 될 일입니다.

```sql
-- 의도했던 것: 쿼리 1번
SELECT posts.*, users.name
FROM posts JOIN users ON users.id = posts.user_id;
```

ORM은 이 문제를 가려놓습니다. `post.author`라는 코드가 **숨은 쿼리**라는 사실이 안 보이기 때문입니다. 해결책(eager loading, `include`, `relations` 옵션)은 ORM마다 있지만, **문제가 거기 있다는 걸 알아야** 쓸 수 있습니다.

### 4-2. 복잡한 쿼리의 표현 한계

집계, 윈도우 함수, 무거운 다중 JOIN, CTE 같은 쿼리는 ORM 문법으로 표현하기 어렵거나, 표현해도 비효율적인 SQL이 나갑니다. 이런 쿼리는 어떤 ORM을 쓰든 **결국 raw SQL로 내려가야** 합니다.

### 4-3. 추상화가 가리는 비용

ORM의 편리함은 "SQL을 안 봐도 된다"에서 옵니다. 그런데 성능 문제는 대부분 그 안 보이는 SQL에서 생깁니다. 그래서 ORM을 쓰더라도 **실제로 어떤 쿼리가 나가는지 로그로 확인하는 습관**이 필요합니다. 추상화를 쓰되 그 아래를 모르면 안 됩니다.

### 결론적으로

실무 평균은 양자택일이 아닙니다. **기본 CRUD는 ORM, 무거운 쿼리는 raw SQL 병행.** 모든 주요 ORM은 raw SQL을 실행하는 탈출구를 제공합니다. ORM은 SQL을 대체하는 게 아니라 흔한 경우를 줄여주는 도구로 보는 편이 정확합니다.

## 5. NestJS에서 뭘 쓰나

NestJS에서 자주 보이는 네 가지입니다.

| 도구                 | 성격                                              | 언제                          |
| -------------------- | ------------------------------------------------- | ----------------------------- |
| **Prisma**           | 스키마 파일 기반. 타입 추론·DX가 가장 강함        | 새로 시작하는 대부분, 학습용  |
| **TypeORM**          | NestJS **공식 문서의 기본 예시**. 데코레이터 기반 | Nest 스타일 통일, 레거시 유지 |
| **MikroORM**         | TypeORM과 비슷하나 더 엄격한 설계(Unit of Work)   | TypeORM 대안                  |
| **Drizzle / Kysely** | SQL에 가까운 경량. ORM 추상화를 줄이고 싶을 때    | SQL 통제력이 중요할 때        |

여기서 주의할 점 하나. **NestJS 공식 문서는 TypeORM으로 예시를 들지만, 새 프로젝트의 현실 선택은 Prisma로 많이 기울었습니다.** 공식 튜토리얼을 따라가다가 "왜 다들 Prisma를 쓴다고 하지?"라며 혼란을 겪기 쉽습니다. 둘 다 정답이고, 차이를 알면 됩니다.

## 6. Prisma vs TypeORM — 깊게 보기

### 스키마를 어디에 정의하나

**Prisma는 별도 스키마 파일** 하나에 모델을 모읍니다. 이 파일이 단일 진실 공급원(single source of truth)입니다.

```prisma
// schema.prisma
model User {
  id    Int    @id @default(autoincrement())
  email String @unique
  posts Post[]
}

model Post {
  id       Int    @id @default(autoincrement())
  title    String
  author   User   @relation(fields: [authorId], references: [id])
  authorId Int
}
```

`prisma generate`를 돌리면 이 스키마에서 **타입이 완비된 클라이언트가 코드로 생성**됩니다. 타입 추론이 강력한 이유입니다.

**TypeORM은 클래스에 데코레이터**를 붙여 정의합니다. 모델이 곧 엔티티 클래스입니다.

```ts
@Entity()
export class User {
  @PrimaryGeneratedColumn()
  id: number;

  @Column({ unique: true })
  email: string;

  @OneToMany(() => Post, (post) => post.author)
  posts: Post[];
}
```

이 데코레이터 방식은 NestJS의 `@Module`, `@Injectable`, `@Controller`와 결이 같습니다. Nest 코드 스타일과의 일관성은 TypeORM의 장점입니다.

### NestJS 통합 코드

**TypeORM** — 모듈에 등록하고 리포지토리를 주입받습니다.

```ts
// users.module.ts
@Module({
  imports: [TypeOrmModule.forFeature([User])],
  providers: [UsersService],
})
export class UsersModule {}

// users.service.ts
@Injectable()
export class UsersService {
  constructor(
    @InjectRepository(User)
    private readonly users: Repository<User>,
  ) {}

  findAll() {
    return this.users.find();
  }
}
```

**Prisma** — `PrismaClient`를 감싼 서비스 하나를 주입받습니다.

```ts
// prisma.service.ts
@Injectable()
export class PrismaService extends PrismaClient implements OnModuleInit {
  async onModuleInit() {
    await this.$connect();
  }
}

// users.service.ts
@Injectable()
export class UsersService {
  constructor(private readonly prisma: PrismaService) {}

  findAll() {
    return this.prisma.user.findMany();
  }
}
```

### 차이 정리

|              | Prisma                       | TypeORM                            |
| ------------ | ---------------------------- | ---------------------------------- |
| 스키마 정의  | 별도 `.prisma` 파일          | 엔티티 클래스 + 데코레이터         |
| 타입 추론    | 매우 강함 (코드 생성)        | 보통 (데코레이터 기반)             |
| 마이그레이션 | `prisma migrate`로 자동 생성 | 직접 작성 또는 자동 생성           |
| Nest 스타일  | 별도 서비스로 감쌈           | `@InjectRepository`로 자연스럽게   |
| 관계 로딩    | `include` 옵션               | `relations` 옵션 / lazy            |
| 학습 곡선    | 완만함                       | 데코레이터·관계 설정이 다소 가파름 |

## 7. 그래서 무엇을 고를까

**FE 출신 백엔드 입문자라면 Prisma를 권합니다.** 스키마가 한 파일에 모이고, 타입·자동완성이 강력해서 학습 부담이 가장 적습니다. TypeScript를 쓰던 감각이 거의 그대로 이어집니다.

**NestJS 공식 튜토리얼을 그대로 따라가거나, 데코레이터 스타일로 통일하고 싶다면 TypeORM**도 좋은 선택입니다. Nest의 다른 코드와 일관됩니다.

무엇을 고르든 두 가지는 공통입니다.

1. **무거운 쿼리는 raw SQL을 병행한다.** ORM 문법에 억지로 욱여넣지 않는다.
2. **실제로 나가는 SQL을 로그로 본다.** N+1을 비롯한 성능 문제는 거기서 드러난다.

## 8. 결론

- ORM은 **객체와 테이블을 매핑**해 타입 안정성·마이그레이션·반복 CRUD 제거를 준다.
- 대가는 **N+1**, 복잡한 쿼리의 표현 한계, 그리고 **SQL이 가려진다는 점**이다.
- ORM은 SQL을 대체하지 않는다. 흔한 경우를 줄여줄 뿐, 무거운 쿼리는 raw SQL로 간다.
- NestJS 신규·학습용은 **Prisma**, 공식 스타일·레거시는 **TypeORM**. 둘 다 정답이다.

1부에서 DB를 고르고, 2부에서 그 DB를 다루는 도구를 골랐습니다. 다음에 BE를 더 파면 인증이나 트랜잭션 설계를 이어서 정리할 생각입니다.
