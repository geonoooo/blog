> [!NOTE] 명령은 똑같은데 환경만 바꿨더니 깨졌다
> 로컬 PC에선 잘 뚫리던 SSH 터널이 GCP VM에선 안 됩니다. "포트 번호도 같고 호스트도 같은데 왜?" — 답은 명령어가 아니라 **경로**에 있었고, 그 경로를 받쳐주고 있던 건 그동안 의식 못 했던 IP 화이트리스트였습니다.

> [!WARNING] 숫자는 실제 값이 아닙니다
> 이 글에 나오는 포트 번호(`51234`, `45000–45010`, `8800`, `3100` 등)와 호스트 이름(`gpu-server`)은 실제 회사 환경의 값이 아니라, 설명을 위해 임의로 잡은 숫자입니다. 구조와 인과 관계만 실제 그대로고, 숫자는 모두 픽션이라고 봐주세요.

## 0. 발단

회사 GPU 서버(`gpu-server`)에 vLLM이 `51234`번 포트에서 떠 있습니다. 로컬에서 vLLM을 호출할 때는 늘 이렇게 썼어요.

```bash
ssh -L 51234:localhost:51234 gpu-server
```

그래서 다른 환경에서도 당연히 될 줄 알았습니다. GCP에 fe/be/ai 세 개를 띄워놓고, ai 컨테이너에서 똑같이 `gpu-server`로 터널을 뚫으려고 한 거죠.

결과는 침묵. 명령은 멈춰있고 `curl localhost:51234`는 연결 거부. _"명령도 똑같고 포트도 똑같은데 뭐가 다르지?"_ — 거기서부터 출발한 이야기입니다.

## 1. 먼저 — SSH 터널이란 뭘 하는 건가

이 모든 이야기의 출발점인 `ssh -L`은 **SSH 터널링**의 한 형태입니다. 그래서 한 단계 먼저 — 터널링이 뭔지부터 짚고 가야 해요.

### 터널링이란?

**한 프로토콜의 패킷을 다른 프로토콜의 패킷 안에 감싸서 전달**하는 기술입니다. 비유하면 봉투에 편지를 넣어 보내는 거예요. 외부에서 보이는 건 봉투(겉 프로토콜)뿐이지만, 봉투를 까보면 안에 진짜 내용물(속 프로토콜)이 들어있는 식이죠.

```text
[ 51234로 보낼 트래픽 ]   ← 속 (실제 보내고 싶은 것)
        │
        ▼
[ SSH 패킷으로 감싸기 ]   ← 겉 (외부에 보이는 것)
        │
        ▼   (인터넷, 방화벽 통과)
        │
[ SSH 패킷 풀기 ]
        │
        ▼
[ 51234 트래픽 복원 ]     ← 다시 원래대로
```

이게 필요한 이유는 단순합니다. **외부에 직접 노출되지 않은 트래픽을, 이미 외부에 노출돼있는 안전한 채널 안에 감싸서 보내는 것.** 51234는 외부에 안 열려있어도, 22번(SSH)이 열려있다면 51234 트래픽을 22번 SSH 패킷 안에 감싸서 보내면 통과시킬 수 있어요.

### `ssh -L`이 정확히 하는 일

`ssh -L`은 **"로컬 포트 포워딩"** 이라고 부르는 SSH 터널의 한 종류입니다.

```bash
ssh -L 51234:localhost:51234 gpu-server
```

이 한 줄은 이렇게 풀립니다.

1. 내 PC와 `gpu-server` 사이에 **SSH 세션(22번)을 먼저 맺는다**.
2. 내 PC의 `localhost:51234`로 들어오는 TCP 트래픽을 **SSH 패킷으로 감싸서** 그 세션 안으로 흘려보낸다.
3. `gpu-server` 쪽 sshd가 패킷을 풀어 원래 TCP 트래픽으로 복원한 다음, **`gpu-server` 입장에서의 `localhost:51234`** 로 전달한다.

`-L`의 두 번째 인자 `localhost`는 **`gpu-server` 기준**의 localhost입니다. 내 PC가 아니라요. 그래서 vLLM이 `gpu-server`에서 `0.0.0.0`이 아니라 `127.0.0.1:51234`로만 바인딩돼 있어도 터널은 통합니다. 같은 머신 안에서 잡기 때문이에요.

여기서 결정적인 포인트:

> **`51234`가 외부에 열려있을 필요가 없습니다.** 외부에 열린 건 22번이고, 51234 트래픽은 22번 SSH 패킷 안에 들어가서 통과하니까요. 터널의 통과 조건은 _"목적지 포트가 외부에 열려있는가"_ 가 아니라 **"SSH가 들어갈 수 있는가"** 예요.

## 2. "왜 로컬에선 됐었지?" — 회사 IP 화이트리스트

여기서 진짜 의문이 시작됩니다. `gpu-server`는 회사 사내망에 있는 서버고, `51234`가 외부에 열려있던 적도 없습니다. **그런데 왜 로컬에선 됐었지?**

답은 단순했어요. `gpu-server`의 방화벽에 **회사 공인 IP가 화이트리스트로 등록돼 있었기 때문**입니다.

### 화이트리스트가 뭐냐

> [!NOTE] Whitelist vs Blacklist
> **화이트리스트(허용 목록)**: 기본은 차단. 명시적으로 허용한 것만 통과시킴.
> **블랙리스트(차단 목록)**: 기본은 허용. 명시적으로 차단한 것만 막음.
>
> 방화벽은 거의 항상 화이트리스트 방식입니다. _"누가 들어와도 되는지"_ 명시한 목록만 통과시키고, 그 외엔 전부 거절(default-deny).

`gpu-server`의 화이트리스트엔 회사 공인 IP가 들어있었고, 제 노트북은 회사 사무실 와이파이에 붙어있을 때 그 공인 IP를 거쳐 나갑니다.

```text
allow  from <회사 공인 IP>  to 0-65535   # 회사망에서 오면 모든 포트 허용
```

그래서 회사망에 있으면 22번이든 51234번이든 다 닿았어요. 22번이 닿으니 SSH가 들어가고, 그 위에 51234 터널이 얹히고. 깔끔하게 동작했죠.

문제는 이 우회로가 **너무 자연스럽게 작동하고 있어서**, 정작 받쳐주고 있던 게 뭔지를 의식하지 못했다는 거예요. 어렴풋이 이런 모델만 갖고 있었습니다.

> "ssh -L로 터널 뚫으면 되는구나."

화이트리스트가 깔아주던 다리는 보이지 않았던 거고요. GCP에서 깨지면서 그게 드러납니다.

## 3. GCP에선 — 1단계부터 막혔다

GCP VM에서 같은 명령을 치면 이렇게 됩니다.

```bash
$ ssh -L 51234:localhost:51234 gpu-server
ssh: connect to host gpu-server port 22: Connection timed out
```

22번 SSH 자체가 거부돼요. 이유는 단순합니다. **`gpu-server` 화이트리스트에 GCP VM의 공인 IP가 없었던 것.**

```text
allow  from <회사 공인 IP>  to 0-65535     # 회사망에서만 OK
# GCP VM IP는 어디에도 등록 안 됨 → 22번 핸드셰이크부터 드롭
```

SSH가 안 들어가면 그 위에 얹을 터널도 없어요. `-L`은 이미 맺힌 SSH 위에 얹는 기능이니까요.

여기까지는 사실 예상 가능했습니다. _"아 IP가 등록 안 돼서 막힌 거구나"_ — 보안팀에 요청해서 GCP VM의 공인 IP를 화이트리스트에 추가받았어요.

### 그래서 IP를 등록받았다 — 그런데도 안 됐다

이제 SSH는 들어갑니다.

```bash
$ ssh gpu-server
# 잘 들어감
```

근데 51234 터널이 **여전히 안 닿아요**.

```bash
$ ssh -L 51234:localhost:51234 gpu-server
# 터널 명령은 떴는데
$ curl http://localhost:51234/v1/models
curl: (52) Empty reply from server
```

여기서부터가 제가 **가장 오래 헷갈렸던 지점**이에요. _"IP 등록까지 받았는데 왜 안 되지? 회사망에선 똑같이 IP 등록만으로 됐었잖아?"_

답은 다음 장에 있습니다 — 제가 갖고 있던 _"IP만 등록하면 다 통과한다"_ 라는 모델이 사실은 **한 차원 부족**했어요.

## 4. 방화벽은 1차원이 아니다 — IP × Port

답은 **방화벽 룰의 단위**에 있었어요. 제 머릿속 모델은 *"IP를 등록하면 다 통과한다"*였는데, 실제 방화벽은 그렇게 안 굴러갑니다.

### 방화벽 룰은 IP × Port의 2차원이다

방화벽 정책의 한 줄은 거칠게 표현하면 이런 튜플입니다.

```text
allow  from <source IP/CIDR>  to <dest port range>  proto <tcp/udp>
```

축이 두 개라는 게 핵심이에요. **Source IP**가 통과해야 하고, **Destination Port**도 통과해야 합니다. 두 축이 모두 매칭돼야 패킷이 들어옵니다.

`gpu-server`의 룰을 다시 보면 — GCP IP 등록을 받은 뒤의 모양은 사실 이랬어요.

```text
allow  from <회사 공인 IP>  to 0-65535       # 회사망: 전체 포트 허용 (wildcard)
allow  from <GCP VM IP>     to 45000-45010   # GCP: 특정 범위만 허용 (방금 추가됨)
```

같은 "화이트리스트 등록"이라도 **부여된 포트 스코프가 달랐던** 겁니다.

| 어디서 왔는가 | 허용 포트            | 51234 닿나?     |
| ------------- | -------------------- | --------------- |
| 회사 공인 IP  | `0–65535` (wildcard) | OK              |
| GCP VM IP     | `45000–45010`        | 매칭 실패, 드롭 |
| 그 외 IP      | 룰 없음              | 22번부터 거절   |

내가 GCP IP를 "등록받았다"고 한 건 **Source 축에서만 통과시켜준 것**이고, Destination Port 축은 별도로 정해져 있었습니다. **51234는 GCP의 포트 스코프 밖이라 룰 매칭에서 떨어진 것**이고요.

### 왜 회사망만 wildcard였을까

이건 보안 운영에서 흔한 패턴입니다. 신뢰 도메인별로 스코프를 다르게 줘요.

- **신뢰 도메인 (trusted zone)**: 회사 내부망은 물리적·관리적 통제가 이미 들어간 네트워크. wildcard 허용해도 위협 표면이 작다고 판단 → 개발 편의 위해 전체 포트 개방.
- **준신뢰/외부 (semi-trusted)**: GCP 같은 외부 클라우드는 IAM 키나 인스턴스가 털리면 곧장 인터넷 노출이 됩니다. 그래서 **최소 권한 원칙**으로 정말 필요한 포트만 열어줘요.

51234가 막힌 건 **버그가 아니라 의도된 정책**이었습니다.

### 내가 잘못 갖고 있던 모델 vs 실제 모델

|                     | 내가 갖고 있던 모델   | 실제 모델                      |
| ------------------- | --------------------- | ------------------------------ |
| 허용의 단위         | IP (등록 = 전체 접근) | (IP, Port) 튜플                |
| 차원                | 1차원                 | 2차원                          |
| "회사망은 왜 됐지?" | IP가 등록돼서         | IP 등록 + 포트 wildcard        |
| "GCP는 왜 안 됐지?" | IP 등록이 안 된 줄    | IP는 등록됐는데 포트 스코프 밖 |

> 방화벽에서 "허용됐다"는 말은 항상 **누가(Source) × 어디로(Port)**의 곱집합 위 한 점입니다. IP만 보면 통과한 줄 알고, 포트만 보면 열린 줄 압니다. 두 축을 같이 보지 않으면 "왜 됐었지?"도 "왜 안 되지?"도 영원히 안 풀려요.

## 5. 그래서 구조를 바꿨다 — 외부 통신 표면적 줄이기

해결책은 두 갈래였어요.

| 선택지                           | 설명                                                         | 비용                     |
| -------------------------------- | ------------------------------------------------------------ | ------------------------ |
| (A) 네트워크를 GCP에 맞춰 늘리기 | `gpu-server` 화이트리스트에서 GCP IP에도 51234를 추가        | 보안팀과 협의 필요, 시간 |
| (B) 통신해야 할 표면적을 줄이기  | ai/be를 `gpu-server`로 옮겨서, 외부 통신을 fe→be 하나로 축소 | 배포 한 번이면 끝        |

(B)를 택했어요. 시간 비용이 낮고, **구조적으로 더 단순**해지니까요. 외부 통신이 줄면 그만큼 보안 표면적도 줄고, 디버깅할 네트워크 경로도 줄어듭니다.

| 서비스 | 전           | 후                  |
| ------ | ------------ | ------------------- |
| `fe`   | GCP          | GCP (유지)          |
| `be`   | GCP          | `gpu-server`로 이사 |
| `ai`   | GCP          | `gpu-server`로 이사 |
| `vLLM` | `gpu-server` | `gpu-server`        |

이제 `ai ↔ vLLM`은 같은 머신 안이라 `localhost:51234`로 그냥 호출됩니다. 터널 필요 없음. 남은 외부 통신은 `fe → be` 하나고, 그건 GCP IP의 허용 포트 범위(`45000–45010`) 안에서 골라 쓰면 끝이에요.

> "서비스 간 거리가 짧을수록 네트워크 문제가 줄어든다." 같은 호스트면 loopback, 같은 VPC면 사설 IP, 외부면 방화벽 통과. 거리 한 단계 줄일 때마다 깨질 수 있는 지점이 한 줄씩 사라집니다.

## 6. 마지막 오해 — "AI 포트가 이미 있는 줄 알았는데"

구조를 다 바꾸고 나서 또 한 번 헷갈린 지점이 있었어요. fe에서 be를 호출하려고 보니 — _"AI 포트는 51234니까 그건 그대로 두고, be 포트만 정하면 되겠지?"_ 라고 생각하고 시작했거든요.

근데 막상 띄워보니 `ai` 컨테이너가 안 떴어요. `51234`가 이미 vLLM이 쓰고 있어서요.

여기서 깨달았습니다. **"AI 서버"는 포트 하나로 안 끝납니다.**

```text
[ gpu-server 머신 안 ]
  vLLM         : 51234  ← LLM inference 서버 (모델 서빙)
  AI FastAPI   : 8800   ← .docx 파싱 + vLLM 호출하는 우리 코드
  BE NestJS    : 3100   ← FE가 호출하는 진입점
```

vLLM은 **모델 서빙 엔진**이고, 우리가 만든 AI FastAPI 서버는 **그 위에서 비즈니스 로직을 도는 별도 프로세스**입니다. 둘은 같은 머신 안에 있어도 다른 프로세스, 다른 포트예요.

"한 서버 = 한 포트"라는 무의식의 1:1 매핑이 출발점이었어요. 사실은 **한 프로세스 = 한 포트**가 맞는 모델이고, 한 서버 안에 여러 프로세스가 있으면 포트도 그만큼 필요합니다.

결국 통신 구조는 이렇게 정리됐어요.

```text
FE (GCP)
  │
  │  HTTPS, 45000–45010 범위 중 한 포트
  ▼
BE NestJS (gpu-server:3100)  ← 외부 노출은 여기 하나만
  │
  │  localhost:8800 (같은 머신 안)
  ▼
AI FastAPI (gpu-server:8800)
  │
  │  localhost:51234 (같은 머신 안)
  ▼
vLLM (gpu-server:51234)
```

외부 통신은 fe→be 한 번이고, 나머지는 전부 loopback. **방화벽이랑 싸울 일이 한 줄로 줄어든 거예요.**

## 7. 정리

처음엔 "터널만 뚫으면 끝"이라고 생각했고, 다음엔 "포트 번호 안다고 다 열린 게 아니"라는 걸 배웠고, 마지막엔 "한 서버 = 한 포트가 아니라 한 프로세스 = 한 포트"라는 당연한 사실을 다시 확인했습니다.

배운 걸 정리하면 이렇게 세 줄이에요.

1. **SSH 터널은 포트를 여는 게 아니라, 이미 뚫린 SSH 위에 트래픽을 얹는 것이다.** 그래서 SSH가 들어갈 수 있느냐가 모든 것의 출발점.
2. **방화벽 허용은 IP × Port의 2차원이다.** "IP 등록했다"와 "그 IP에 모든 포트가 열렸다"는 별개의 결정.
3. **"왜 됐었지?"를 설명하지 못하면 "왜 안 되지?"도 못 푼다.** 명령이 작동하던 것을 받쳐주던 환경(IP 화이트리스트)을 의식하지 않으면, 환경 바뀌었을 때 무너지는 이유도 안 보입니다.

네트워크 문제는 명령어 한 줄의 문법이 아니라, 그 명령이 통과해야 하는 **경로 전체**의 문제였어요. 다음에 또 다른 환경에서 같은 명령이 안 될 때, 이번엔 명령어부터 의심하지 않고 경로부터 그려보려고요.
