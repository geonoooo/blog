> 369줄짜리 `styles.css` 하나의 기록입니다. 토큰을 정하는 일의 절반은 무엇을 쓸지 고르는 것이고, 나머지 절반은 무엇을 **안** 쓸지 못 박는 것입니다. 그리고 어길 자리는 어긴다고 적어 둡니다. 중간에 Tailwind v4 + Lightning CSS 함정 세 개가 나옵니다.

폴더 구조와 lint 편은 [폴더 이름은 응집도를 지켜주지 않는다](/posts/folder-names-dont-enforce-cohesion)에 따로 적었습니다.

## 선이 아니라 면으로 나눈다

관리 도구 화면은 금방 선으로 뒤덮입니다. 카드에 `border`, 표 행마다 `border-bottom`, 섹션 사이에 `hr`. 하나씩 보면 다 합리적인데 모아 놓으면 화면이 격자로 갈립니다. 그래서 이 파일은 맨 위에 원칙 세 줄을 박아 놓고 시작합니다.

```css
/* fe/src/styles.css
 * 경계선이 아니라 면(surface)의 톤 차이와 아주 옅은 그림자로 위계를 만든다.
 * 색은 "선택된 것"(accent)과 "조치가 필요한 것"(warn) 두 곳에만 쓴다.
 * 정상 상태에는 색을 쓰지 않는다.
 */
```

면은 세 단입니다. 그리고 **세 값이 서로 달라야 3단계가 성립한다**는 조건이 주석에 같이 적혀 있습니다. 밝기를 3%쯤씩 벌려 둡니다.

| 토큰      | 라이트    | 역할 |
| --------- | --------- | ---- |
| `canvas`  | `#edeff4` | 바닥 |
| `sunken`  | `#f4f5f7` | 함몰 |
| `surface` | `#ffffff` | 카드 |

## 유채색은 네 가지 뜻만 가진다

색을 토큰으로 만들 때 흔한 실수는 **색 이름**으로 만드는 것입니다. `blue-500`, `red-400`. 그러면 "이 배지는 무슨 색이지?"에는 답할 수 있지만 "이 자리에 색을 써도 되나?"에는 못 답합니다.

여기서는 네 개뿐이고 각각 뜻을 가집니다. 하나에 하나씩이고 겹쳐 쓰지 않습니다.

| 토큰     | 뜻                    | 쓰는 곳                       |
| -------- | --------------------- | ----------------------------- |
| `accent` | 지금 선택된 것        | 선택된 탭, 고른 칩, 포커스 링 |
| `warn`   | 네가 확인해야 하는 것 | 설정이 비어 있는 항목         |
| `danger` | 이미 틀린 것          | 오역 건수, 검증 실패          |
| `ok`     | 이 일이 끝났다        | 검수 통과율, 완료 배지        |

`warn`과 `danger`를 가른 게 이 목록의 핵심입니다. 보통 이 둘은 "노란색/빨간색" 정도로 뭉뚱그려지는데, 주석은 뜻으로 갈라 놓습니다.

```css
/* warn과 뜻이 다르다 — warn은 확인을 요구하고, danger는 이미 잘못된 것을 가리킨다. */
```

이 구분이 있으면 "시험방법이 아직 설정 안 된 항목"은 `warn`이고 "번역 검증에서 튕긴 문장"은 `danger`라는 게 논쟁 없이 정해집니다. 구분이 없으면 매번 다시 정합니다.

## 정상 상태에는 색을 쓰지 않는다

보고서 상태는 셋입니다 — 진행중, 검토중, 완료. 셋 다 정상입니다. 여기에 파랑/노랑/초록을 붙이는 게 자연스러워 보이지만, 그 배지는 목록의 **모든 행**에 붙습니다.

```tsx
// modules/reports/ui/status-badge.tsx
/*
 * 상태는 색이 아니라 톤과 굵기로 나눈다. 진행중·검토중·완료는 셋 다 정상 상태라
 * 색을 쓰면 목록 전체가 물들고, 정작 조치가 필요한 것이 묻힌다.
 * 지금 살아 있는 것일수록 앞으로 나오고, 끝난 것은 가라앉는다.
 */
const TONE: Record<ReportStatus, string> = {
  "in-progress": "bg-sunken font-semibold text-ink",
  review: "bg-sunken font-medium   text-ink-3",
  completed: "font-medium text-ink-4",
};
```

잉크 램프(`ink → ink-4`)와 굵기만으로 세 단계를 만듭니다. 완료는 배경조차 없습니다.

절제의 근거는 미학이 아니라 예산입니다. 화면에서 눈이 갈 수 있는 자리는 한정돼 있고 색은 그 예산을 씁니다. 정상 상태에 색을 쓰면 조치가 필요한 것에 쓸 예산이 남지 않습니다.

이 규칙은 **이미 한 번 깨져 있고**, 그것도 적혀 있습니다.

```md
<!-- fe/CLAUDE.md -->

ok는 화면기획이 그렇게 그려져 있어 검수 이력 목록의 모든 행에도 붙는데,
초록이 행마다 깔리면 같은 칸의 오역 건수가 묻힌다. 나중에 좁힐 자리다.
```

규칙과 현실이 어긋날 때 할 수 있는 건 셋입니다. 규칙을 고치거나, 현실을 고치거나, 어긋났다는 걸 적어 두거나. 세 번째는 임시방편이 아닙니다. 다음에 이 화면을 여는 사람이 "왜 여기만 초록이지?"에서 시작하지 않게 해 줍니다.

## 함정 1 — `@theme`의 그림자는 다크 모드에서 안 바뀐다

Tailwind v4에서는 토큰을 `@theme` 블록에 넣는 게 기본입니다. 색도, 반경도, 활자도 거기 넣었습니다. 그림자만 빼고.

```css
/*
 * 그림자만 @theme 밖에 둔다. @theme의 --shadow-*는 Tailwind가 유틸리티에 값을
 * 그대로 인라인해버려서 .dark에서 아무리 덮어써도 바뀌지 않기 때문이다.
 * 색상 토큰은 var() 참조로 나가므로 @theme에 두어도 정상 동작한다.
 */
:root {
  --shadow-card: inset 0 -1px 0 rgb(17 20 26 / 0.05), /* … */;
}

@utility shadow-card {
  box-shadow: var(--shadow-card);
}
```

증상이 고약합니다. `.dark` 블록에 `--shadow-card`를 다시 정의해도 화면은 안 바뀝니다. DevTools로 보면 변수는 제대로 덮여 있습니다. 그런데 유틸리티에는 라이트 값이 문자열로 박혀 있습니다. **변수는 맞고 화면은 틀린** 상태라 원인을 색상 쪽에서 찾다가 시간을 버립니다.

해법은 `@theme`이 아니라 `:root`에 두고 `@utility`로 `var()` 참조를 직접 만드는 것입니다. 색상 토큰은 어차피 `var()`로 나가니 `@theme`에 둬도 됩니다.

일반화하면, 런타임에 갈아끼워야 하는 값은 빌드타임에 인라인되지 않는지 확인해야 합니다. 다크 모드·테마 전환은 전부 이 조건에 걸립니다. "변수는 바뀌었는데 화면은 그대로"면 인라인을 의심하십시오.

## 함정 2 — Lightning CSS가 조용히 고쳐 놓는 것

Tailwind v4는 Lightning CSS로 CSS를 처리합니다. 빠른 대신 계산할 수 있는 건 빌드타임에 계산해 버립니다. 이 파일에는 그 성질에 물린 자리가 두 군데 적혀 있습니다.

**`color-mix`는 못 풉니다.** 바탕 얼룩에 쓰는 강조색을 투명도만 바꿔 여러 번 써야 했습니다. 보통은 `color-mix`를 쓰지만, 여기서는 색이 아니라 RGB 세 값을 토큰으로 둡니다.

```css
/* 색이 아니라 RGB 세 값이다. 아래에서 알파만 갈아끼워 쓴다. color-mix로
   쓰면 Lightning CSS가 빌드할 때 계산을 못 하고 원색을 그대로 깐다. */
--tint: 47 107 240;

background-image: radial-gradient(65rem 45rem at 5% -10%, rgb(var(--tint) / 0.45), transparent 62%);
```

실패 모드가 나쁩니다. 에러가 아니라 불투명한 원색이 깔립니다. 옅어야 할 얼룩이 진한 파랑이 됩니다.

**`-webkit-` 접두사를 손으로 쓰면 안 됩니다.**

```css
/* -webkit- 접두사는 직접 쓰지 마라. 손으로 쓰면 Lightning CSS가 그걸
   정답으로 보고 접두사 없는 쪽을 지워버려서 파이어폭스에서 유리가 사라진다. */
```

호환성을 챙기려고 한 줄 더 쓴 게 호환성을 깨는 경우입니다. 빌드 도구가 접두사를 알아서 붙이는 환경에서는 손으로 쓴 접두사가 도구에게 "이미 처리됨" 신호로 읽힙니다.

## GPU를 쓰지 않는 유리

사이드바와 헤더는 유리판처럼 보입니다. 보통 `backdrop-filter: blur()`로 만듭니다. 여기서는 그렇게 보이는 것의 대부분이 블러가 아니라 그림자에서 나옵니다.

핵심은 두께입니다. 네 방향 안쪽 테두리를 서로 다른 밝기로 깝니다. 위가 제일 밝고 아래가 제일 어둡습니다. 네 값이 같으면 그냥 테두리 선이 됩니다.

```css
--glass-thickness:
  inset 0 1.5px 0 rgb(255 255 255 / 0.95),
  /* 위: 제일 밝다 */ inset 1.5px 0 0 rgb(255 255 255 / 0.5),
  inset -1.5px 0 0 rgb(255 255 255 / 0.5), inset 0 -1.5px 0 rgb(255 255 255 / 0.3),
  /* 아래: 제일 어둡다 */ inset 0 14px 20px -14px rgb(255 255 255 / 0.9),
  inset 0 -14px 20px -14px rgb(30 48 100 / 0.26);
```

전부 `box-shadow`입니다. GPU를 쓰지 않습니다.

그림자를 하나의 유틸리티로 합쳐 둔 데도 이유가 있습니다. `box-shadow`는 유틸리티끼리 겹치면 나중 것이 앞의 것을 통째로 덮습니다. `shadow-thickness`와 `shadow-drop`을 따로 만들어 두 클래스를 같이 붙이면 한쪽이 조용히 사라집니다. 그래서 하나로 합칩니다.

그리고 이 유틸리티에는 쓰는 쪽이 지켜야 할 조건까지 적혀 있습니다.

```css
/* 붙이는 요소에 반드시 모서리 반경과 사방 여백을 줘라.
   가장자리에 딱 붙은 직사각형에는 두께가 보이지 않는다. */
```

## 원칙을 어긴 자리를 표시해 둔다

유리는 이 파일이 맨 위에 세운 원칙 두 개를 정면으로 어깁니다. 바탕에 유채색을 깔고(`--tint`), 가장자리를 선으로 세웁니다(`--glass-thickness`). "정상 상태에 색을 쓰지 않는다"와 "선으로 나누지 않는다" 둘 다 위반입니다.

숨기지 않습니다. 어긴다고 쓰고 되돌리는 방법까지 적어 둡니다.

```css
/* 여기부터 이 파일 위쪽의 원칙 두 개를 일부러 어긴다. (…) 둘 다 유리가 유리로
   보이는 데 필수라 뺄 수가 없다. 유리를 걷어내면 같이 걷어내라. */
```

마지막 문장이 이 주석을 쓸모 있게 만듭니다. "예외입니다"만 적힌 주석은 예외를 영구화합니다. "유리를 걷어내면 같이 걷어내라"는 `--tint`와 `--glass-thickness`의 수명을 유리에 묶어 놓습니다.

## 블러는 두 곳에만 쓴다

블러를 아예 안 쓰는 건 아닙니다. 다만 비용을 식으로 적어 놓고 씁니다.

```text
비용 = 면적 × 반지름 × 뒤 레이어가 다시 그려지는 횟수
```

그리고 "뒤로 무늬가 있는 것이 지나가는 곳에만 붙여라"라는 조건이 붙습니다. 바탕 얼룩처럼 완만한 그라디언트는 흐려도 같은 그라디언트가 나오니 비용만 들고 효과가 없습니다. 조건을 통과한 자리는 둘뿐입니다.

| 쓰는 곳       | 면적        | 다시 그리는 때                      |
| ------------- | ----------- | ----------------------------------- |
| 헤더          | 화면의 4.5% | 스크롤 중에만. 본문이 밑으로 흐른다 |
| 모달 오버레이 | 화면 전체   | 열 때 한 번. 뒤가 멈춰 있다         |

모달은 판이 아니라 **뒤에** 블러를 겁니다. 이유는 대비입니다. 판을 반투명하게 하면 그 위에서 폼을 읽고 입력해야 하는 글자의 대비가 3.1:1까지 떨어집니다.

같은 논리로 유리는 셸 판에만 씁니다. 사이드바, 헤더, 목차 레일. 글을 읽고 쓰는 면(카드, 모달, 편집기)은 불투명하게 둡니다. 반투명한 면 위에서는 글자 대비가 뒤에 뭐가 있느냐에 따라 변해서 4.5:1을 보장할 수 없습니다. `saturate`도 장식이 아닙니다. `blur`만 걸면 뒤의 색이 평균으로 뭉개져 회색이 됩니다.

## 토큰만 갈아끼우면 컴포넌트는 몰라도 된다

투명 효과를 줄이도록 설정한 사용자에게는 불투명한 면으로 되돌립니다. 컴포넌트는 아무것도 안 고칩니다. `--glass-bg` 하나만 바꿉니다.

```css
@media (prefers-reduced-transparency: reduce) {
  :root {
    --glass-bg: #ffffff;
  }
  .dark {
    --glass-bg: #20242c;
  }
}
```

`.dark` 뒤에 와야 다크에서도 덮입니다. `:root`와 `.dark`는 특이도가 같아서 순서로 갈립니다. 이런 건 몰라서 틀리는 게 아니라 파일 중간에 끼워 넣다가 틀립니다.

포커스 링은 반대 방향의 기교를 씁니다. `:where()`로 감싸 특이도를 0으로 만들어 두면 필요한 곳에서 컴포넌트 클래스 하나로 덮어쓸 수 있습니다.

```css
:where(a, button, input, select, textarea, [tabindex]):focus-visible {
  outline: var(--focus-ring-width) solid var(--color-accent);
  outline-offset: var(--focus-ring-offset);
}
```

`outline`은 요소의 `border-radius`를 따라가므로 모양은 각자 맞습니다. `:focus-visible`이라 마우스 클릭에는 안 뜨고 키보드로 옮겨왔을 때만 뜹니다. `sr-only` 입력을 품은 `label`에는 `focus-ring-within`을 따로 만들어 붙입니다. 입력이 클립돼 있어 자기 포커스 링을 못 보여주니 눌러야 하는 판이 대신 링을 받습니다. 두 규칙이 같은 토큰을 읽는다는 게 요점입니다. 키보드로 옮겨온 자리는 화면 어디서나 같은 모양이어야 합니다.

## 다크: 바닥을 검정까지 내리지 않는다

다크 팔레트를 만들 때 반사적으로 하는 일이 배경을 `#000`에 가깝게 내리는 것입니다. 그러면 카드가 떠오를 것 같지만 안 그렇습니다.

```css
/* 바닥을 검정까지 내리지 않는다. 어둠을 더 어둡게 해도 카드가 떠오르지 않는다.
   카드 쪽을 들어올려야 위계가 생기고, 그 위의 글자도 읽힌다. */
```

| 토큰      | 다크      | 역할 |
| --------- | --------- | ---- |
| `canvas`  | `#0f1216` | 바닥 |
| `sunken`  | `#171b21` | 함몰 |
| `surface` | `#20242c` | 카드 |

라이트와 같은 순서로 벌립니다. canvas가 가장 어둡고 surface가 가장 밝습니다. 역할이 뒤집히지 않으니 컴포넌트는 두 테마를 구분할 필요가 없습니다.

면이 밝아지면 나머지가 따라 움직입니다. 잉크 램프를 그대로 쓰면 아래 두 단이 묻히고, `accent-soft`·`danger-soft`는 면이 밝아진 만큼 같이 올려야 "고른 것"으로 읽힙니다. 원색도 밝은 쪽으로 갑니다. 어두운 면 위에서는 라이트의 원색이 탁합니다.

그림자는 방향이 통째로 뒤집힙니다. 어두운 면은 바닥보다 밝으므로 두께를 아랫변이 아니라 윗변에 줍니다. 유리도 같습니다. 위쪽 하이라이트는 라이트의 1/4로 줄이고 아래쪽은 흰색 대신 검정으로 바꿉니다. 알파도 `0.6`에서 `0.09`로 내립니다. 어두운 면에 라이트의 알파를 쓰면 흰 판이 됩니다.

정직하게 덧붙이면, 이 다크 팔레트는 시안이 있어서 나온 값이 아닙니다. 주석에 그대로 적혀 있습니다 — "피그마에 다크 시안이 없어 무채색 램프로 대응한 값이다. 시안이 나오면 이 블록만 교체하면 된다." 토큰으로 갈라 놨기 때문에 그 교체가 블록 하나로 끝난다는 게 요점입니다.

## 정리

- **색 토큰은 색 이름이 아니라 뜻으로 지으십시오.** `red-400`은 "이 자리에 색을 써도 되나"에 답하지 못하고 `danger`는 답합니다.
- **`warn`과 `danger`를 가르십시오.** 확인을 요구하는 것과 이미 틀린 것은 다른 행동을 부릅니다.
- **Tailwind v4의 `@theme`에 `--shadow-*`를 두지 마십시오.** 유틸리티에 값이 인라인돼서 테마 전환이 안 먹습니다. `:root` + `@utility var()`로 빼십시오.
- **`-webkit-` 접두사를 손으로 쓰지 마십시오.** Lightning CSS가 그걸 정답으로 보고 표준 속성을 지웁니다.
- **`box-shadow` 유틸리티를 쪼개지 마십시오.** 겹치면 나중 것이 앞의 것을 통째로 덮습니다.
- **글을 읽고 쓰는 면은 불투명하게 두십시오.** 반투명 위에서는 대비가 뒤 내용에 따라 변해 4.5:1을 보장할 수 없습니다.
- **어기는 자리는 어긴다고 적고 되돌릴 조건까지 적으십시오.** "유리를 걷어내면 같이 걷어내라" 같은 문장이 예외의 수명을 정해 줍니다.
