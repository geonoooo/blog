요즘 면접을 보러 다니면서 자바스크립트 기본 개념이 많이 부족하다는 걸 느꼈습니다. 알고 있는 것과 그걸 말로 설명하는 것은 전혀 다른 일이었습니다. 코드로 짜면 맞게 동작하는데, 왜 그렇게 동작하는지 물어보면 문장이 나오지 않았습니다.

면접이 끝나면 남는 생각은 늘 같았습니다 — "아, 그 말을 했어야 했는데." 첫 질문은 그럭저럭 넘겨도 "그럼 이건요?" 하고 꼬리질문이 붙으면 말이 길어졌습니다. 용어가 떠오르지 않아서입니다. TDZ 한 단어면 끝날 걸 "let으로 선언한 변수를 선언 전에 쓰면 에러가 나는 그 구간이..." 하고 한참 돌려 말했습니다. 결과는 또 탈락. ~~이번엔 다를 줄 알았습니다.~~

면접 준비만의 문제는 아니었습니다. 바이브코딩을 하면서부터 코드를 직접 읽는 일이 크게 줄었습니다. 여러 세션에서 작업을 돌리다 보니 코드를 하나하나 보는 대신 검증을 늘렸습니다 — CodeRabbit 리뷰, 뮤테이션 테스트, Playwright E2E 테스트를 두세 번씩 돌려서 문제를 걸러내는 식입니다. 그렇게 코드를 안 보다 보니 알고 있던 개념도 잊어버리는 경우가 생겼습니다.

그래서 면접을 잠시 멈추고 자바스크립트 기본 개념부터 다시 다지기로 했습니다. 기준은 하나입니다 — 아는 것을 **말로 설명할 수 있을 때까지**.

이 글은 주제마다 첫 질문과 답, 이어질 수 있는 꼬리질문과 답을 적었습니다.

> [!NOTE] 기준
> 언어 동작은 ECMAScript 표준, 브라우저 동작은 HTML 표준 기준입니다. 출력 순서를 적은 예제는 Node 24와 Chromium 155에서 실행해 확인했습니다. 따로 적지 않으면 ES 모듈(strict mode)에서 실행한다고 가정합니다.

## 답변하는 방법

### 네 단계로 답한다

정의만 말하고 끝내면 꼬리질문이 이어졌습니다. 그래서 처음 답할 때 네 단계를 한 번에 말하는 연습을 하기로 했습니다. 꼬리질문 몇 개는 미리 답한 셈이 됩니다.

| 단계         | 내용               | 이벤트 루프 예시                                     |
| ------------ | ------------------ | ---------------------------------------------------- |
| 1. 정의      | 한 문장            | 콜 스택이 비면 큐에서 콜백을 꺼내 실행하는 루프      |
| 2. 동작 원리 | 표준·엔진 용어로   | 태스크 하나 → 마이크로태스크 전부 → 렌더링           |
| 3. 코드      | 짧은 예제 하나     | `setTimeout`보다 `Promise.then` 콜백이 먼저 실행된다 |
| 4. 실무      | 겪은 일, 코드 결정 | 무거운 계산 때문에 로딩 스피너가 안 보이는 문제      |

### 출력 순서 문제는 큐를 적으면서 푼다

머릿속으로만 돌리지 않고 세 칸을 적거나 말로 짚으면서 풀기로 했습니다.

```yaml
콜 스택: 지금 실행 중인 동기 코드
마이크로태스크 큐: Promise.then 콜백, await 이후 코드, queueMicrotask
태스크 큐: setTimeout, setInterval, 이벤트 콜백
```

순서는 항상 같습니다. 동기 코드를 끝까지 실행하면서 큐에 넣고, 콜 스택이 비면 마이크로태스크 큐를 전부 비우고, 그다음 태스크를 하나 꺼냅니다. 답만 말하지 않고 이 과정을 말로 따라갑니다. 틀리더라도 어느 단계에서 틀렸는지가 드러납니다.

### 모르는 꼬리질문이 나오면

"모르겠습니다"로 끝내지 않기로 했습니다. 아는 사실에서 추론한 답을 말하고, 추론이라고 밝힙니다.

> "정확히 확인해본 적은 없습니다. 다만 `await` 이후 코드가 마이크로태스크로 재개된다는 건 알고 있어서, 이 경우 `setTimeout` 콜백보다 먼저 실행될 것 같습니다."

## 1. 이벤트 루프

### Q. 자바스크립트는 싱글 스레드인데 비동기 작업은 어떻게 처리하나요?

**답변**

싱글 스레드라는 건 자바스크립트 코드를 실행하는 콜 스택이 하나라는 뜻입니다. 타이머, 네트워크 요청, 이벤트 대기는 자바스크립트 엔진이 아니라 호스트 환경이 처리합니다. 브라우저에서는 Web API, Node에서는 libuv입니다.

호스트는 작업이 끝나면 콜백을 큐에 넣습니다. 이벤트 루프는 콜 스택이 비었을 때 큐에서 콜백을 꺼내 콜 스택에 올립니다.

![콜 스택이 setTimeout을 호스트의 타이머에 등록하고, 타이머가 끝나면 콜백이 태스크 큐에 들어간다. Promise가 이행되면 then 콜백은 마이크로태스크 큐에 들어간다. 이벤트 루프는 콜 스택이 비면 마이크로태스크 큐를 먼저 전부 비우고, 그다음 태스크를 하나 꺼내 콜 스택에 올린다.](/posts/javascript-interview-follow-up-questions/runtime.svg)

이벤트 루프는 ECMAScript가 아니라 HTML 표준에 정의돼 있습니다. 브라우저 이벤트 루프의 한 바퀴는 이렇습니다.

![1단계: 태스크 큐에서 가장 오래된 태스크 하나를 실행한다. 2단계: 마이크로태스크 큐가 빌 때까지 전부 실행한다. 실행 중 추가된 것도 포함한다. 3단계: 화면을 갱신할 차례면 requestAnimationFrame 콜백, 스타일, 레이아웃, 페인트 순서로 렌더링한다. 그다음 1단계로 돌아간다.](/posts/javascript-interview-follow-up-questions/loop-cycle.svg)

큐는 두 종류입니다.

| 구분           | 들어가는 것                                                                            | 한 바퀴에 실행되는 양 |
| -------------- | -------------------------------------------------------------------------------------- | --------------------- |
| 태스크         | `setTimeout`, `setInterval`, 이벤트 콜백, `MessageChannel`                             | 하나                  |
| 마이크로태스크 | `then`/`catch`/`finally` 콜백, `await` 이후 코드, `queueMicrotask`, `MutationObserver` | 큐가 빌 때까지 전부   |

흔히 쓰는 "매크로태스크"는 표준 용어가 아닙니다. 표준은 그냥 태스크라고 부릅니다. 태스크 큐는 하나가 아니라 출처(타이머, 사용자 입력, 네트워크)별로 여러 개일 수 있고, 어느 큐에서 먼저 꺼낼지는 브라우저가 정합니다. 마이크로태스크 큐는 하나입니다.

#### 꼬리 1. `setTimeout(fn, 0)`은 0ms 뒤에 실행되나요?

아닙니다. 0ms는 최소 대기 시간입니다. 타이머가 만료돼도 콜백은 태스크 큐에 들어갈 뿐이고, 지금 실행 중인 동기 코드와 그 뒤의 마이크로태스크가 모두 끝나야 실행됩니다. 앞에 다른 태스크가 쌓여 있으면 더 늦어집니다.

여기에 두 가지가 더 붙습니다. HTML 표준은 `setTimeout`이 5단계를 넘게 중첩되면 대기 시간을 최소 4ms로 올립니다. 그리고 백그라운드 탭에서는 브라우저가 타이머를 1초 이상 간격으로 묶어서 실행합니다.

중첩 제한은 Chromium 155에서 직접 재봤습니다. 콜백 안에서 다음 `setTimeout(fn, 0)`을 부르는 연쇄를 12번 이어가고, 호출 사이 간격을 `performance.now()`로 쟀습니다. 시행마다 `MessageChannel` 태스크에서 새로 시작해서 중첩 단계가 0부터 세어지게 했고, 40번 반복한 중앙값입니다.

![연쇄 setTimeout(fn, 0)의 실제 대기 시간 막대 그래프. 1번째부터 6번째 호출은 0ms, 최대 0.2ms. 7번째부터 12번째 호출은 중앙값 4.5ms, 범위 4.1~4.7ms.](/posts/javascript-interview-follow-up-questions/timer-clamp.svg)

6번째 호출까지는 0ms이고 7번째부터 4ms를 넘습니다. 7번째 호출은 6단계 중첩된 콜백 안에서 부른 것이라 "5단계 초과" 조건에 걸립니다.

그래서 `setTimeout`이나 `setInterval`을 호출 횟수로 세는 타이머는 오차가 쌓입니다. 경과 시간은 매번 `performance.now()`나 `Date.now()`의 차이로 계산해야 합니다.

#### 꼬리 2. 마이크로태스크가 마이크로태스크를 계속 추가하면 어떻게 되나요?

```js
function loop() {
  Promise.resolve().then(loop);
}
loop();
```

화면이 멈춥니다. 마이크로태스크 큐는 빌 때까지 실행하고, 실행 중에 새로 들어온 것도 같은 차례에 처리합니다. 큐가 비지 않으니 렌더링 단계와 다음 태스크로 넘어가지 못합니다. 클릭에도 반응하지 않습니다.

같은 재귀를 `setTimeout(loop)`로 바꾸면 멈추지 않습니다. 호출마다 별도 태스크가 되므로 태스크 사이에 렌더링과 다른 이벤트가 실행될 수 있습니다.

![Promise.resolve().then(loop) 재귀는 첫 태스크 뒤에 마이크로태스크가 끝없이 이어져 렌더링과 다음 태스크 차례가 오지 않는다. setTimeout(loop) 재귀는 loop 태스크 사이에 렌더링, click, input 같은 다른 태스크가 끼어든다.](/posts/javascript-interview-follow-up-questions/microtask-starvation.svg)

#### 꼬리 3. 마이크로태스크는 태스크가 끝날 때만 실행되나요?

정확히는 **콜 스택이 빌 때마다** 실행됩니다. 차이가 드러나는 예가 있습니다.

```js
button.addEventListener("click", () => {
  Promise.resolve().then(() => console.log("micro 1"));
  console.log("listener 1");
});
button.addEventListener("click", () => {
  Promise.resolve().then(() => console.log("micro 2"));
  console.log("listener 2");
});
```

사용자가 직접 클릭할 때와 코드에서 `button.click()`을 호출할 때 순서가 다릅니다.

```yaml
사용자 클릭: listener 1 → micro 1 → listener 2 → micro 2
button.click(): listener 1 → listener 2 → micro 1 → micro 2
```

사용자 클릭은 브라우저가 리스너를 하나씩 호출하고, 리스너 하나가 끝날 때마다 콜 스택이 비므로 그 사이에 마이크로태스크가 실행됩니다. `button.click()`은 그 호출을 한 자바스크립트 코드가 아직 콜 스택에 남아 있어서 리스너 사이에 스택이 비지 않습니다. 마이크로태스크는 `click()`을 호출한 코드까지 끝난 뒤에 실행됩니다.

![사용자 클릭에서는 listener 1이 끝나 콜 스택이 비면 micro 1이 실행되고, listener 2가 끝나면 micro 2가 실행된다. button.click() 호출에서는 click()을 부른 스크립트가 콜 스택 바닥에 남아 있어 listener 1과 listener 2가 그 위에서 연달아 실행되고, 스크립트가 끝나 스택이 빈 뒤에 micro 1과 micro 2가 실행된다.](/posts/javascript-interview-follow-up-questions/listener-microtask.svg)

테스트 코드에서 `click()`으로 이벤트를 흉내 낼 때 실제 사용자 클릭과 순서가 달라지는 이유가 이것입니다.

#### 꼬리 4. 무거운 작업 때문에 화면이 멈추면 어떻게 하나요?

```js
button.addEventListener("click", () => {
  spinner.hidden = false;
  buildReport(); // 2초 걸리는 동기 계산
  spinner.hidden = true;
});
```

스피너는 한 번도 보이지 않습니다. 두 번의 DOM 변경이 같은 태스크 안에서 일어나고, 렌더링은 태스크가 끝난 뒤에 일어납니다. 렌더링 시점에는 이미 `hidden = true`입니다. 2초 동안 클릭이나 스크롤에도 반응하지 않습니다.

방법은 세 가지입니다.

1. **작업을 쪼개고 태스크 사이에 양보한다.** 조각 사이에 태스크를 끊으면 그 틈에 렌더링과 입력 처리가 들어옵니다. `Promise.resolve()`로는 양보가 되지 않습니다. 마이크로태스크는 렌더링 전에 전부 실행되기 때문입니다.
2. **Web Worker로 옮긴다.** 별도 스레드에서 실행되므로 메인 스레드가 막히지 않습니다. 대신 DOM에 접근할 수 없고, 데이터는 `postMessage`로 복사해서 주고받습니다.
3. **계산량을 줄인다.** 메모이제이션, 가상 스크롤, 서버로 계산 옮기기.

```js
async function processInChunks(rows, handleRow, chunkSize = 500) {
  for (let start = 0; start < rows.length; start += chunkSize) {
    rows.slice(start, start + chunkSize).forEach(handleRow);
    await new Promise((resolve) => setTimeout(resolve));
  }
}
```

한 번에 계산할 때와 나눠서 계산할 때 메인 스레드가 쓰이는 모양은 이렇게 다릅니다. 실측값이 아니라 개념도입니다.

![한 번에 계산하면 click 핸들러가 2000ms 동안 메인 스레드를 잡고, 첫 페인트는 2000ms 뒤에 일어나며 그때는 스피너가 이미 숨겨져 있다. 250ms 조각 8개로 나누면 핸들러가 바로 끝나 스피너가 먼저 그려지고, 조각 사이마다 렌더링이 들어간다.](/posts/javascript-interview-follow-up-questions/long-task.svg)

`scheduler.yield()`를 지원하는 브라우저에서는 `setTimeout` 대신 그걸 씁니다. 양보한 뒤 다른 태스크 뒤로 밀리지 않고 우선해서 재개됩니다. 지원 범위는 쓰기 전에 확인해야 합니다.

Core Web Vitals의 INP(Interaction to Next Paint)가 이 문제를 잽니다. 사용자 입력부터 다음 페인트까지 걸린 시간이므로, 이벤트 핸들러가 메인 스레드를 오래 잡으면 수치가 그대로 나빠집니다. "INP를 개선해본 적 있나요?"로 이어질 수 있는 지점입니다.

#### 꼬리 5. Node.js의 이벤트 루프는 브라우저와 같나요?

다릅니다. Node는 libuv가 이벤트 루프를 돌리고, 한 바퀴가 여러 단계(phase)로 나뉩니다.

```yaml
timers: 만료된 setTimeout, setInterval 콜백
pending callbacks: 다음 바퀴로 미뤄진 일부 I/O 콜백
poll: 새 I/O 이벤트를 가져와 I/O 콜백 실행
check: setImmediate 콜백
close callbacks: socket.on("close") 같은 종료 콜백
```

![Node.js 이벤트 루프는 timers, pending, poll, check, close 단계를 차례로 돌고 다시 timers로 돌아간다. 각 단계 안에서 콜백 하나가 끝날 때마다 process.nextTick 큐를 전부 비우고, 그다음 Promise 마이크로태스크를 전부 비운 뒤 다음 콜백으로 넘어간다.](/posts/javascript-interview-follow-up-questions/node-phases.svg)

브라우저와 다른 점은 셋입니다.

- `process.nextTick` 큐가 따로 있고, Promise 마이크로태스크보다 먼저 비워집니다.
- `setImmediate`는 poll 단계 바로 뒤인 check 단계에서 실행됩니다. I/O 콜백 안에서 `setTimeout(fn, 0)`과 `setImmediate`를 같이 걸면 항상 `setImmediate`가 먼저입니다. 메인 모듈에서 걸면 순서가 보장되지 않습니다.
- Node 11부터는 브라우저처럼 콜백 하나가 끝날 때마다 마이크로태스크를 비웁니다. 그전에는 같은 단계의 콜백을 전부 실행한 뒤에 비웠습니다.

```js
// Node, CommonJS
Promise.resolve().then(() => console.log("promise"));
process.nextTick(() => console.log("nextTick"));
require("fs").readFile(__filename, () => {
  setTimeout(() => console.log("timeout"), 0);
  setImmediate(() => console.log("immediate"));
});
// nextTick → promise → immediate → timeout
```

### Q. 아래 코드의 출력 순서를 설명해주세요

```js
async function first() {
  console.log("first start");
  await second();
  console.log("first end");
}

async function second() {
  console.log("second");
}

console.log("script start");
setTimeout(() => console.log("setTimeout"), 0);
first();
new Promise((resolve) => {
  console.log("promise executor");
  resolve();
}).then(() => console.log("then"));
console.log("script end");
```

**답변**

```yaml
동기: script start → first start → second → promise executor → script end
마이크로태스크: first end → then
태스크: setTimeout
```

한 줄씩 따라가면 이렇습니다.

1. `script start`를 출력하고, `setTimeout` 콜백을 태스크 큐에 넣습니다.
2. `first()`를 호출합니다. `first start`를 출력하고 `second()`를 호출해 `second`를 출력합니다. async 함수는 이미 이행된 Promise를 반환합니다.
3. `await`이 그 Promise에 재개 작업을 걸고 `first`를 멈춥니다. Promise가 이미 이행돼 있으므로 재개 작업이 바로 마이크로태스크 큐에 들어갑니다. 제어는 `first()`를 호출한 쪽으로 돌아옵니다.
4. `new Promise`에 넘긴 함수(executor)는 동기로 실행됩니다. `promise executor`를 출력하고 `resolve()`합니다. `.then`을 거는 시점에 이미 이행돼 있으므로 콜백이 마이크로태스크 큐에 들어갑니다. 큐는 `[first 재개, then 콜백]`입니다.
5. `script end`를 출력합니다. 콜 스택이 비었으니 마이크로태스크를 순서대로 실행합니다. `first end`, `then`.
6. 마지막으로 태스크 큐의 `setTimeout`.

같은 과정을 네 시점의 큐 상태로 그리면 이렇습니다.

![1. await 직후: 콜 스택에는 전역 코드만 남고, 마이크로태스크 큐에 first 재개, 태스크 큐에 setTimeout 콜백이 있다. 출력은 script start, first start, second. 2. 동기 코드 끝: 콜 스택이 비고, 마이크로태스크 큐에 first 재개와 then 콜백이 있다. 출력은 promise executor, script end. 3. 마이크로태스크 처리: first 재개와 then 콜백이 차례로 실행되고 큐가 빈다. 출력은 first end, then. 4. 태스크 처리: setTimeout 콜백이 실행된다. 출력은 setTimeout.](/posts/javascript-interview-follow-up-questions/order-trace.svg)

#### 꼬리 1. `first end`가 `then`보다 먼저 나오는 건 항상 그런가요?

지금은 그렇지만 예전에는 아니었습니다. Chrome 72(V8 7.2) 이전에는 `await`이 넘겨받은 Promise를 한 번 더 감싸서 재개가 몇 틱 늦었고, `then`이 먼저 나왔습니다. 표준이 바뀌어 지금은 네이티브 Promise를 `await`하면 감싸지 않고 바로 재개 작업을 겁니다.

다만 서로 다른 Promise 체인 사이의 실행 순서는 엔진 세부 구현에 가깝습니다. 실무 코드가 이 순서에 기대고 있다면 그 코드가 문제입니다. 순서가 중요하면 `await`으로 명시적으로 이어야 합니다.

## 2. 실행 컨텍스트

### Q. 실행 컨텍스트가 무엇인가요?

**답변**

코드를 실행하는 데 필요한 배경이 되는 조건과 환경을 묶어둔 표준상의 개념입니다. 전역 코드, 함수 호출, 모듈, `eval` 코드를 실행할 때 만들어지고, 실행 컨텍스트 스택에 쌓입니다. 이 스택을 흔히 콜 스택이라고 부릅니다.

> [!IMPORTANT] 콜 스택
> 지금 실행 중인 함수와, 그 함수가 끝나면 돌아갈 곳을 기록하는 자료구조입니다. 나중에 들어간 것이 먼저 나오는(LIFO) 구조라서 함수를 호출하면 새 컨텍스트가 맨 위에 올라가고, 함수가 끝나면 빠집니다. 맨 위가 지금 실행 중인 컨텍스트이고, 바로 아래가 그 함수를 부른 쪽입니다.

함수 세 개로 보면 이렇습니다.

```js
function a() {
  b();
  c();
}
function b() {}
function c() {}
a();
```

![① 시작하면 콜 스택에 전역 컨텍스트만 있다. ② a()를 호출하면 전역 위에 a가 올라간다. ③ a 안에서 b()를 호출하면 b가 올라간다. ④ b가 끝나면 b가 빠지고 a가 다시 맨 위가 된다. ⑤ c()를 호출하면 c가 올라간다. ⑥ c가 끝나면 c가 빠진다. ⑦ a가 끝나면 전역만 남는다. 맨 위가 항상 지금 실행 중인 컨텍스트이고, b와 c는 콜 스택에 함께 있었던 적이 없다.](/posts/javascript-interview-follow-up-questions/call-stack.svg)

정리하면 함수를 실행할 때마다 실행 컨텍스트가 하나씩 생기고, 콜 스택은 그중 지금 진행 중인 것들만 들고 있다고 이해했습니다. 끝난 함수의 컨텍스트는 콜 스택에서 빠집니다.

컨텍스트가 들고 있는 핵심 정보는 이렇습니다.

| 구성 요소           | 쉽게 말하면                         | 담는 것                                                        |
| ------------------- | ----------------------------------- | -------------------------------------------------------------- |
| LexicalEnvironment  | 지금 위치에서 보이는 변수 목록      | `let`, `const`, `class`. 블록에 들어갈 때마다 새 목록으로 바뀜 |
| VariableEnvironment | 함수 전체에서 쓰는 변수 목록        | `var`, 함수 선언. 블록에 들어가도 그대로                       |
| this                | 함수 안에서 "이 객체"가 가리키는 값 | 함수를 어떻게 호출했는지로 정해짐(꼬리 2)                      |

3장에서 `var`는 블록을 무시하고 `let`은 블록마다 따로 생기는 이유가 이 차이입니다. 블록에 들어가면 LexicalEnvironment만 새 목록으로 바뀌고 VariableEnvironment는 함수 것 그대로입니다.

두 목록의 실제 내용은 Environment Record라는 구조에 들어 있습니다. Environment Record는 "변수 이름 → 값" 목록과, 바깥 목록을 가리키는 연결(`[[OuterEnv]]`)로 이루어집니다. 변수를 찾을 때 지금 목록에 없으면 이 연결을 따라 바깥 목록으로 올라갑니다. 이게 스코프 체인입니다.

컨텍스트는 두 단계로 동작합니다.

1. **생성 단계**: 코드를 실행하기 전에 컨텍스트 안의 코드를 처음부터 끝까지 훑어서, 선언된 이름(변수 이름, 함수 이름, 매개변수 이름)을 Environment Record에 등록합니다. "식별자 정보를 수집한다"고도 합니다.
2. **실행 단계**: 코드를 위에서부터 한 줄씩 실행합니다. 할당문에 도착하면 그때 Environment Record의 값을 바꿉니다.

```js
function run(id) {
  var count = 1;
  let name = "kim";
  function log() {}
}
run(7);
```

`run(7)`을 호출하면 본문 첫 줄을 실행하기 전에 Environment Record가 이렇게 채워집니다.

```yaml
id: 7 (매개변수는 넘긴 값으로 바로 채워짐)
count: undefined (var)
name: 초기화 안 됨 (let)
log: 함수 객체 (함수 선언은 통째로)
```

`= 1`, `= "kim"` 같은 할당은 이때 처리되지 않습니다. 생성 단계는 이름만 모으고, 값은 실행 단계에서 그 줄에 도착했을 때 들어갑니다.

**이렇게 실행 전에 선언을 Environment Record에 먼저 담아두는 것이 자주 듣는 호이스팅입니다.** 이름이 미리 등록돼 있으니, 선언보다 위에서 그 이름을 써도 엔진은 이미 그 이름을 알고 있습니다. 선언 종류마다 등록되는 값이 다른 이유와 그 결과는 5장에서 다룹니다.

> [!NOTE] 책마다 용어가 다른 이유
> ES3 시절 자료는 Variable Object, Activation Object, Scope Chain이라는 용어를 씁니다. ES5에서 Lexical Environment로 바뀌었고, ES2015부터는 this도 Environment Record 안으로 들어갔습니다. 이 글은 ES2015 이후 용어로 적었습니다.

에러의 스택 트레이스가 그 순간의 실행 컨텍스트 스택입니다.

#### 꼬리 1. 콜 스택이 넘치면 어떻게 되나요? 꼬리 재귀 최적화는 되나요?

`RangeError: Maximum call stack size exceeded`가 납니다. 한계 깊이는 엔진과 스택 크기 설정에 따라 다릅니다.

ES2015 표준에는 꼬리 호출 최적화(proper tail calls)가 들어 있습니다. strict mode에서 함수의 마지막 동작이 다른 함수 호출이면 현재 프레임을 재사용하는 규칙입니다. 하지만 이걸 구현한 주요 엔진은 Safari의 JavaScriptCore뿐입니다. V8과 SpiderMonkey는 구현하지 않았습니다. 프레임이 사라지면 스택 트레이스에서 호출 경로가 빠진다는 게 반대 이유 중 하나였습니다.

그래서 깊이를 예측할 수 없는 재귀는 반복문과 명시적 스택으로 바꿉니다.

```js
function sumTree(root) {
  let sum = 0;
  const pending = [root];
  while (pending.length > 0) {
    const node = pending.pop();
    sum += node.value;
    pending.push(...node.children);
  }
  return sum;
}
```

#### 꼬리 2. `this`는 어떻게 정해지나요?

함수를 **어떻게 호출했는지**로 정해집니다. 어디서 정의했는지가 아닙니다. 화살표 함수만 예외입니다.

| 호출 방식                                       | this                                                  |
| ----------------------------------------------- | ----------------------------------------------------- |
| `new Foo()`                                     | 새로 만든 객체                                        |
| `fn.call(obj)`, `fn.apply(obj)`, `fn.bind(obj)` | 넘긴 `obj`                                            |
| `obj.method()`                                  | 점 앞의 `obj`                                         |
| `fn()`                                          | strict mode면 `undefined`, 아니면 전역 객체           |
| 화살표 함수                                     | 자기 this가 없음. 정의된 위치 바깥의 this를 그대로 씀 |

위에 있을수록 우선합니다. `bind`로 묶은 함수도 `new`로 호출하면 묶어둔 this는 무시됩니다.

```js
const user = {
  name: "kim",
  regular() {
    console.log(this.name);
  },
  arrow: () => {
    console.log(this?.name);
  },
  nested() {
    function inner() {
      console.log(this?.name);
    }
    const innerArrow = () => console.log(this.name);
    inner();
    innerArrow();
  },
};

user.regular(); // kim
user.arrow(); // undefined
user.nested(); // undefined, kim
```

- `arrow`: 객체 리터럴의 중괄호는 스코프를 만들지 않습니다. 화살표 함수의 바깥은 모듈 최상위이고, 모듈 최상위의 this는 `undefined`입니다.
- `inner`: 메서드 안에서 정의했어도 `inner()`는 점 없이 호출했습니다. strict mode라 `undefined`입니다.
- `innerArrow`: 바깥인 `nested`의 this를 씁니다. `nested`는 `user.nested()`로 호출했으므로 `user`입니다.

#### 꼬리 3. 메서드를 콜백으로 넘기면 왜 this가 사라지나요?

```js
class Counter {
  count = 0;
  increase() {
    this.count += 1;
  }
}

const counter = new Counter();
const { increase } = counter;
increase(); // TypeError: Cannot read properties of undefined (reading 'count')

button.addEventListener("click", counter.increase); // this는 button
```

`counter.increase`는 함수 값만 꺼냅니다. 어느 객체에서 꺼냈는지는 함께 넘어가지 않습니다. 호출 시점에 점 앞에 객체가 없으니 기본 규칙이 적용되고, class 본문은 항상 strict mode라 `undefined`입니다. `addEventListener`는 콜백을 호출할 때 this를 리스너가 걸린 요소로 지정합니다.

해결 방법은 셋입니다.

```js
// 1. 넘기는 쪽에서 화살표 함수로 감싼다
button.addEventListener("click", () => counter.increase());

// 2. 생성자에서 bind한다
class BoundCounter {
  count = 0;
  constructor() {
    this.increase = this.increase.bind(this);
  }
  increase() {
    this.count += 1;
  }
}

// 3. 클래스 필드에 화살표 함수를 둔다
class ArrowCounter {
  count = 0;
  increase = () => {
    this.count += 1;
  };
}
```

3번이 가장 편하지만 트레이드오프가 있습니다. 메서드가 프로토타입에 한 번 있는 게 아니라 인스턴스마다 새로 만들어집니다. 인스턴스가 많으면 메모리를 더 쓰고, 자식 클래스에서 `super.increase()`로 부를 수 없습니다.

## 3. 스코프

### Q. 스코프가 무엇이고, 자바스크립트는 어떤 스코프를 쓰나요?

**답변**

스코프는 식별자를 참조할 수 있는 범위입니다. 자바스크립트는 렉시컬 스코프입니다. 함수의 바깥 스코프는 함수를 **어디서 호출했는지가 아니라 어디서 정의했는지**로 정해집니다.

```js
const level = "global";

function printLevel() {
  console.log(level);
}

function run() {
  const level = "local";
  printLevel();
}

run(); // global
```

호출한 위치로 정해지는 동적 스코프였다면 `local`이 나왔을 겁니다.

구현으로 보면 이렇습니다. 함수 객체가 만들어질 때 그 시점의 LexicalEnvironment를 내부 슬롯 `[[Environment]]`에 저장합니다. 함수를 호출하면 새 Environment Record를 만들고, 그 바깥 참조를 `[[Environment]]`로 연결합니다. 호출한 위치는 이 연결에 관여하지 않습니다. 이 `[[Environment]]`가 4장 클로저의 근거입니다.

### Q. 함수 레벨 스코프와 블록 레벨 스코프는 어떻게 다른가요?

**답변**

`var`는 함수 레벨 스코프입니다. 함수 본문만 스코프를 만들고 `if`, `for` 블록은 무시합니다. `let`, `const`, `class`는 블록 레벨 스코프입니다. 중괄호 블록마다 새 스코프가 생깁니다.

```js
function pickEnds(items) {
  if (items.length > 0) {
    var first = items[0];
    let last = items.at(-1);
  }
  console.log(first); // 블록 밖에서도 보인다
  console.log(last); // ReferenceError: last is not defined
}
```

차이가 가장 크게 드러나는 건 반복문 안의 비동기 콜백입니다.

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));
}
// 3, 3, 3

for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));
}
// 0, 1, 2
```

`var` 버전은 `i`가 함수 스코프에 하나뿐이고, 세 콜백이 같은 `i`를 봅니다. 콜백은 태스크로 실행되므로 그때는 반복문이 끝나 `i`가 3입니다. `let` 버전은 반복마다 새 환경이 만들어지고, 각 콜백이 자기 반복의 `i`를 봅니다.

#### 꼬리 1. `let`이 반복마다 새로 만들어진다면 `i++`는 이전 값을 어떻게 아나요?

표준의 `CreatePerIterationEnvironment` 동작입니다. 본문 실행이 끝나면 새 환경을 만들고 직전 반복의 `i` 값을 복사한 다음, 증가식 `i++`를 새 환경에서 실행합니다. 그래서 반복마다 바인딩은 따로이고 값은 이어집니다.

`const`는 일반 `for` 문에 쓸 수 없습니다. 증가식이 재할당이기 때문입니다. `for...of`에는 쓸 수 있습니다. `for...of`는 반복마다 새 바인딩을 선언하고 값을 넣을 뿐 재할당하지 않습니다.

#### 꼬리 2. `var`로 같은 결과를 내려면 어떻게 하나요?

함수를 호출해서 반복마다 새 함수 스코프를 만듭니다. `let`이 없던 시절 쓰던 방법입니다.

```js
for (var i = 0; i < 3; i++) {
  (function (index) {
    setTimeout(() => console.log(index));
  })(i);
}
// 0, 1, 2
```

#### 꼬리 3. 전역에서 `var`와 `let`으로 선언하면 차이가 있나요?

일반 `<script>`에서는 있습니다.

```js
var legacy = 1;
let modern = 2;

window.legacy; // 1
window.modern; // undefined
```

전역 Environment Record는 두 부분으로 나뉩니다. 전역 객체를 감싼 부분에는 `var`와 함수 선언이 들어가서 `window`의 프로퍼티가 됩니다. 나머지 부분에는 `let`, `const`, `class`가 들어가고 `window`에는 붙지 않습니다. 다만 같은 페이지의 다른 `<script>`에서는 `modern`이 보입니다. 전역 스코프 자체는 공유하기 때문입니다.

ES 모듈은 최상위 선언이 모듈 스코프에 들어가므로 `var`든 `let`이든 전역이 아닙니다. 번들러로 모듈을 쓰는 프로젝트에서 전역 변수 충돌을 거의 겪지 않는 이유입니다.

## 4. 클로저

### Q. 클로저가 무엇인가요?

**답변**

함수가 정의될 때의 렉시컬 환경을 기억해서, 그 환경을 만든 함수가 끝난 뒤에도 바깥 변수에 접근할 수 있는 현상입니다. 3장의 `[[Environment]]` 때문에 생깁니다.

바깥 함수가 반환되면 그 실행 컨텍스트는 콜 스택에서 빠집니다. 하지만 그 함수의 Environment Record는 안쪽 함수의 `[[Environment]]`가 참조하고 있어서 가비지 컬렉션 대상이 되지 않습니다.

```js
function createCounter() {
  let count = 0;
  return {
    increase: () => ++count,
    read: () => count,
  };
}

const counter = createCounter();
counter.increase();
counter.increase();
counter.read(); // 2
```

`count`는 반환된 두 함수로만 바꿀 수 있습니다. 바깥에서 직접 접근할 방법이 없으므로 상태를 숨기는 효과가 있습니다.

엄밀히 보면 모든 함수가 `[[Environment]]`를 가지므로 모든 함수가 클로저입니다. 보통 클로저라고 부르는 건 안쪽 함수가 바깥 함수보다 오래 살아남는 경우입니다.

### Q. 실무에서 클로저 때문에 문제를 겪은 적이 있나요?

**답변**

React의 stale closure가 대표적입니다.

```jsx
function Timer() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setSeconds(seconds + 1);
    }, 1000);
    return () => clearInterval(id);
  }, []);

  return <p>{seconds}</p>;
}
```

화면은 1에서 멈춥니다. 함수 컴포넌트는 렌더마다 다시 호출되고, 각 호출의 `seconds`는 그 렌더에 고정된 상수입니다. 의존성 배열이 비어 있어 effect는 첫 렌더 뒤에 한 번만 실행되고, 그 안의 interval 콜백은 첫 렌더의 `seconds`, 즉 0을 잡고 있습니다. 매초 `setSeconds(0 + 1)`만 반복합니다.

```jsx
setSeconds((prev) => prev + 1);
```

업데이터 함수를 넘기면 React가 최신 state를 인자로 줍니다. 클로저가 잡은 값을 읽지 않으므로 문제가 사라집니다. 의존성 배열에 `seconds`를 넣어도 동작하지만 매초 interval을 지우고 다시 만듭니다. state가 아니라 최신 props를 콜백에서 읽어야 한다면 `useRef`에 최신 값을 넣어두고 `ref.current`를 읽거나, React 19.2부터 정식 API가 된 `useEffectEvent`를 씁니다.

같은 자리의 컴포넌트가 렌더 사이에 무엇을 유지하고 무엇을 새로 만드는지는 [props가 바뀌었는데 useState는 왜 그대로일까?](/posts/prop-changed-but-state-didnt)에 따로 적었습니다.

#### 꼬리 1. 디바운스를 직접 구현해보세요

```js
function debounce(fn, delay) {
  let timerId;
  return function (...args) {
    clearTimeout(timerId);
    timerId = setTimeout(() => fn.apply(this, args), delay);
  };
}
```

`timerId`를 클로저로 유지하는 게 핵심입니다. 호출될 때마다 이전 타이머를 지우고 새로 걸기 때문에, 마지막 호출 뒤 `delay`만큼 조용해야 `fn`이 실행됩니다.

이어서 나올 질문이 두 개 있습니다.

- **반환 함수를 왜 화살표 함수가 아니라 `function`으로 썼나요?** 호출 시점의 this를 `fn`에 넘기려고 했습니다. 화살표 함수로 반환하면 this가 `debounce`를 호출한 곳의 this로 고정됩니다. 안쪽 `setTimeout` 콜백은 반대로 화살표 함수여야 바깥 함수의 this를 그대로 씁니다.
- **스로틀과 무엇이 다른가요?** 디바운스는 호출이 멈춘 뒤 한 번 실행합니다(검색어 입력). 스로틀은 호출이 계속돼도 일정 간격마다 한 번씩 실행합니다(스크롤 위치 추적).

#### 꼬리 2. 그 debounce를 React 컴포넌트 안에서 쓰면 어떻게 되나요?

```jsx
function SearchInput() {
  const [keyword, setKeyword] = useState("");
  const search = debounce((value) => fetchResults(value), 300);

  return (
    <input
      value={keyword}
      onChange={(event) => {
        setKeyword(event.target.value);
        search(event.target.value);
      }}
    />
  );
}
```

디바운스가 되지 않습니다. 키를 누를 때마다 `setKeyword`로 리렌더되고, 렌더마다 `debounce`가 새로 호출되어 새 `timerId`를 가진 새 클로저가 만들어집니다. 새 함수는 이전 렌더의 타이머를 모르기 때문에 지우지 못합니다. 결과적으로 300ms 늦게, 키 입력 수만큼 요청이 나갑니다.

렌더 사이에 같은 함수를 유지해야 합니다. `useMemo(() => debounce(...), [])`나 `useRef`로 한 번만 만들고, 언마운트될 때 남은 타이머를 정리합니다.

#### 꼬리 3. 클로저 때문에 메모리 누수가 생길 수 있나요?

클로저 자체가 누수는 아닙니다. 다 쓴 함수가 어딘가에 계속 등록돼 있으면, 그 함수가 잡은 환경도 같이 남는 게 문제입니다. 흔한 경우는 해제하지 않은 이벤트 리스너, 정리하지 않은 `setInterval`, 전역 `Map`에 넣고 지우지 않은 콜백입니다.

```js
function attachResizeLogger(rows) {
  window.addEventListener("resize", () => {
    console.log(rows.length);
  });
}
```

`window`가 리스너를, 리스너가 `rows`를 잡고 있어서 `rows`는 페이지가 살아 있는 동안 해제되지 않습니다. 리스너를 떼야 합니다.

```js
const controller = new AbortController();
window.addEventListener("resize", onResize, { signal: controller.signal });

controller.abort(); // 이 signal로 등록한 리스너가 전부 해제된다
```

React의 `useEffect` cleanup이 하는 일이 이것입니다.

엔진 쪽 사정도 하나 있습니다. V8은 안쪽 함수가 실제로 참조하는 변수만 남깁니다. 다만 같은 스코프에서 만든 클로저들은 그 저장 공간을 공유합니다. 그래서 한 클로저가 큰 객체를 참조하면, 그 객체를 쓰지 않는 다른 클로저가 살아 있는 동안에도 객체가 남습니다. Chrome DevTools의 Memory 탭에서 힙 스냅샷을 찍고 Retainers를 보면 무엇이 붙잡고 있는지 확인할 수 있습니다.

#### 꼬리 4. 클로저로 만든 private과 class의 `#private`은 어떻게 다른가요?

외부에서 접근할 수 없다는 점은 같습니다. 차이는 메서드가 어디에 있느냐입니다. 클로저 방식은 인스턴스를 만들 때마다 메서드 함수도 새로 만듭니다. `#` 필드를 쓰는 클래스는 메서드가 프로토타입에 하나만 있고 필드만 인스턴스마다 생깁니다. 인스턴스를 많이 만들면 클래스, 상태가 하나뿐인 모듈이면 클로저로 충분합니다.

## 5. 호이스팅, TDZ, var / let / const

### Q. 호이스팅이 무엇인가요?

**답변**

코드를 실행하기 전에 선언을 먼저 처리해서, 선언이 스코프 맨 위로 올라간 것처럼 보이는 현상입니다. 코드가 실제로 옮겨지지는 않습니다. 실행 컨텍스트가 만들어질 때 스코프 안의 선언을 전부 Environment Record에 등록하기 때문입니다.

모든 선언이 등록되지만 **초기화 시점**이 다릅니다.

| 선언           | 등록될 때 값            | 선언 전에 접근하면        |
| -------------- | ----------------------- | ------------------------- |
| `var`          | `undefined`             | `undefined`               |
| 함수 선언      | 함수 객체               | 호출 가능                 |
| `let`, `const` | 초기화 안 됨            | `ReferenceError`          |
| `class`        | 초기화 안 됨            | `ReferenceError`          |
| `import`       | 모듈 연결 단계에서 연결 | 모듈 본문보다 먼저 처리됨 |

함수 표현식은 함수가 아니라 변수 규칙을 따릅니다.

```js
greet(); // TypeError: greet is not a function
var greet = function () {};
```

`greet`는 `undefined`로 등록돼 있으므로 `ReferenceError`가 아니라 `TypeError`입니다. 에러 종류로 무엇이 등록돼 있었는지 알 수 있습니다.

### Q. `let`, `const`도 호이스팅되나요? TDZ가 무엇인가요?

**답변**

됩니다. 등록은 되지만 초기화되지 않은 상태로 남고, 선언문이 실행돼 초기화되기 전에 접근하면 `ReferenceError`가 납니다. 이 구간이 TDZ(Temporal Dead Zone)입니다.

호이스팅된다는 증거는 이 코드입니다.

```js
let x = "outer";

function show() {
  console.log(x); // ReferenceError: Cannot access 'x' before initialization
  let x = "inner";
}

show();
```

안쪽 `x`가 호이스팅되지 않는다면 바깥의 `outer`가 출력됐을 겁니다. 에러 메시지도 `x is not defined`가 아니라 `before initialization`입니다. 엔진이 안쪽 `x`를 이미 알고 있다는 뜻입니다.

"Temporal"인 이유는 코드 위치가 아니라 실행 시점이 기준이기 때문입니다.

```js
function read() {
  return value;
}

// read(); // 여기서 호출하면 ReferenceError
const value = 1;
read(); // 1
```

`read` 함수 본문은 선언보다 위에 있지만, 호출 시점에 `value`가 초기화돼 있으면 문제없습니다.

#### 꼬리 1. `typeof`로 확인하면 안전하지 않나요?

선언되지 않은 변수에는 안전하고 TDZ 변수에는 아닙니다.

```js
typeof notDeclared; // "undefined"

typeof later; // ReferenceError: Cannot access 'later' before initialization
const later = 1;
```

#### 꼬리 2. TDZ는 왜 있나요?

`const`가 가장 큰 이유입니다. `const`가 `var`처럼 `undefined`로 먼저 초기화된다면, 선언 전에는 `undefined`, 선언 후에는 실제 값으로 상수가 두 값을 갖게 됩니다. 그리고 선언 전에 변수를 쓰는 코드는 대부분 버그입니다. `undefined`로 조용히 진행하는 대신 즉시 에러를 내서 버그가 드러나게 합니다.

기본 매개변수에도 TDZ가 있습니다. 매개변수는 왼쪽부터 초기화됩니다.

```js
function createRange(start = end, end = 10) {}
createRange(); // ReferenceError: Cannot access 'end' before initialization
```

#### 꼬리 3. `const`로 선언한 객체는 바꿀 수 없나요?

바뀝니다. `const`가 막는 건 바인딩의 재할당이지 값의 변경이 아닙니다.

```js
const config = { retry: 3 };
config.retry = 5; // 가능
config = {}; // TypeError: Assignment to constant variable.
```

값까지 막으려면 `Object.freeze`를 쓰는데, 얕게만 얼립니다. 중첩 객체는 그대로 바뀝니다. TypeScript의 `readonly`, `as const`는 컴파일 타임 검사일 뿐 런타임에는 아무것도 막지 않습니다.

#### 꼬리 4. `var`를 쓰지 않는 이유는 무엇인가요?

1. 함수 스코프라 블록 안 변수가 블록 밖으로 보입니다.
2. 같은 스코프에서 다시 선언해도 에러가 없어서 덮어쓴 걸 모릅니다.
3. 선언 전에 접근하면 `undefined`라서 버그가 늦게 드러납니다.
4. 전역에서 선언하면 `window` 프로퍼티가 됩니다.

실무 기본값은 `const`이고, 재할당이 필요할 때만 `let`을 씁니다. 읽는 사람이 `const`를 보면 이 이름이 끝까지 같은 값을 가리킨다고 믿고 넘어갈 수 있습니다. ESLint의 `no-var`, `prefer-const`로 강제합니다.

#### 꼬리 5. `Cannot access 'X' before initialization` 에러를 실무에서 본 적이 있나요?

순환 import에서 자주 납니다. 모듈 A와 B가 서로를 import하면 한쪽이 먼저 평가되는데, 그때 상대 모듈의 `const` export는 아직 TDZ입니다. 배럴 파일(`index.ts`)로 re-export를 모아두면 의도하지 않은 순환이 생기기 쉽습니다. 8장 꼬리 3에서 코드로 봅니다.

## 6. Promise, async / await

### Q. Promise가 무엇이고, 콜백보다 나은 점은 무엇인가요?

**답변**

비동기 작업의 최종 결과를 나타내는 객체입니다. 상태는 pending에서 fulfilled 또는 rejected로 한 번만 바뀝니다. 바뀐 뒤(settled)에는 다시 바뀌지 않습니다.

콜백 방식에는 세 가지 문제가 있었습니다.

- 비동기 작업을 이어가려면 콜백 안에 콜백을 넣어야 해서 중첩이 깊어집니다.
- 에러 처리를 콜백마다 따로 해야 합니다.
- 콜백을 다른 함수에 넘기면, 그 콜백이 몇 번 호출될지, 호출이 되기는 할지 그 함수가 정합니다.

Promise는 `then` 체이닝으로 중첩을 펼치고, `catch` 하나로 앞 단계의 에러를 모두 받고, 결과가 한 번만 정해지는 것을 보장합니다. 그리고 `then` 콜백은 항상 마이크로태스크로 실행됩니다. 이미 settled된 Promise에 `then`을 걸어도 동기로 실행되지 않으므로, 상황에 따라 동기였다가 비동기였다가 하는 일이 없습니다.

#### 꼬리 1. `new Promise` 안의 코드는 비동기로 실행되나요?

아닙니다. executor 함수는 `new Promise`를 호출하는 즉시 동기로 실행됩니다.

```js
const p = new Promise((resolve) => {
  console.log("A");
  resolve("B");
  resolve("X");
  console.log("C");
});
p.then((value) => console.log(value));
console.log("D");
```

```yaml
출력: A → C → D → B
```

`resolve`를 호출해도 executor는 멈추지 않으므로 `C`가 출력됩니다. 두 번째 `resolve("X")`는 무시됩니다. 이미 settled됐기 때문입니다. `B`는 `then` 콜백이라 마이크로태스크로 실행되고 `D`보다 늦습니다.

#### 꼬리 2. `.then(onOk, onErr)`와 `.then(onOk).catch(onErr)`는 같나요?

다릅니다. `then`의 두 번째 인자는 같은 `then`의 첫 번째 인자에서 던진 에러를 받지 못합니다.

```js
fetchUser().then(
  (user) => user.profile.name, // 여기서 던진 에러는
  (error) => report(error), // 여기로 오지 않는다
);

fetchUser()
  .then((user) => user.profile.name)
  .catch((error) => report(error)); // fetchUser 실패와 위 콜백의 에러 모두 받는다
```

#### 꼬리 3. `Promise.all`, `allSettled`, `race`, `any`의 차이는 무엇인가요?

| 메서드       | 이행 조건                     | 거부 조건                      | 결과                             |
| ------------ | ----------------------------- | ------------------------------ | -------------------------------- |
| `all`        | 전부 이행                     | 하나라도 거부되면 즉시         | 입력 순서대로 값 배열            |
| `allSettled` | 전부 settled                  | 거부되지 않음                  | `status`와 `value`/`reason` 배열 |
| `race`       | 가장 먼저 settled된 것이 이행 | 가장 먼저 settled된 것이 거부  | 그 하나의 결과                   |
| `any`        | 하나라도 이행                 | 전부 거부되면 `AggregateError` | 처음 이행된 값                   |

여기서 바로 이어지는 질문이 있습니다. **`Promise.all`에서 하나가 실패하면 나머지 요청은 취소되나요?** 취소되지 않습니다. `Promise.all`이 거부될 뿐 나머지 작업은 끝까지 진행됩니다. Promise에는 취소 개념이 없습니다. 요청을 실제로 끊으려면 `AbortController`를 씁니다.

```js
const controller = new AbortController();

try {
  const [user, posts] = await Promise.all([
    fetch("/api/user", { signal: controller.signal }),
    fetch("/api/posts", { signal: controller.signal }),
  ]);
} catch (error) {
  controller.abort(); // 아직 진행 중인 요청을 끊는다
  throw error;
}
```

시간 제한만 필요하면 `fetch(url, { signal: AbortSignal.timeout(5000) })`로 충분합니다.

대시보드처럼 위젯 하나가 실패해도 나머지는 보여줘야 하는 화면은 `allSettled`, 데이터가 전부 있어야 의미가 있는 화면은 `all`을 씁니다.

### Q. async/await는 Promise와 어떤 관계인가요?

**답변**

Promise 위에 얹은 문법입니다. async 함수는 항상 Promise를 반환합니다. `return` 값은 이행 값이 되고, `throw`는 거부가 됩니다.

`await`은 Promise가 settled될 때까지 **그 async 함수만** 멈추고 제어를 호출한 쪽에 돌려줍니다. 스레드를 막지 않습니다. Promise가 settled되면 나머지 코드가 마이크로태스크로 재개됩니다. 함수 실행을 중간에 멈췄다 이어가는 구조는 제너레이터의 `yield`와 같습니다. async/await이 표준에 들어오기 전에는 제너레이터와 Promise를 조합하는 라이브러리로 같은 동작을 구현했습니다.

#### 꼬리 1. 아래 코드에서 개선할 점이 있나요?

```js
async function loadPage(userId) {
  const user = await getUser(userId);
  const notices = await getNotices();
  return { user, notices };
}
```

두 요청이 서로 의존하지 않는데 순차로 기다립니다. 걸리는 시간이 두 요청의 합입니다. 동시에 시작하면 둘 중 긴 쪽만큼 걸립니다.

```js
async function loadPage(userId) {
  const [user, notices] = await Promise.all([getUser(userId), getNotices()]);
  return { user, notices };
}
```

뒤 요청이 앞 요청의 결과를 써야 할 때만 순차로 둡니다.

#### 꼬리 2. `forEach` 안에서 `await`을 쓰면 어떻게 되나요?

```js
async function saveAll(items) {
  items.forEach(async (item) => {
    await save(item);
  });
  console.log("done"); // 저장이 끝나기 전에 출력된다
}
```

`forEach`는 콜백이 반환한 Promise를 기다리지 않습니다. `saveAll`도 저장 완료를 기다리지 않고 끝나고, 저장 중 에러가 나면 아무도 받지 않아 처리되지 않은 rejection이 됩니다.

```js
// 순차
for (const item of items) {
  await save(item);
}

// 병렬
await Promise.all(items.map((item) => save(item)));
```

#### 꼬리 3. `return await`는 불필요한 코드인가요?

`try/catch` 안에서는 결과가 다릅니다.

```js
async function withoutAwait() {
  try {
    return fetchData(); // fetchData가 거부돼도
  } catch {
    return "fallback"; // 여기로 오지 않는다
  }
}

async function withAwait() {
  try {
    return await fetchData();
  } catch {
    return "fallback"; // 여기로 온다
  }
}
```

`fetchData`가 거부되면 `withoutAwait()`는 거부되고, `withAwait()`는 `"fallback"`으로 이행됩니다. `return fetchData()`는 아직 settled되지 않은 Promise를 들고 함수를 떠납니다. 거부는 함수가 끝난 뒤에 일어나므로 `try` 블록이 받을 수 없습니다.

예전에는 `return await`이 마이크로태스크를 한 번 더 써서 느리다는 이유로 ESLint `no-return-await` 규칙이 이를 막았습니다. 엔진의 Promise 처리가 바뀌면서 이 근거가 사라졌고, 규칙은 8.46에서 deprecated됐습니다. Node 24에서 재보면 오히려 `return await p`가 `return p`보다 마이크로태스크 한 틱 먼저 이행됩니다.

#### 꼬리 4. 처리되지 않은 rejection은 어떻게 되나요?

브라우저는 `unhandledrejection` 이벤트를 발생시키고 콘솔에 에러를 찍습니다. 페이지는 계속 동작합니다. Node는 15부터 기본 동작이 프로세스 종료입니다. 서버에서 `catch` 하나를 빠뜨리면 서버가 내려갈 수 있습니다.

```js
window.addEventListener("unhandledrejection", (event) => {
  sendToErrorTracker(event.reason);
});
```

Sentry 같은 에러 수집 도구가 이 이벤트를 받아서 보고합니다.

## 7. undefined / null

### Q. `undefined`와 `null`은 어떻게 다른가요?

**답변**

둘 다 값이 없다는 뜻의 원시값이고, 누가 넣느냐가 다릅니다. `undefined`는 엔진이 넣는 "아직 할당되지 않음"입니다. 선언만 한 변수, 없는 프로퍼티, `return`이 없는 함수의 반환값, 넘기지 않은 인자가 `undefined`입니다. `null`은 개발자가 "값이 없음"을 의도적으로 넣을 때 씁니다.

```js
let selectedId; // undefined: 아직 고르지 않았다
selectedId = null; // null: 선택을 해제했다
```

동작 차이는 이렇습니다.

| 항목                          | `undefined`   | `null`            |
| ----------------------------- | ------------- | ----------------- |
| `typeof`                      | `"undefined"` | `"object"`        |
| `Number()`                    | `NaN`         | `0`               |
| `JSON.stringify` 프로퍼티     | 키가 빠짐     | `null`로 남음     |
| 기본 매개변수·구조분해 기본값 | 기본값 적용   | 기본값 적용 안 됨 |
| `== null`                     | `true`        | `true`            |

`typeof null`이 `"object"`인 건 첫 구현의 버그입니다. 값의 타입을 태그 비트로 구분했는데 객체 태그가 0이었고, `null`은 널 포인터라 태그 자리가 0이었습니다. 고치면 기존 웹 코드가 깨지기 때문에 그대로 남았습니다.

#### 꼬리 1. 기본값은 `null`에도 적용되나요?

적용되지 않습니다. 기본 매개변수와 구조분해 기본값은 `undefined`일 때만 적용됩니다.

```js
function greet(name = "guest") {
  return name;
}
greet(undefined); // "guest"
greet(null); // null

const { nickname = "익명" } = { nickname: null };
nickname; // null
```

API 응답에서 값이 없는 필드를 `null`로 주면 구조분해 기본값이 동작하지 않습니다. 이럴 때는 `nickname ?? "익명"`으로 받습니다.

#### 꼬리 2. `||`와 `??`는 어떻게 다른가요?

`||`는 왼쪽이 falsy(`false`, `0`, `""`, `NaN`, `null`, `undefined`)면 오른쪽을 씁니다. `??`는 왼쪽이 `null`이나 `undefined`일 때만 오른쪽을 씁니다.

```js
0 || 10; // 10
0 ?? 10; // 0
"" || "전체"; // "전체"
"" ?? "전체"; // ""
```

`0`이나 빈 문자열이 정상 값인 곳에서 `||`를 쓰면 버그가 됩니다.

```js
function getPageSize(options) {
  return options.pageSize || 20; // pageSize에 0을 넘겨도 20
}

function getPageSizeFixed(options) {
  return options.pageSize ?? 20; // null, undefined일 때만 20
}
```

#### 꼬리 3. `null`과 `undefined`를 한 번에 확인하려면 어떻게 하나요?

`value == null`입니다. `==`는 `null`과 `undefined`끼리만 같다고 보고 다른 값과는 같지 않다고 봅니다. `value === null || value === undefined`와 결과가 같습니다. ESLint `eqeqeq` 규칙도 `{ null: "ignore" }` 옵션으로 이 경우만 허용할 수 있습니다.

`!value`로 확인하면 `0`과 `""`까지 걸러지므로 의미가 다릅니다.

비교 연산자 쪽에는 함정이 하나 있습니다.

```js
null == 0; // false
null > 0; // false
null >= 0; // true
```

`>`, `>=` 같은 관계 비교는 `null`을 숫자 0으로 바꿔서 비교합니다. `==`는 숫자로 바꾸지 않고 `null`을 `undefined`하고만 같다고 봅니다. 규칙이 다른 두 연산이라 결과가 맞지 않습니다.

#### 꼬리 4. API를 설계할 때 둘을 구분해야 하는 경우가 있나요?

부분 수정(PATCH) 요청이 대표적입니다. 필드를 보내지 않으면 "바꾸지 않음", `null`을 보내면 "값을 지움"으로 구분합니다. 프론트에서 `undefined`로 두면 `JSON.stringify`가 키를 빼버리므로 이 구분이 그대로 전달됩니다.

```js
JSON.stringify({ nickname: undefined, bio: null });
// '{"bio":null}'
```

배열 안의 `undefined`는 빠지지 않고 `null`로 바뀝니다. `JSON.stringify([undefined])`는 `'[null]'`입니다.

## 8. ES Module vs CommonJS

### Q. ES Module과 CommonJS는 무엇이 다른가요?

**답변**

| 항목                 | CommonJS                        | ES Module                                   |
| -------------------- | ------------------------------- | ------------------------------------------- |
| 문법                 | `require`, `module.exports`     | `import`, `export`                          |
| 의존성이 정해지는 때 | 실행 중 (`require`는 함수 호출) | 실행 전 (`import` 선언은 최상위에만)        |
| 로딩                 | 동기                            | 파싱 → 연결 → 평가 단계로 나뉨, 비동기 가능 |
| 내보낸 값            | `module.exports` 객체           | 원본 변수와 연결된 live binding             |
| 최상위 this          | `module.exports`                | `undefined`                                 |
| strict mode          | 직접 선언해야 함                | 항상                                        |
| top-level await      | 불가                            | 가능                                        |
| 파일 경로            | `__dirname`, `__filename`       | `import.meta.url`, `import.meta.dirname`    |

가장 큰 차이는 정적이냐 동적이냐입니다. `require`는 일반 함수 호출이라 `if` 안에서 부를 수도 있고 경로를 변수로 만들 수도 있습니다. 그래서 코드를 실행하기 전에는 의존성을 확정할 수 없습니다. `import` 선언은 모듈 최상위에서 문자열 리터럴 경로로만 쓸 수 있습니다. 코드를 실행하지 않고도 의존성 그래프가 정해집니다. 아래 꼬리질문들은 대부분 이 차이에서 나옵니다.

#### 꼬리 1. live binding이 무엇인가요?

같은 카운터를 두 방식으로 내보내 봅니다.

```js
// counter.cjs
let count = 0;
function increase() {
  count++;
}
module.exports = { count, increase };

// main.cjs
const counter = require("./counter.cjs");
counter.increase();
console.log(counter.count); // 0
```

```js
// counter.mjs
export let count = 0;
export function increase() {
  count++;
}

// main.mjs
import { count, increase } from "./counter.mjs";
increase();
console.log(count); // 1
count = 5; // TypeError: Assignment to constant variable.
```

CommonJS는 `module.exports = { count }`가 실행되는 순간의 값 0을 객체 프로퍼티에 넣습니다. 그 뒤 모듈 안의 `count`가 바뀌어도 프로퍼티는 0입니다. ES Module의 `import`는 값을 복사하지 않고 원본 변수에 연결된 읽기 전용 참조를 만듭니다. 원본이 바뀌면 import한 쪽에서도 바뀐 값이 보이고, import한 쪽에서 재할당하면 에러가 납니다.

#### 꼬리 2. 트리 셰이킹이 ES Module에서 잘 되는 이유는 무엇인가요?

번들러는 코드를 실행하지 않고 분석합니다. ES Module은 어느 모듈에서 어느 이름을 가져오는지가 문법으로 고정돼 있어서, 쓰이지 않는 export를 빌드할 때 지울 수 있습니다. CommonJS는 `module.exports[name] = ...`처럼 실행해봐야 결과를 아는 코드가 가능해서 안전하게 지우기 어렵습니다.

ES Module이라고 다 지워지지는 않습니다. 모듈을 평가하는 것 자체가 부수 효과를 가질 수 있기 때문입니다. 전역 객체를 수정하는 폴리필이나 CSS import가 그렇습니다. 번들러는 부수 효과가 없다고 확신할 수 없으면 모듈을 남깁니다. 라이브러리는 `package.json`의 `"sideEffects": false`로 부수 효과가 없다고 알려줍니다.

배럴 파일로 re-export를 모았을 때 코드 스플리팅이 깨지는 경우는 [React.lazy를 썼는데 왜 다른 페이지까지 로딩될까?](/posts/vite-bundle-optimization)에서 측정했습니다.

#### 꼬리 3. 순환 참조가 있으면 어떻게 동작하나요?

두 방식의 결과가 다릅니다.

```js
// a.mjs
import { b } from "./b.mjs";
export const a = "a";

// b.mjs
import { a } from "./a.mjs";
export const b = "b";
console.log(a); // ReferenceError: Cannot access 'a' before initialization
```

`node a.mjs`로 실행하면 `a.mjs`가 의존하는 `b.mjs`가 먼저 평가됩니다. 바인딩 연결은 실행 전에 끝나 있으므로 `b.mjs`는 `a`라는 이름을 압니다. 하지만 `a.mjs` 본문은 아직 실행되지 않아서 `a`는 TDZ 상태입니다. 5장의 TDZ가 모듈 단위로 나타나는 경우입니다.

```js
// a.cjs
exports.before = "before";
const b = require("./b.cjs");
exports.after = "after";

// b.cjs
const a = require("./a.cjs");
console.log(a); // { before: 'before' }
```

CommonJS는 실행 중인 모듈의 `exports` 객체를 미완성인 채로 돌려줍니다. 에러 없이 `after`가 빠진 객체를 받습니다. 에러가 나지 않으니 문제를 늦게 발견합니다.

해결은 순환을 끊는 것입니다. 두 모듈이 같이 쓰는 부분을 세 번째 모듈로 빼거나, 배럴 파일 대신 실제 파일 경로로 import합니다.

#### 꼬리 4. Node에서 둘을 섞어 쓸 수 있나요?

파일 종류는 이렇게 정해집니다.

```yaml
.mjs: 항상 ES Module
.cjs: 항상 CommonJS
.js: 가장 가까운 package.json의 type이 module이면 ES Module, 없거나 commonjs면 CommonJS
```

- **ES Module에서 CommonJS를 import**: 됩니다. `module.exports`가 default export로 들어옵니다. named import는 Node가 정적 분석으로 찾아낼 수 있는 export만 됩니다.
- **CommonJS에서 ES Module을 불러오기**: 동적 `import()`로 됩니다. Promise를 반환합니다. Node 22.12부터는 top-level await이 없는 ES Module을 `require()`로도 불러올 수 있습니다.

동적 `import()`는 정적 구조의 예외입니다. 경로를 실행 중에 정할 수 있고 Promise를 반환합니다. 번들러는 동적 `import()`로 불러온 모듈을 별도 청크로 나눕니다. `React.lazy`도 이 동작을 이용합니다.

#### 꼬리 5. 브라우저의 `<script type="module">`은 일반 스크립트와 무엇이 다른가요?

- `defer`를 붙인 것처럼 동작합니다. HTML 파싱을 막지 않고, 파싱이 끝난 뒤 문서 순서대로 실행됩니다.
- 항상 strict mode이고, 최상위 선언이 전역이 되지 않습니다.
- 같은 URL의 모듈은 여러 번 import해도 한 번만 평가됩니다.
- 다른 출처의 모듈을 불러오려면 CORS 헤더가 필요합니다. 그래서 `file://`로 연 HTML에서는 모듈 스크립트가 동작하지 않습니다.
